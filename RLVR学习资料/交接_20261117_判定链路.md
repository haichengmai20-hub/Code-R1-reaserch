## 六、2026-11-18 续：可见性分层与 exec 时序

主文件新增 **§15**（[判定链路_候选到奖励.md](判定链路_候选到奖励.md#chain-visibility-exec)），固定三个结论：

1. **Q1 注释版 vs prelude**：模型可见的 `ListNode` 注释块是 prelude 的**子集**；相交部分去掉 `# ` 后逐字相等（`add-two-numbers` 实测 True）；prelude 额外有 imports、`list_node`、`is_same_list`（模型看不到，测试侧工具）。
2. **Q2 exec 时序**：`exec` 把字符串当程序**立即执行**——`def`/`class` 只创建对象、函数体与方法体不跑，但**模块级调用（构造、`Solution().solve()`）在 exec 期间就会跑**；**exec 后**恢复 6 个保留名，测试时方法体查 `globals` 得到环境版；**最终检查输出在「exec 后、逐条考试」阶段产生**（`repr(out)` + status）。
3. **`list_node`/`is_same_list`**：列表→链表、按值递归比较，是测试侧基础设施，不是模型 API。

**外部审查已回（2026-11-18，见主文件 §15.4）**：结论是 **「快照 + 恢复 6 个名字」只修部分名称冲突，不是安全边界**。已实测的绕过路径包括别名、默认参数、类属性、真闭包、方法内局部类、导入/容器引用、模块级已创建对象；更严重的是候选可改 `__coder1_reserved`、直接改环境类/函数（`ListNode.__init__`、`is_same_list.__code__`）、劫持 `repr`/`len`、恢复后再写 `globals`；nonce 不能认证已被控制的 reporter。推荐顺序：仅修兼容性 → 独立候选 dict；要抗主动篡改 → 独立 dict + 受限进程 + 父进程比较。另有两个实现细节：`None` 值恢复会保留候选绑定；`try/except/else` 的 `else` 块异常不被捕获。

### 6.1 2026-11-18 晚：Q2 收口（以旗舰 AI 复核结论为准）

**定稿一句话（后续引用以这段为准）：**

> **exec 期间先执行候选代码并建立状态；之后恢复六个名字，让相关全局查找使用环境定义，再运行候选算法接受测试。旧对象和旧引用不会被自动替换，它们可能影响结果；恢复只是部分名称冲突修补，不能替整个测试过程兜底。**

#### 6.1.1 用户三句说法的逐句判定

| 原话 | 判定 | 精确表述 |
|---|---|---|
| 「exec 期间是让模型自由发挥」 | **大致对** | 执行的是模型已生成的候选代码；它定义类/函数/变量、创建对象、调用函数。这些操作发生在**共享环境**里，所以可能覆盖环境原名、改变状态。 |
| 「exec 后真正要得到测试用的输出结果，再由 GT 里唯一对的辅助函数定义兜底」 | **部分对** | 对的一半：恢复六个名字后，测试期的相关全局查找走环境定义（例如用环境版 `list_node` 造输入）。需要收紧的：**测试期候选算法仍在运行**；环境辅助函数只负责按约定造输入/转换/检查输出，**不修候选算法、不修已有对象**。另外「唯一对」不准确，应叫「**判题环境规定使用的定义**」——符合相同约定的实现可以不止一种。 |
| 「这样会出问题吗？因为 exec 自由发挥期间一些对象的引用还是那时定义的」 | **担心成立** | 恢复全局名字不会替换已经保存的对象或引用。`saved = ListNode(9)` 在 exec 期间用模型类创建，恢复后 `return saved` 仍返回模型对象；只有 `return ListNode(9)` 才会在测试期查全局名、用环境类新建。**但保留模型对象不一定导致失败**，见 6.1.3。 |

#### 6.1.2 三个阶段，不是两个世界

「exec 期间是候选的世界，之后是测试的世界」只能当**比喻**。准确说是**同一个共享环境里的两个执行阶段 + 一次恢复**：

```text
exec 期间：
    执行候选顶层代码
    建立类、函数、对象、状态
    可覆盖 prelude 的 6 个保留名

恢复六个名字：
    只改 globals 里「名字 → 对象」的绑定

测试期：
    环境构造输入（如 list_node）
        ↓
    候选方法计算答案        ← 这里仍在运行模型写的代码，也可能读候选先前留下的状态
        ↓
    环境转换结果（__coder1_list / __coder1_tree）
        ↓
    父进程把转换结果与 expected 比较
```

所以不能理解成「后面由正确的环境代码完全接管」；**测试期仍会调用候选方法，也可能读取候选先前留下的状态**。

#### 6.1.3 旧对象怎么影响结果：直接、间接、不在路径上

```python
saved = ListNode(9)      # exec 期间创建；用哪个类，取决于那一刻 globals["ListNode"] 指向谁

def solve(self):
    return saved         # 直接：旧对象进入转换路径

def solve2(self):
    return saved.val + 1 # 间接：返回的是数字，但旧对象仍在计算路径上

def solve3(self):
    return 42            # 不在路径上：旧对象不影响本题
```

判定标准不是「对象属于哪个类」，而是：**所需属性和遍历行为符合约定 → 转换成功 → 转换出的值与 expected 相符**，三条全满足才 pass。

| 返回对象 | 数据情况 | 结果 |
|---|---|---|
| 模型类对象 | `.val`/`.next` 正常，值序列正确 | 可以通过（转换器不检查 `isinstance`） |
| 模型类对象 | 缺少 `.val` | 转换时报错 → `runtime_error:AttributeError` |
| 模型类对象 | `.val` 值错误 | 比较不通过 → `wrong_answer` |
| 环境类对象 | 值序列错误 | 同样 `wrong_answer` |
| 旧对象完全没进入测试路径 | — | 该对象本身不影响结果 |

**本机实测（2026-11-18，Windows / Python 3.14.6，用仓库真实 harness + 与数据集对齐的 prelude，prelude 见 `RLVR学习资料/examples/upstream_probe/crawler.py:39-60`）**：

| 情况 | `x` 是否被测试路径用到 | 结果 | verdict |
|---|---|---|---|
| A：模型 `ListNode` 用 `.v`，方法 `return module_x` | 用到 | 失败 | `runtime_error:AttributeError` |
| B：模型 `ListNode` 用 `.val`，方法 `return module_x` | 用到 | 通过 | `pass` |
| C：方法 `return ListNode(9)`（恢复后用环境类新建） | 不用 `x` | 通过 | `pass` |
| D：`x` 创建了，但方法不返回它 | 不用 | 通过 | `pass` |

原始事件（A / B）：

```text
A: {"case": 0, "status": "error", "error": "AttributeError"}   → runtime_error:AttributeError
B: {"case": 0, "status": "ok", "repr": "[9]"}                   → pass
```

#### 6.1.4 恢复能修什么、不能修什么

| | 内容 |
|---|---|
| **能修** | 测试期的全局名查找：环境版 `list_node` 造输入；候选方法体里的 `ListNode(...)` 解析到环境类；模型对 `list_node`/`is_same_list` 等同名函数的重定义被撤销。 |
| **修不了** | exec 期间已创建的对象；别名（`MyNode = ListNode`）、默认参数、类属性、真闭包、方法内局部类、模块级对象等已被抓走的引用；对象/类的内部状态（`ListNode.__init__`、`is_same_list.__code__` 被改）；`__coder1_reserved` 被改写；恢复后再写 `globals`。 |
| **已知实现缺口** | 恢复代码 `if value is not None: globals()[name] = value`：原来不存在或原值为 `None` 的名字会保留候选绑定；`try/except/else` 的 `else` 块内异常不被前面的 `except` 捕获（`protocol.py:114-132`）。 |

#### 6.1.5 三处措辞纠正（旗舰 AI 复核）

| 上一轮说法 | 问题 | 改为 |
|---|---|---|
| 「exec 对调用方是**原子**的，要硬插只能上 `sys.settrace`」 | 「同步调用」不等于「原子操作」；exec 内部可以调用其他函数/回调、抛异常，也可能永不结束；「只能用 settrace」不是普遍结论。 | 「**在这段普通同步流程中，写在 exec 后面的恢复代码，要等 exec 返回之后才执行。**」 |
| 「只有返回旧对象、且字段不对，才会失败」 | 范围说窄了：旧对象可以**间接**参与（`return saved.val + 1`），返回数字也可能因旧对象缺字段或值错而失败。 | 按 6.1.3 的三条标准判定；「属性对就通过」改成「属性与遍历符合约定、转换成功、转换值与 expected 相符才通过」。 |
| 「expected 留在父进程就是**硬隔离**」 | 不把 expected 传给候选是有价值的设计，但是否真正阻断其他访问路径，要看进程创建方式、权限和完整实现；也不能由此推出子进程 reporter 可信。 | 「**期望答案不进入子进程是重要设计；它不构成对子进程行为的完整隔离证明。**」nonce 只能过滤「不是本次运行」的输出，不能认证被候选控制的 reporter。 |

#### 6.1.6 `__coder1_list` 自身的边界（环境辅助函数也要验证）

`protocol.py:101-106`：

```python
def __coder1_list(head):
    out = []
    while head is not None and len(out) < 100000:
        out.append(head.val)
        head = head.next
    return out
```

- 达到 100000 就返回，**没有检查链表是否仍有剩余节点** → 超长链表会被**静默截断**。
- 父进程做的是**精确比较**（`_same`，`protocol.py:143-148`；调用在 `:181`），不是前缀比较。因此普通情况下截断会造成长度不符 → `wrong_answer`；但若 expected 恰好等于截断后的前缀（例如 expected 本身就有 100000 项），一个更长且错误的结果也可能通过。
- 结论：**不能因为辅助函数属于环境就假定它一定正确**；环境侧同样需要边界测试。

#### 6.1.7 最终口径（替代所有更早的强表述）

1. **exec 期间**：执行候选顶层代码，建立类/函数/对象/状态；可覆盖 6 个保留名。
2. **恢复**：只改 `globals` 名字绑定；修部分名称冲突，不修对象、不修引用、不修内部状态。
3. **测试期**：环境造输入 → **候选方法仍在运行** → 环境转换 → 父进程比较。
4. **旧对象**：可能直接或间接影响结果；是否失败看属性/遍历/值是否符合约定，而不是看它属于哪个类。
5. **安全边界**：期望答案不进子进程是设计优点，但不是「硬隔离」证明；nonce 不是认证；彻底方案是独立候选 dict + 受限进程 + 父进程比较。
