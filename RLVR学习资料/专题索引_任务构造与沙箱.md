## 专题一：Task 的选取、筛选与构造

**一句话机制：** 先定来源和许可，读成能执行的任务（题面、接口、测试、入口），再按质量、可执行、去重、训练/评测隔离、长度、难度筛选，最后把题面、签名、约束和输出格式写成 actor prompt——测试和答案藏起来。Code-R1 原版的选取只做了去重和粗过滤，没有对评测集去污染，也没有按当前模型的难度筛题。

## 专题二：GT 构造

**一句话机制：** GT 是「已接受的测试」的评分接口表示：`json.dumps({"functional": test + "\n\ncheck(" + entry_point + ")"})`，判分时和候选代码拼成一个程序跑；它不是参考解。原版不拼原始 `prompt` 前缀，121 道依赖前缀辅助函数的题必然 `NameError`；补强版把前缀存进 `prelude` 字段，判分先拼前缀。

| 层次 | 看哪里 | 讲了什么 |
|---|---|---|
| 先读 | [00 第 ② 站](00_一条记录从原始Task到训练.md#station-2) | `leetcode2k()` 做的三件事：题面 → prompt、测试 + 入口 → GT 字符串、参考解 → 履历 |
| 先读 | [01 统一 schema](01_数据理解与GT构建.md#schema-1)、[metadata 字段字典](01_数据理解与GT构建.md#metadata-fields) | 一行的形状；三层字段；`case_index`、`test_version` 怎样让每条 assert 可追溯 |
| 先读 | [01 内部审查和外部审查](01_数据理解与GT构建.md#internal-external-review)、[出错时在哪一层处理](01_数据理解与GT构建.md#error-layers-1) | 121 题前缀问题是内部审查能查出来的；一条坏 expected 只隔离一行，题意冲突才隔离整题，测试改了就升版本 |
| 动手 | [作业 1.3](01_数据理解与GT构建.md#assignment-1-3) | 从接受的测试追到 GT：解码、逐条核对 assert 与 `case_index`、入口核对、正负程序结果 |
| 深读 | [主框架 A6 GT 封装 `gt-packaging`](RLVR工业流程.md#gt-packaging) | 序列化、版本化、manifest；GT 与 Oracle、Reference Code、Reference Policy 的区别 |
| 补强版 | [补强项 1：GT 执行契约](examples/source-supplements/README.md#supplement-1) | `prelude` 字段；补强版下训练集 1877/1890、验证集 199/200 通过，剩下 14 题全缺第三方库 |
| 代码 | [coder1.py](../examples/data_preprocess/coder1.py) 的 `process_fn`、[coder1_plus.py](../examples/data_preprocess/coder1_plus.py) | 原版拼法与补强版 `prelude`；`verify_gt_contract.py` 做 2090 题两种契约对照 |

本课的数字：LeetCode 53 的 3 条 seed 断言 `[-2,1,-3,4,-1,2,1,-5,4] → 6`、`[1] → 1`、`[5,4,-1,7,8] → 23`，答案全是正数，抓不住允许空子数组的错解。

## 专题三：expected output 怎么来、oracle 与测试扩展

**一句话机制：** 期望输出要有接受依据：已有的可信结果直接复用，新加的输入先按约束校验合法，再用参考解算、用独立 oracle（按题意直接计算、写法和参考解不同）核对，一致才接受，不一致隔离，没有 oracle 的保持待审核；只有接受的用例进 GT，测试版本随之变化。测试够不够不看条数，看能不能抓住确认过的错解——变异审计给杀死率，但杀死率高不等于够。

| 层次 | 看哪里 | 讲了什么 |
|---|---|---|
| 先读 | [01 文字版导读第三、四节](01_数据理解与GT构建.md#guide-1) | 校验、审查、过滤的分工；「测试够不够，不看条数，看能不能抓住确认过的错解」 |
| 动手 | [作业 1.2](01_数据理解与GT构建.md#assignment-1-2) | 逐条核对 input 与 expected；追加一条自己的小数组和手算的 expected，再追加一条同输入、故意配错的；hash 只证明输入对齐不证明答案对 |
| 深读 | [主框架 A3 准备测试 `tests`](RLVR工业流程.md#tests) | 输入、期望输出逐条配对；来源一致性检查 |
| 深读 | [主框架 A4 求解与核对答案](RLVR工业流程.md#a4-answers)、[条件分支：用参考程序求新增输入答案时](RLVR工业流程.md#a-reference-answers)、[答案核验 `answer-validation`](RLVR工业流程.md#answer-validation) | 方法可换，接受依据要保留；参考解、暴力枚举、多解互证各证明到哪一步 |
| 深读 | [主框架 A5 测试验收与扩展 `test-strength`](RLVR工业流程.md#test-strength) | 错解表：允许空子数组、直接返回总和、只返回最大元素、前缀和漏掉空前缀……哪条测试能抓住哪种错解 |
| 面试 | [01 面试深挖](01_数据理解与GT构建.md#interview-1) | 「GT、Oracle、参考解谁先做」「一条坏 expected 影响什么」「Code-R1 的 LeetCode 测试够吗」 |
| 补强版 | [补强项 2：测试强度审计](examples/source-supplements/README.md#supplement-2) | 对参考解做单点变异（`<` 改 `<=`、`max` 换 `min`、常数加一），看现有测试能否判失败；2014 题 17316 个变异体，样例测试杀死 81%；存活的只是可疑，要找到区分输入才算错解 |
| 补强版 | [补强项 3：测试补充与逐条审核](examples/source-supplements/README.md#supplement-3) | 候选输入 → 校验合法 → 参考解算 → oracle 核对 → 接受/隔离/待审；LeetCode 53 杀死 9/9 仍放过 wrong_empty，oracle 补 10 条后才抓住 |
| 代码 | [coder1_plus_tests.py](../examples/data_preprocess/coder1_plus_tests.py) | `audit_test_strength`（变异审计）、`audit_new_cases`（逐条审核）、`extend_test`（追加进 GT） |
| 代码 | [coder1_plus_oracles.py](../examples/data_preprocess/coder1_plus_oracles.py) | 每题 `generate / validate / oracle` 三个函数，7 道示范题；扩到更多题照格式加 |
| 工具 | `verify_test_quality.py`（补强项 2、3 的验证，抽 200 题约 1 分钟，`--all` 约 7 分钟）、`coder1_plus.py --augment_cases` | 跑审计、生成 `accepted_cases.json`、追加进 GT 并升 `test_version` |

本课的数字：8 条接受、7 条隔离的演示；全负输入 `[-3,-2,-5] → -2` 抓住 `wrong_empty`；杀死率 81% 但 LeetCode 53 的 9/9 仍漏错解。

## 专题四：Sandbox 构造

**一句话机制：** 执行后端像考场，管权限、网络、资源、超时；判分器像判卷机，管格式、拼接、比较。考场守规矩不证明卷子答完了，判卷机正确也不证明考场安全，两者分别验收。原版四个缺口：提前退出拿满分、超时不清理、判题故障记 0.0 混进组内统计、期望答案和候选代码同进程。补强版：受保护的判题协议（期望答案不进候选进程、逐条报告）、结构化执行层（状态分类、耗时、超时杀进程组；macOS 用 sandbox-exec，Linux 用 firejail）、判题故障先重试仍失败整组作废。

| 层次 | 看哪里 | 讲了什么 |
|---|---|---|
| 先读 | [00 第 ④ 站](00_一条记录从原始Task到训练.md#station-4) | 一个回答怎样变成 −1.1 / 0.1 / 1.1：格式门 + 拼断言跑一遍 + 看退出码 |
| 先读 | [02 三个角色](02_Verifier与任务池验收.md#prerequisites-2)、[判分七步](02_Verifier与任务池验收.md#pipeline-2) | 判分器 / 执行后端 / 奖励管理器各自的输入输出；第 4 步 firejail 的限额：进程 32、文件 32、单文件 2 MB、内存 4 GB、30 秒、禁 socket |
| 先读 | [02 执行边界 `execution-gaps-2`](02_Verifier与任务池验收.md#execution-gaps-2) | 原版四个缺口怎么复现、补强版怎么堵；本机 sandbox-exec 禁网、限写、禁读仓库的实测表 |
| 动手 | [作业 2.2](02_Verifier与任务池验收.md#assignment-2-2) 第 3 问 | 为什么把 firejail 换成 docker 也堵不住 `early_exit` |
| 深读 | [主框架第三章 Sandbox 与 Verifier 的工程关系 `execution-boundary`](RLVR工业流程.md#execution-boundary) | 用仓库理解具体边界；Sandbox 总执行预算；四个后端（firejail / docker / ces / kira）各看什么判成功 |
| 深读 | [主框架 A7 Verifier + Sandbox](RLVR工业流程.md#verification)、[第五章 Verifier 的构造与内部执行流程](RLVR工业流程.md#verifier-internals) | 机制复现与可信运行分别验收；在线执行的步骤 |

| 补强版 | [补强项 4：受保护的判题协议](examples/source-supplements/README.md#supplement-4) | 期望答案不进候选进程，子进程逐条报告输出，判分方比较；2090 题断言只有三种写法全部覆盖；`compare=unordered_outer` |
| 补强版 | [补强项 5：结构化执行层与隔离后端](examples/source-supplements/README.md#supplement-5) | 状态分类（正常、编译错、运行错、内存超限、超时、被杀、判题故障）、耗时、超时杀进程组；`CODER1_PLUS_SANDBOX` 选后端 |
