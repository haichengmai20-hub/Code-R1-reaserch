# 事故报告：your-01 第 65–66、129–130、193–194 步存盘后判题故障（推演）

**现象。** 每次存完 checkpoint 的后一步，reward 掉 0.10–0.14，再一步半恢复，第三步回到原位：

| 存盘步 → 后两步 | reward | 超时 / 重试后仍失败 / 作废组 | `timing_s/reward` |
|---|---|---|---|
| 64 → 65 → 66 → 67 | 0.458 → 0.342 → 0.369 → 0.427 | 15 / 8 / 4 组；10 / 5 / 2 组 | 23 → 65 → 65 → 22 秒 |
| 128 → 129 → 130 → 131 | 0.506 → 0.411 → 0.463 → 0.530 | 14 / 7 / 3 组；9 / 4 / 2 组 | 26 → 66 → 67 → 33 秒 |
| 192 → 193 → 194 → 195 | 0.553 → 0.412 → 0.480 → 0.569 | 15 / 8 / 4 组；8 / 4 / 2 组 | 22 → 68 → 69 → 20 秒 |

共作废 17 组 / 3,200（0.5%），6 步各多约 40 秒。

**三条证据链（不看日志只看指标也能定位）：**

1. 三次都紧跟 `timing_s/save_checkpoint`（第 64 / 128 / 192 步各 140–170 秒），周期性，不是随机抖动：128–200 步去掉事故步的 reward 标准差只有 0.018，而三次跌幅 0.10–0.14。
2. `timing_s/reward` 从 25 秒翻到 64–69 秒——两轮 10 秒的沙箱启动超时串在 64 进程池里；而 `rewards/min` 仍是 −1.1（格式错还在判，不像参考 run-01 那次所有分数被原版管理器记成 0.0），`ppo_kl`、`pg_clipfrac`、`grad_norm` 在 64–67 步没动，所以不是策略走偏。
3. 控制台（[incident_step65-66.log](../logs/your-01/incident_step65-66.log)）：15 条 `[prime_plus] infra error: sandbox start timeout (10.0s) in /data/tmp/judge/…; retrying once`，然后一条汇总 `{'policy': 'neutralize_group', 'samples': 128, 'infra_errors_after_retry': 8, 'neutralized_groups': 4, 'neutralized_samples': 32, 'retried': 15}`。落盘 [rollouts/your-01/65.jsonl.gz](../rollouts/your-01/65.jsonl.gz) 前 4 组 32 条分数全是 0.0。

**第 65 步的算术。** 作废 32 条；剩 96 条里 39 过、53 败、4 格式错：(1.1 × 39 + 0.1 × 53 − 1.1 × 4) / 128 = 0.342，与指标行一致。作废的 32 条若正常判，均值回到 0.44 上下（邻步 0.458 / 0.427）。

**原因。** 每份 checkpoint 98 GB 落到数据盘后，`save` 返回了但页缓存写回还要三四分钟把盘占满；判题临时目录 `/data/tmp/judge` 与它同盘，firejail 建私有目录超过 10 秒就启动超时。prime_plus 把它记成判题故障、重试一次，约一半成功，仍失败的按 uid 整组作废（分数 0.0、advantage 0），梯度没被污染——这是它和参考 run-01 事故的本质区别。

**反证两条。** 第 34 / 96 / 121 步的判题时间并没有尖峰（LeetCode 题判题稳定在 25 秒上下），所以不能拿「判题慢」解释；reward 的自然抖动 ±0.02，解释不了 0.10 以上的三次同步下跌。

**修法与验证。** your-02 把判题临时目录改到 tmpfs（`/dev/shm/judge`，内存 512 GiB 够用；每步 128 条候选加测试不到 100 MB）。第 257 / 321 / 385 步 `timing_s/reward` 25.0 / 23.5 / 27.5 秒，作废 0 组（[after_save_step256-258.log](../logs/your-02/after_save_step256-258.log)）。
