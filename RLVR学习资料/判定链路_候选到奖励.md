## 一、全链路一句话

```text
模型吐出的整段文本
   └─① 格式门 + 抽代码块 ──→ 候选代码（纯 Python 片段）
                                   │
GT 数据行（prelude + functional）──┤
                                   ▼
        子进程程序 = prelude + harness + 候选代码 + 逐条调用（期望答案不进去）
                                   ▼
        子进程按 nonce 打事件：start / case i / done / solution_error
                                   ▼
        判分方自己拿 expected 逐条比对 → passed / 逐条 verdict
                                   ▼
        奖励管理器：分数写进 reward_tensor 的「最后一个有效回答 token」
                                   ▼
        core_algos 按 uid 求和 → GRPO 组内标准化 → advantage
```

一句话记：**抽取在父进程，执行在子进程，期望答案只在父进程；分数是标量，原因是结构化信息；管理器只搬运与兜底，不判断对错。**

## 二、一条完整候选（candidate）长什么样

它不是一个单独的"代码字段"，**就是一整段解码后的文本**：

```python
# verl/workers/reward_manager/prime_plus.py:57
sequences_strs = self.tokenizer.batch_decode(data.batch['responses'], skip_special_tokens=True)
```

`responses` 是模型生成部分的 token（不含 prompt）。真实形态：

````text
<think>
子数组和问题：维护以当前元素结尾的最大和 f，以及全局最大 ans。
对每个 x，f = max(f, 0) + x；ans = max(ans, f)。
</think>
<answer>
```python
class Solution:
    def maxSubArray(self, nums: List[int]) -> int:
        ans = f = nums[0]
        for x in nums[1:]:
            f = max(f, 0) + x
            ans = max(ans, f)
        return ans
```
</answer>
````

| 事实 | 出处 |
|---|---|
| system prompt 就要求 `<think>…</think>` + `<answer>…</answer>` | `examples/data_preprocess/coder1.py:51-54` |
| 只解码 response，不解码 prompt（否则格式门永远过不了） | `prime_plus.py:57`；`naive.py` 是踩这个坑的对照 |
| `skip_special_tokens=True` → EOS 不在字符串里；有效长度另由 `attention_mask` 算 | `prime_plus.py:56` |

## 三、提取：文本 → 候选代码（并纠正一个常见误解）

### 3.1 `exec(compile(...))` 不是提取

**提取发生在父进程，`exec` 是子进程在执行已经提取好的代码，中间隔了一个 `repr()`。**

```python
# verl/utils/reward_score/coder1_plus/__init__.py:84-85（父进程：抽取）
strict        = _orig.validate_response_structure(solution_str)
solution_code = _orig.extract_code_from_string(solution_str)      # ← 真正的“提取”在这里

# :111（父进程：拼程序）
result = sandbox.run_python(protocol.build_harness(gt["prelude"], solution_code, entry, cases, nonce), ...)
```

```python
# protocol.py:115（模板里用 !r）
exec(compile({solution!r}, "<solution>", "exec"), globals())
```

`!r` 就是 `repr()`：把多行 Python 压成带 `\n` 转义的单行字符串字面量，安全嵌进程序。

| 阶段 | 进程 | 动作 | 产物 |
|---|---|---|---|
| 抽取 | **父进程**（判分方） | 正则找最后一个 `<answer>` → 拼所有代码块 | `solution_code`（纯 Python 文本） |
| 拼装 | 父进程 | `repr(solution_code)` 嵌进模板 | `program`（一整段源码字符串） |
| 执行 | **子进程** | 写 `program.py` → 启动 → `exec` | 事件流 stdout |
| 判分 | **父进程** | 拿 `cases` 的 expected 比对 | verdict |

三个关键点：

1. `exec` 用的是 **`globals()`** —— 即 prelude 那一层命名空间。候选与 `ListNode`/`list_node` 住在同一个字典里，**这就是 BC-24 的入口**。
2. 候选是**字符串**不是模块；`compile(..., "<solution>", "exec")` 的第二个参数只是 traceback 里的文件名标签。
3. `try/except BaseException` 包住 `exec`，所以 `sys.exit(0)`（抛 `SystemExit`）也会被捕获 → `solution_error` 事件。

### 3.2 原版提取（两步，简单也糙）

```python

```

实测输出：

```text

        ans = f = nums[0]
        ...

### 3.3 补强版的 fallback（补强项 9）

```python
# coder1_plus/__init__.py:84-97
strict = _orig.validate_response_structure(solution_str)
solution_code = _orig.extract_code_from_string(solution_str)
extraction = "strict" if strict and solution_code else ("fallback" if solution_code else "none")

即：标签不合格但正文有完整代码块 → 照样执行，只是格式分从 +0.1 变 −0.1；一个代码块都没有 → 直接 −0.1，不进沙箱。

> **口径校准：** 原版"取最后一个 `<answer>` 里所有代码块拼接"与原生 LeetCodeDataset 的 `extract_completion`（取最长块）**不同**，是两个项目的行为差异，不是 bug。

## 四、GT 长什么样（候选不进 GT）

GT 是数据行里**冻结好**的 `reward_model.ground_truth` 字符串，训练时只读不改：

```python
# 原版：examples/data_preprocess/coder1.py:325-327
"ground_truth": json.dumps({"functional": f"{example['test']}\n\ncheck({example['entry_point'].strip()})"})

# 补强版：examples/data_preprocess/coder1_plus.py:154-160
functional = f"{test}\n\ncheck({record['entry_point'].strip()})"
gt = {"prelude": record["prompt"], "functional": functional}
if ANY_ORDER.search(...) or record["task_id"] in UNORDERED_OVERRIDES:
    gt["compare"] = "unordered_outer"
```

LeetCode 53 的真实 GT（实测打印）：

```json
{"prelude": "from typing import *\n\nfrom functools import *\nfrom collections import *\n...\ninf = float('inf')\n",
 "functional": "def check(candidate):\n    assert candidate(nums = [-2,1,-3,4,-1,2,1,-5,4]) == 6\n    assert candidate(nums = [1]) == 1\n    assert candidate(nums = [5,4,-1,7,8]) == 23\n\n\ncheck(Solution().maxSubArray)"}
```

| 字段 | 内容 | 作用 |
|---|---|---|
| `prelude` | 数据集原始 `prompt`（`from typing import *` 那一坨，含 `TreeNode`/`list_node` 等 helper） | 补强项 1：树/链表 121 题靠它才不 `NameError` |
| `functional` | `def check(candidate):` + 若干 `assert` + 末尾 `check(入口)` | 测试本体 |
| `compare` | 可选，`unordered_outer` | 68 道「in any order」题忽略列表外层顺序 |

**这就是"test = 题面样例"的实体**：3 条断言 = 题面 3 个 example，中位数 2 条。GT 里没有任何"期望代码"，只有期望值。

## 五、判定程序全貌：prelude + 候选 + 断言 + 接口

### 5.1 先把 GT 拆开（`protocol.parse_cases`，`:36-75`）

```python
entry = "Solution().maxSubArray"      # 来自末尾 check(...) 的参数
cases = [
  {"call": "candidate(nums=[-2, 1, -3, 4, -1, 2, 1, -5, 4])", "kind": "value", "expected": 6,  "label": "assert-1"},
  {"call": "candidate(nums=[1])",                              "kind": "value", "expected": 1,  "label": "assert-2"},
  {"call": "candidate(nums=[5, 4, -1, 7, 8])",                 "kind": "value", "expected": 23, "label": "assert-3"},
]
```

只支持三种断言写法（`candidate(...) == 字面量`、`is_same_tree(...)`、`is_same_list(...)`），2090 题全覆盖；拆不开就 `UnsupportedTests`，退回旧拼接契约。

**拆开后两侧分离**：`call` 进子进程，`expected` 留在判分方。

### 5.3 三个设计细节

1. **nonce 每次随机**（`secrets.token_hex(16)`，`coder1_plus/__init__.py:110`）：候选既不知道标记、也不知道期望值，伪造不出一份"正确的报告"。
2. **环境定义优先**：exec 前记下 `ListNode/list_node/is_same_tree` 等，exec 后还原。否则候选写错一个 `ListNode` 会污染 prelude 的 `is_same_list`，让正确解被误判失败（BC-24 实锤）。
3. **树/链表归一化**：`__coder1_tree` 转层序列表、`__coder1_list` 转普通列表，判分方只比 Python 字面量。

## 六、判分方看什么：七步算法

```python
# protocol.py:151
def judge(stdout, cases, nonce, compare="exact")
```

| 输入 | 来源 | 用途 |
|---|---|---|
| `stdout` | 子进程标准输出 | 唯一的"事实来源" |
| `cases` | 父进程 `parse_cases` 拆出的 `(call, kind, expected, label)` | 提供 expected（**子进程从没见过**） |
| `nonce` | 父进程 `secrets.token_hex(16)` | 过滤谁说的话算数 |
| `compare` | GT 的 `compare` 字段，默认 `exact` | 列表是否忽略外层顺序 |

**它不看的东西**（最容易被追问）：不看退出码、不看 stderr、不看候选打印的非标记行。退出码只在上一层用于区分 `infra_error` / `timeout`（`coder1_plus/__init__.py:115-117`）。

```text
① 算标记      marker = "@@CODER1_PLUS@@" + nonce + " "
② 逐行过滤    不以 marker 开头的行 —— 直接丢弃（候选的 print 噪声、错误信息都在这被扔掉）
③ 解析 JSON   marker 之后的部分 json.loads 失败 —— 跳过
④ 分两类记录  "case" 在记录里 → results[索引] = 记录（setdefault：同一条只认第一次报告）
              否则 → events 追加；solution_error 记第一个非空的
⑤ 逐条裁决    对 cases 里每个索引，查 results（见第七节）
⑥ 判完整性    completed = "start" ∈ events and "done" ∈ events and solution_error 为空
⑦ 判通过      passed = completed and 所有 verdict == "pass"
```

**核心设计：`passed` 是"完整性 ∧ 逐条全对"的合取。** 少一个完成事件、少一条结果，都直接失败——这就是"提前退出 = 失败"的实现。

## 七、五类 verdict 与真实例子

```python
# protocol.py:168-184
verdict = "missing"            # 没这一条的报告
        | "runtime_error:X"    # 这一条抛异常
        | "unparseable_output" # repr 解析不回来
        | "wrong_answer"       # 对不上 expected
        | "pass"
completed = "start" in events and "done" in events and "solution_error" not in events
passed = completed and all(v == "pass" for v in verdicts)
```

<a id="chain-verdict-vs-error"></a>

## 八、`wrong_answer` 和 `solution_error` 不是兄弟

一句话：**`wrong_answer` 是用例级的"判分结论"，`solution_error` 是程序级的"执行事件"。** 一个由父进程算出来，一个由子进程报出来。

### 8.1 层次表

| | `wrong_answer` | `solution_error` |
|---|---|---|
| 是什么 | 某一条用例的 verdict | 整次执行的一个事件 |
| 谁产生 | **判分方（父进程）** `protocol.judge()` | **执行方（子进程）** harness 的 `except` 分支 |
| 代码位置 | `protocol.py:181` | `protocol.py:116-117` |
| 触发条件 | 候选**跑起来了**、返回了值，但 `值 != expected` | 候选代码**根本没跑起来**：`exec` 阶段抛了异常 |
| 粒度 | 每条用例一个 | 整次执行最多一个 |
| 对 `completed` 的影响 | 无 | **直接 `completed=False`** |
| 对用例 verdict 的影响 | 只影响自己那条 | 所有用例变 `missing` |
| 分数（strict） | 0.1 | 0.1 |
| 日志能定位到 | `assert-2: wrong_answer` | 只有 `solution_error: SystemExit`，不知道哪条 |

### 8.2 生产位置图

```text
子进程（执行方）
  ├─ emit start
  ├─ try:  exec(compile(候选))          ← 这里抛异常
  │  except BaseException as e:
  │       emit {"event":"solution_error", "error": type(e).__name__}   ← 只报“挂了”，不报哪条
  │  else:
  │       for each case:
  │           try:  out = eval(call)
  │           except: emit {"case": i, "status":"error", ...}          ← 这是 runtime_error
  │           else:   emit {"case": i, "status":"ok", "repr": repr(out)}
  └─ emit done
                              │
父进程（判分方）              ▼
  收到 repr → literal_eval → 与 expected 比
     相等  → "pass"
     不等  → "wrong_answer"
  events 里有 solution_error → completed=False → 全部 missing
```

**关键：`solution_error` 和 case 记录互斥。** exec 一失败，循环根本不会进，子进程只输出 `start` + `solution_error`，一条 `case` 都没有。

 "cases": [{"verdict":"missing"},{"verdict":"missing"},{"verdict":"missing"}]}
```

同理：`import` 不存在的库 → `ImportError`；测试前 `sys.exit(0)` → `SystemExit`；模块级引用未定义名 → `NameError`。只要发生在 exec 里，都是 `solution_error`。

**跑起来了但某一条调用抛异常 → `runtime_error`（第三种，别混）**

```python
class Solution:
    def maxSubArray(self, nums):
        if len(nums) == 1: raise ValueError("boom")
        return 6
```

```json
{"passed": false, "completed": true,
 "cases": [{"verdict":"pass"},{"verdict":"runtime_error:ValueError"},{"verdict":"wrong_answer"}]}
```

### 8.4 三层完整区分

| 层 | 事件/结论 | 含义 |
|---|---|---|
| 程序级 | `solution_error` | 候选代码没跑起来 |
| 用例级 | `runtime_error` | 这一条调用抛异常 |
| 用例级 | `wrong_answer` | 这一条跑出值了，但不对 |
| 用例级 | `unparseable_output` | 跑出值了，但 repr 解析不回来 |
| 用例级 | `missing` | 该报的没报（进程中途死了/提前退出） |

### 8.5 为什么要分成两个

因为**分数一样，归因不一样**：

```python
# coder1_plus/__init__.py:152
return (answer_reward + fmt if passed else fmt), info
```

strict 格式下"答错""没跑起来""调用抛异常"全是 **0.1**——分值只由"正确性 0/1 + 格式 ±0.1"决定，**不看失败原因**。

但归因要靠原因：

- `wrong_answer` → 模型**会做但做错了**（能力问题，正是 RL 要学的信号）
- `solution_error: SyntaxError` → 模型**输出结构崩了**（格式/生成问题）
- `solution_error: SystemExit` → **作弊尝试**（要拦，要记账）
- `runtime_error: IndexError` → 边界没处理（也是能力问题，但类别不同）
- `missing` + 无 `done` → **提前退出**（对抗行为）

**设计结论：分数是标量，原因是结构化信息。** 逐条 verdict 和 `solution_error` 不进 reward，只进日志与归因（`prime_plus` 走 `compute_score_detailed` 就是为这个）。

## 十、奖励管理器：分数 → 张量 → advantage

### 10.1 分数 → 张量（`prime_plus.py:54, 86`）

```python
reward_tensor = torch.zeros_like(data.batch['responses'], dtype=torch.float32)   # :54
for i in range(len(data)):
    reward_tensor[i, valid_response_length[i].item() - 1] = scores[i]            # :86
```

**每条 rollout 只有一个 token 拿到分数**——最后一个有效响应 token，其余全 0（原版 `prime.py:144` 同做法）。

判题故障走 `infra_policy`（`:78-83`）：先重试 2 次，仍失败则 `mask_sample`——故障样本分数设成**组内有效均值**，GRPO 标准化后 advantage 恰为 0；全组故障才整组作废。

### 10.2 分数 → 标量 → advantage（`core_algos.py:111-154`）

```python
scores = token_level_rewards.sum(dim=-1)      # :131 只有一个 token 非零 → 求和=恢复标量
id2score[index[i]].append(scores[i])          # :140 按 uid 分组（同题 16 条）
id2std[idx] = torch.std(...)                  # :147 样本标准差
scores = scores.unsqueeze(-1).tile([1, response_length]) * eos_mask   # :152 广播回整条回答
```

于是：同题 16 条里，1.1 的那条 advantage 为正、0.1 的为负；**全组同分（比如都 0.1）→ std=0 → advantage 全 0，这组不产生梯度**。这就是"错答也能有正 reward，但只有相对排序进入梯度"的完整落地。

## 十一、Verifier / 判分方 / 执行方 / 奖励管理器

这三个词是**三层不同粒度**，不是同义词。

### 11.1 分层图

```text
训练循环 ray_trainer.fit()
│   产出 responses（token）+ reward_model.ground_truth（GT 字符串）
│
└─ ③ 奖励管理器  prime.py / prime_plus.py
   │   职责：批量解码、并发调用、重试、故障策略、把标量写进 reward_tensor
   │   不判断对错
   │
   └─ ② Verifier（整体）  coder1/ 或 coder1_plus/
      │   职责：从 (候选文本, GT) 得到分数 + 结构化结论
      │
      ├─ 抽取：格式门 + 代码块
      ├─ 协议层：把 GT 拆成 call/expected
      │
      ├─ ① 判分方（judge，父进程角色）
      │    持有 expected、收事件、比较、下 verdict
      │
      └─ ① 执行方（harness，子进程角色）
           只拿 call、跑候选、报输出
           └─ 沙箱 sandbox.py（隔离后端）
```

读法：**③ 调 ②，② 内部再分成 ① 的两半。**

### 11.2 职责表

| 概念 | 是什么 | 输入 | 输出 | 代码位置 | **不负责** |
|---|---|---|---|---|---|
| **Verifier** | 整套判分系统 | 候选文本 + GT + extra_info | 分数（+ 结构化信息） | `verl/utils/reward_score/coder1_plus/`（`coder1/` 是原版） | 不管批量、不管故障回填 |
| **判分方**（judge） | Verifier 内部**父进程**那一侧 | 子进程 stdout + cases + nonce | 逐条 verdict + `completed` | `protocol.py:151-187` | 不执行候选代码、不碰 token |
| **执行方**（harness） | Verifier 内部**子进程**那一侧 | prelude + 候选 + call | 带 nonce 的事件流 | `protocol.py:78-140` | **拿不到 expected** |
| **奖励管理器** | Verifier 的上层调度 | `DataProto`（responses、GT、uid、extra_info） | `reward_tensor`（bs × resp_len） | `prime.py` / `prime_plus.py` | **不判断对错**，只搬运与兜底 |

**常见混淆点：** "判分方"在原版里不存在。原版 `coder1` 是"候选 + functional 拼成一个程序、看退出码"——判分和执行在同一进程，没有分离的两侧。判分方/执行方这对角色是补强项 4（2026-10-14）才引入的。面试说"判分方"要落在**受保护协议**这个上下文里。

### 11.3 一次样本走查

```text
① 训练循环给出：response token + GT 字符串 + extra_info
        │
② 奖励管理器（prime_plus.py:57-60）
   tokenizer.batch_decode(responses) → 一整段文本
        │
③ 奖励管理器 → Verifier（coder1_plus.compute_score_detailed, :70）
        │   ├─ 抽取：validate_response_structure + extract_code_from_string   (:84-85)
        │   ├─ 格式门：没代码 → -0.1，直接返回                                  (:95-97)
        │   ├─ 判分方拆 GT：parse_cases → (entry, cases)                        (:101)
        │   ├─ 拼程序：build_harness(prelude, code, entry, cases, nonce)        (:111)
        │   ├─ 执行方：子进程跑，吐事件                                          (sandbox)
        │   ├─ 判分方：judge(stdout, cases, nonce) → verdict                    (:117)
        │   └─ 打分：1.0 + 0.1 / 0 + 0.1 / …                                    (:152)
        │
④ 奖励管理器（prime_plus.py:78, 86）
   收集标量 → resolve_group_failures（只处理 infra_error）

### 11.4 出问题时谁负责

| 现象 | 谁决定的 | 落到哪 |
|---|---|---|
| 候选答错 | **Verifier**（judge 的 `wrong_answer`） | 分数 0.1 |
| 候选代码没跑起来 | **Verifier**（`solution_error`） | 分数 0.1 |
| 大输入上答错 | **Verifier**（perf 轮 `mismatch`） | 分数 0.1 |
| 大输入超时 | **Verifier**（perf 轮 `slow`） | 分数 0.9 |
| 沙箱起不来 | **Verifier 抛出 `InfraError`** | 管理器接住 |
| 判分卡死 600s | **奖励管理器**（`FuturesTimeout`） | `infra_error` |
| 故障怎么处理 | **奖励管理器**（`infra_policy`） | 单条掩码 / 整组作废 |
| 分数写在哪 | **奖励管理器** | 最后一个有效 token |

**口诀：Verifier 负责"这答案值几分"，奖励管理器负责"这分怎么落地、判不了怎么办"。**

### 11.5 BC 归属：坏在哪一层

登记表的分层与本文的三层概念**不是一一对应**：Verifier 内部还被拆成"判分器"与"沙箱"两个 BC 章节，因为它们的修法完全不同（改代码 vs 换后端）。

| BC 章节 | 对应的概念 | 典型坏法 | 修法性质 | BC 编号 |
|---|---|---|---|---|
| 数据 / GT 层 | **Verifier 的输入**（GT 字符串、prompt、测试本身） | 正确解恒 0.1、错解蒙到 1.1、同题抖动 | 改数据、重建 GT | BC-01/02/03/04/05/06/19/20/25 |
| 判分器层 | **Verifier 内部**：抽取、协议、打分档位 | 提前退出骗满分、格式边际倒挂、两套提取规则、命名空间污染 | 改代码 | BC-07/08/09/22/23/24 |
| 奖励管理器层 | **③ 管理器** | 故障回填 0.0 污染组内均值、解码错整批 −1.1 | 改管理器 | BC-10/11 |
| 沙箱层 | **① 执行方的运行环境** | 三层时限混淆、docker 不禁网 | 换后端 / 调限额 / 加隔离 | BC-12/13 |
| 策略配置层 | 训练配置（不误判 reward，影响曲线解读） | grad_norm 偏小、clip 不触发、首步 lr=0 | 改配置或改解读 | BC-14~18、BC-21 |

**读法：** "Verifier 坏了"在 BC 库里要再问一句——是**判分逻辑**坏了（判分器层），还是**执行环境**坏了（沙箱层）。两者的症状可能一样（都是"这批样本分数不对"），但归因路径和修法完全不同。

```text
Verifier 坏了
  ├─ 判分逻辑坏（判分器层）：退出码当结论、格式边际倒挂、命名空间污染
  │     → 改 protocol.py / coder1_plus/__init__.py
  └─ 执行环境坏（沙箱层）：firejail 起不来、docker 不断网、三层时限混淆
        → 换后端 / 调限额 / 加隔离
```

### 11.6 `InfraError` 与"单条掩码 / 整组作废"的关系

```text
触发（可能在三处）
  A. 沙箱层：后端不可用 / 启动失败 → ExecResult("infra_error")
     sandbox.py:132-134（无后端拒绝执行）、:156-157（OSError）、:173-176（sandbox-exec/firejail 启动错）
  B. Verifier 内部：性能轮返回 infra → 同样记 infra_error
     coder1_plus/__init__.py:143-144
  C. 奖励管理器自己：future.result(timeout=600) 超时
     prime_plus.py:74-76
        ↓
信号
  Verifier 路径：compute_score_detailed 返回 (None, {"status": "infra_error"})
                 → _compute_score 抛 InfraError            [:158-159]
  管理器路径：score_with_retries 捕获异常/None → ("infra_error")   infra_policy.py:22-33
        ↓
分类（只在管理器）
  status == "infra_error"
        ↓
策略（只在管理器）resolve_group_failures          infra_policy.py:36-74
  mask_sample（默认）  故障样本 = 组内有效均值 → advantage 恰 0
  neutralize_group     整组作废（全组同分 → advantage 全 0）
  legacy_zero          故障样本 = 0.0（原版行为，即 BC-10 的 bug）
        ↓
落地
  reward_tensor[i, 最后一个有效 token] = 分数       prime_plus.py:86
```

**四条必须分清的事实：**

1. **`InfraError` 是异常，"掩码/作废"是策略。** 前者回答"判分设施还好吗"，后者回答"坏了以后这分怎么填"。`InfraError` 本身不决定任何分数。
2. **信号横跨两侧，策略只在一侧。** Verifier 负责把"设施坏了"与"候选失败"区分开（`compute_score_detailed` 返回结构化 status，而不是 0 分）；管理器负责消费这个信号。
3. **管理器也会自己产生 `infra_error`**：判分函数卡住超过 600 秒（`FuturesTimeout`），此时 Verifier 根本没返回，是管理器兜底。
4. **原版没有 `InfraError` 概念**：`prime.py` 的 `single_compute_score` 超时或异常一律回填 0.0——这就是 BC-10 的成因，也是"补强项 6"要解决的问题。

**一个容易踩的坑（坑一）：** `score_with_retries` 把**任何**异常都当作 `infra_error`（`infra_policy.py:28` 的裸 `except Exception`）。这包括 Verifier 自身的代码 bug（比如 `KeyError`、`AttributeError`）。"异常 = 设施故障"是一个**假设**，排查时要看异常类型：沙箱类（启动失败、超时）才算设施故障，`KeyError` 属于判分器 bug，应该修而不是掩码。

**坑二：原版把"超时"归成候选失败，补强版才分开。**

| 后端 / 轮次 | 超时的结论 |
|---|---|
| 原版 firejail | 退出码非 0 → `(False, output)` → **0.1（候选失败）** |
| 补强版 correctness 轮 | `ExecResult.status="timeout"` → judge 看到缺结果 → **0.1（失败）** |
| 补强版 perf 轮 | `status="slow"` → **0.9（性能瑕疵）** |
| 补强版 infra | 启动失败 / 无后端 → **`InfraError`** |

**"超时"和"设施故障"是两件事**：超时是候选自己跑太久（候选负责），设施故障是环境没起来（环境负责）。原版把两者混在"退出码非 0"里，是 BC-12 要求"超时归因先分层"的原因。

**掩码的代价（面试可提）：** 故障样本的 token 仍占 loss 分母；组内标准差的分母含故障样本，有效样本的 advantage 被均匀放大 `sqrt((n-1)/(n-2))`（方向与排序不变）。**整组全故障时退回整组作废**——没有有效样本可参照。

### 11.7 按 D24 坐标定位（发现阶段 S × 出错位置 L）

| 现象 | 发现阶段 S | 出错位置 L | 责任人 |
|---|---|---|---|
| 正确解恒 0.1（`AttributeError`） | S3（Verifier 对抗自测） | **L5** Verifier 协议/赋分 | Verifier（判分器层） |
| 某步大量 0.0、错误回答 advantage 变正 | S4（GPU 冒烟） | **L6** 管理器组内回填 | 奖励管理器（BC-10） |
| 沙箱起不来、整批 infra | S4 | **L7** 沙箱/训练配置 | 沙箱层（触发）+ 管理器（放大） |
| 故障被掩码后仍污染组内 | S3 离线算例 | **L6** | 管理器策略 |

**注意最后两行的关系：根因在 L7，伤害放大在 L6。** 这就是"沙箱层"和"管理器层"要分开登记的原因——同一个事故，修沙箱解决"为什么坏"，修管理器解决"坏了以后别乱给分"。S 与 L 的完整定义见 [bad_case 调查方法论 第二节](bad_case调查方法论.md) 与 [设计定案表 D24](设计定案表.md)。

### 11.8 口述版（可直接背）

> 「Verifier 是整个判分系统，输入候选代码和 GT，输出分数。它内部再分两侧：**判分方**在父进程，手里有标准答案，负责比较；**执行方**在沙箱子进程里，只拿到调用表达式和候选代码，负责跑和报告。标准答案永远不进执行方，所以候选既作弊不了、也提前退不掉。
> 再往上一层是**奖励管理器**，它不判断对错，只负责批量解码、并发调判分、把每条样本的标量写到最后一个 token 上；它还负责判分器自己出故障时怎么办——重试、单条掩码、整组作废，都在这一层。」

### 11.9 一条历史线

```text
原版 coder1：判分方 = 执行方（同进程、看退出码）→ BC-01/BC-24 都源于此
补强项 4   ：拆成判分方 / 执行方            → 作弊与提前退出可拦
补强项 6   ：再加一层奖励管理器故障策略      → 判题故障不再污染组内均值
```

"Verifier 内部拆两侧"和"Verifier 外面加一层管理器"是两次不同性质的修复：前者解决"判分不可信"，后者解决"判分不可用时别乱给分"。

## 十三、面试追问清单

1. **为什么分数只放在最后一个 token？** —— outcome reward 是整条回答一个标量，放在最后一个有效 token 是最省事的实现；后面按组求和恢复标量，advantage 再广播回全部 response token。
2. **为什么错答是 0.1 而不是 0？** —— 0.1 是"格式合格"的加分；0 会让"格式合格但错"和"格式不合格"（−0.1）区分不开。字典序 1.1 > 0.9 > 0.1 > −0.1。
3. **原版和补强版的判定程序差在哪？** —— 原版 `solution + "\n" + functional` 一个程序跑、只看退出码；补强版拆 call/expected、期望答案不进子进程、逐条报告 + nonce。
4. **121 道树/链表题为什么会恒 0.1？** —— 原版 GT 只有 `functional`，`tree_node` 等定义在数据集原始 `prompt` 里，没拼进程序 → `NameError`；补强版 GT 多存 `prelude`。
5. **作弊解为什么拿不到分？** —— `except BaseException` 捕获 `SystemExit`，`completed=False`；伪造事件也缺 expected 和 nonce。
6. **`wrong_answer` 和 `solution_error` 有什么区别？** —— 前者是父进程对某条用例的判分结论，后者是子进程报告的程序级执行事件；分数可能相同，归因完全不同。
7. **Verifier 和奖励管理器怎么分工？** —— Verifier 决定"值几分"，管理器决定"分怎么落地、判不了怎么办"。

## 十五、续讨论 2026-11-18：可见性分层与 exec 时序

### 15.1 Q1：模型可见的注释版 vs GT prelude

**结论：子集关系；相交部分去掉 `# ` 后逐字相等；prelude 比模型可见文本多三块。**

实测（`add-two-numbers`，同一冻结行）：

```text
模型可见 meta.query 的注释块（去掉 "# " 后）
  class ListNode:
      def __init__(self, val=0, next=None):
          self.val = val
          self.next = next
  ↔ prelude 里的 class ListNode：归一化后逐字相等 = True

但两份范围不同：
  meta.query：只有 1 个注释类定义
  prelude   ：imports 头 + class ListNode
              + def list_node(values)      ← 模型可见文本里没有
              + def is_same_list(p1, p2)   ← 模型可见文本里没有
```

| 说法 | 判定 |
|---|---|
| 注释版 `ListNode` 与 prelude 的 `ListNode` 是同一份定义 | ✅ 对（去注释后逐字相等） |
| 整个注释版与整个 prelude 是同一份文本 | ❌ 不对——prelude 多 imports + 两个测试辅助函数 |
| GT 自带可执行版是「怕模型抄错」 | ⚠️ 一半：测试侧本来就要用这些函数造输入/比输出；「不抄错」是附带收益，不是唯一目的 |
| 模型看不到 `list_node`/`is_same_list` 是遗漏 | ❌ 不是——它们是判分侧工具，不是解题接口；给模型看反而增加改写/污染风险（BC-24 入口） |

### 15.2 Q2：`exec` 是什么，期间与之后有什么区别

**准确说法：`exec(code, globals())` 把字符串当 Python 程序从上到下立即执行。执行到 `def` 时只创建函数、不跑函数体；执行到调用表达式时才真正运行。** 所以不是「exec 只加载、什么都不跑」——候选如果在模块级写了 `Solution().solve()` 或 `ListNode(9)`，这些调用在 exec 期间就会执行（构造函数也会跑）。

**先纠正一个字面错误**：harness 不是运行时 `compile(repr(源码))`。父进程在生成 harness 时用 `{solution!r}` 把源码 `repr` 成字符串字面量嵌进模板；子进程拿到的程序里已经是源码本身，`exec(compile(源码, "<solution>", "exec"), globals())` 执行的是候选代码，不是「字符串字面量表达式」。

```text
子进程 program 自上而下
│
├─ ① prelude 执行
│     globals: ListNode=环境版, list_node=环境版, is_same_list=环境版, imports...
├─ ② 定义 reporter（带 nonce）
├─ ③ emit {"event":"start"}
├─ ④ 快照 6 个保留名
│     __coder1_reserved = {ListNode: 环境版, list_node: 环境版, ...}
│
├─ ⑤ exec(候选源码, globals())                 ← 【exec 期间：立即执行】
│     ├─ class ListNode / class Solution：创建类，方法体不跑
│     ├─ def helper：创建函数，函数体不跑
│     ├─ 模块级赋值：立即执行
│     ├─ 模块级调用（如 ListNode(9)、Solution().solve()）：立即执行
│     └─ 模型定义可覆盖 globals["ListNode"] 等 6 个名字
│
├─ ⑥ 恢复 6 个保留名                          ← 【exec 之后：环境摆回】
│     globals["ListNode"] = 环境版
│     globals["list_node"] = 环境版
│     ...（模型只留下 Solution 和它自己起名的辅助函数）
│
├─ ⑦ 逐条考试                                  ← 【提交给 judge 的输出在这里产生】
│     for i, call in enumerate(cases):
│         candidate = eval(entry, globals())
│                     ↑ 只有 entry 里含 Solution() 才新建实例
│         out = eval(call, globals(), {"candidate": candidate})
│                     ↑ 方法体此时执行；全局名查找得到环境版
│         emit {"case": i, "status": "ok", "repr": repr(out)}
│
└─ ⑧ emit {"event":"done"}
```

| | exec 期间（⑤） | exec 之后（⑥⑦） |
|---|---|---|
| 在做什么 | 立即执行候选的模块级代码 | 恢复环境 + 逐条调用 |
| class/def | 创建类/函数，方法体/函数体不跑 | 可被调用 |
| 模块级调用 | **会跑**（构造、`Solution().solve()` 等） | — |
| `ListNode` 指向谁 | 模型版（若模型定义了） | **环境版** |
| 提交给 judge 的输出 | 通常没有（除非模块级自己打印） | **`repr(out)` + status 在这里产生** |
| 谁消费 | 子进程解释器 | harness 的 `eval`；父进程 judge 消费事件 |

**`out` 是什么取决于 `call` 的内容**：

| `call` 形态 | `out` |
|---|---|
| `candidate(...)` | 候选返回值（如链表对象） |
| `is_same_list(candidate(...), list_node(...))` | 子进程比较得到的布尔值 |
| 完整 `assert ...` | 不能直接 `eval`，会 `SyntaxError` |

**`repr(out)` 不是可靠的数据证明**：候选可以自定义 `__repr__` 返回任意字符串（如 `"7"`），父进程 `ast.literal_eval` 后看起来像正确值。父进程必须做结构/类型校验，不能只信字符串。

**模拟实测**（最小复现）：

```text
环境有正确 ListNode；模型定义错误 ListNode（self.v）+ Solution.build() 返回 ListNode(7)
+ 模块级 module_level_node = ListNode(9)

exec 后：globals["ListNode"] 是模型类
恢复后：globals["ListNode"] 是环境类
调用 Solution().build()：返回节点是【环境类】，有 .val、没有 .v
exec 期间创建的 module_level_node：是【模型类】，有 .v
```

**为什么不在 exec 期间就用环境版**：`exec` 一次执行整个模块，模型的 `class ListNode` 一定会写进 `globals`，无法中途拦截。现版能保证的是「测试侧」用环境版；exec 期间创建的模型类对象无法追溯修改。彻底方案是隔离命名空间（候选用自己的 dict），但**这也不是安全沙箱**——见 §15.4。

### 15.3 `list_node` / `is_same_list` 为什么存在

```text
测试断言原文：
assert is_same_list(
    candidate(l1 = list_node([2,4,3]), l2 = list_node([5,6,4])),
    list_node([7,0,8])
)
```

| 函数 | 作用 | 为什么需要 |
|---|---|---|
| `list_node([2,4,3])` | Python 列表 → `ListNode` 链：2→4→3 | 测试数据是字面量列表，候选要的是链表；没有它 `l1` 传不进去 |
| `is_same_list(a,b)` | 递归比较两条链表的 `val`/`next` | 候选返回 `ListNode` 对象；`==` 比对象身份，不是内容 |

树题同理：`tree_node([...])` 层序建树，`is_same_tree(a,b)` 递归比左右子树。它们是**测试侧基础设施**，不是模型要实现的 API。

### 15.4 已确认边界：恢复 6 个名字只修名称冲突，不是安全边界（外部审查 2026-11-18）

> 以下结论来自外部 AI 在 **CPython 3.14.6** 上的最小复现（内存实验，未改仓库文件）；标【实测】的是它跑出来的，标【推断】的是风险判断。它审计的是设计，不等于本项目 verifier 的端到端测试。

**会绕过「恢复 6 个名字」的路径【实测】：**

| 路径 | 为什么绕过 | 测试时实际用哪个 |
|---|---|---|
| 模块级已创建的实例 | 对象已生成，改名字不改对象 | 模型类实例 |
| 不同名字保存的类引用（`MyNode = ListNode`） | `MyNode` 不在恢复名单 | 模型类 |
| 函数默认参数（`def f(x=ListNode())`） | 默认表达式在定义时求值并保存 | 模型类实例 |
| 类属性（`class Solution: Node = ListNode`） | 类体执行时保存引用 | 模型类 |
| 真正的闭包捕获（`N = ListNode; lambda: N(7)`） | 闭包 cell 保存绑定，不查全局 | 模型类 |
| 方法调用期间新定义的局部类 | 局部名字完全不受全局恢复影响 | 局部模型类 |
| 导入模块/容器里保存的类引用 | 引用不在恢复名单 | 模型类 |

**更严重：候选可以让「恢复后的环境本身」不可信【实测】：**

```text
① 改快照：__coder1_reserved["ListNode"] = 模型类
   → 恢复时反而恢复成模型类

② 直接改环境类：ListNode.__init__ = lambda self, val=0: setattr(self, "v", val)
   → 快照与 globals 指向同一个类对象；恢复引用后行为已被改坏

③ 改环境函数：is_same_list.__code__ = (lambda a, b: True).__code__
   → 恢复函数引用没用，原函数对象已被修改

④ 劫持 repr：repr = lambda x: "7"
   → harness 的 repr(out) 被劫持

⑤ 劫持 len：len = lambda x: 0
   → 未保护的 helper 内部判断被改变

⑥ 恢复后再写 globals()["ListNode"] = ...
   → 后续测试代码再次被污染
```

**nonce 的边界【实测 + 推断】：**

```text
候选可以包装 reporter：
  saved_emit = emit
  def emit(event):
      if event.get("status") == "ok":
          event = dict(event, repr="7")
      saved_emit(event)        # 原 reporter 替它加正确 nonce
→ 攻击者不必知道 nonce 的值，只要调用原 reporter，就能发出带正确 nonce 的假内容。
```

- ✅ nonce 能区分「当前运行」与其他运行，过滤不匹配输出；
- ❌ 不能认证已被候选控制的 reporter，不能证明某条 case 真的执行过、结果来自哪条路径；
- 把 nonce 放在同一解释器的 globals/闭包/默认参数里，不能对候选保密。

**`repr(out)` 不是可靠的数据证明【实测】：**

```python
class Fake:
    def __repr__(self): return "7"
repr(Fake()) == repr(7)   # True，但对象不是整数 7
```

父进程必须做结构/类型校验（`ast.literal_eval` 后检查类型、链表/树结构），不能只信字符串。

**另两个实现细节【实测】：**

- 恢复代码 `if value is not None: globals()[name] = value`：原来不存在或原值为 `None` 的名字会**保留候选绑定**。应改用 sentinel 区分「原来不存在（删掉）」与「原来是 None（恢复 None）」。
- harness 的 `try: exec(...) except BaseException: ... else: 测试`：**`else` 块内的异常不会被前面的 `except` 捕获**，需要单独处理入口求值/逐条调用/序列化的异常。

**推荐方案【推断】：**

| 方案 | 收益 | 代价/边界 |
|---|---|---|
| 保留共享 globals + 恢复 6 个名 | 改动小，修常见同名覆盖 | 修不了捕获引用、对象状态、运行期污染；还改变候选语义 |
| 独立候选 dict，只取入口 | 测试辅助函数与候选赋值不再直接冲突；候选 helper/imports 可保留 | 同一解释器仍共享模块/对象/调用帧，**不是安全沙箱** |
| **独立 dict + 受限执行进程 + 父进程比较** | 同时改善名称冲突、宿主保护、判分独立性 | 需要明确序列化、I/O 协议、状态生命周期、资源限制 |

**结论**：**恢复 6 个名字只能修复部分名称冲突，不能保证测试环境干净，也不能保证测试期间只使用环境类。** 若只修普通兼容性，独立候选 dict 是最小值得做的结构调整；若要抵抗主动篡改，必须把 expected/比较/裁决留在父进程，并把子进程回传结果当不可信数据。

> 更精确的阶段划分（exec 期间 / 恢复 / 测试期）、旧对象的直接与间接影响、三处措辞纠正（「原子」「只有直接返回旧对象才失败」「硬隔离」）以及 `__coder1_list` 的 100000 截断边界，见 [交接_20261117_判定链路.md](交接_20261117_判定链路.md) 的 §6.1「Q2 收口（以旗舰 AI 复核结论为准）」。
