# bad case 调查方法论：双向铁律与口述纪律

**用途：** 回答两类面试问题的方法基准：「出了问题你怎么查」（下游→上游归因）与「你怎么保证不出问题」（上游→下游推演）。配套的 [bad_case登记表](bad_case登记表.md) 记案例，本篇记方法；定案母版是[设计定案表 D20](设计定案表.md)。

## 一、双向能力总览

| 方向 | 起点 | 铁律 | 回答的面试问题 |
|---|---|---|---|
| **下游→上游**（归因） | reward 异常 | 先拿参考解复现——同分即环境实锤（模型无关） | 出了问题你怎么查 |
| **上游→下游**（推演） | 翻数据/读码发现缺陷 | **列消费者**（见下） | 你怎么保证不出问题 |

BC 库 25 条逐条判定的 20/0 前移统计，就是反向推演跑了一遍全库存量的结果：**发现得早是卖点，不是弱点。**

## 二、上游→下游推演：步骤 0 + 四步

```text
步骤 0  固定原始源材料（2026-11-13 补，硬约束）
        ├─ 源码：原始上游 commit（如 ganler/code-r1 基线 443f8da）
        ├─ 数据：原始数据快照（LeetCodeDataset 固定 commit）+ 原始题面/HTML 快照
        ├─ 禁止：拿已落盘的 coder1_plus / 修复后版本做「发现」——修复会把缺陷修没，
        │        新增字段（prelude/beyond_contract/mask_sample）会误导路径
        └─ 记录：source_commit + 文件:函数(行号) + 数据 sha256；修复后版本只用于「验证修复」

上游缺陷
  ① 定出口   问「这个坏值躺在哪个字段里？」——先钉住缺陷本体与证据
  ② 列消费者 机械动作：不想症状，只想「谁读这个字段」——管线里逐个找消费者
              消费者列全 ⇒ 症状清单自动涌现，不需要灵感
  ③ 推坏产物 每个消费者「拿到坏值会产出什么错的下游产物」——沿真实代码路径
              （文件:函数），禁止凭空想象；读不到的环节标「推断」
  ④ 钉出口   每个坏产物落到一个可观测出口，并分级（见下）
```

**步骤 0 是硬约束，理由是「答案污染」。** 修复后的代码里缺陷已经不存在：上标 105 在 `parse_size_bound` 里被幂识别修好、121 题在 `prelude` 里被补齐、故障在 `mask_sample` 里被掩掉。用这份代码反推，推演者会「看不见」缺陷本身，还会把修复新增的路径误当成原始设计。**原始版本用于发现，修复版本用于验证——两个方向不能混。** 原始源码不进仓（体积/版权），只记录 commit 与片段位置；需要时从 GitHub 拉一份独立副本（如 `D:\RL及harness\Code-R1-original`），整个推演只读它。

**②是核心。** 附带价值：缺陷可能在原版管线里**休眠**、被修另一个缺陷**激活**（上标 105 原本无人读，「补约束」消费它之后才引爆）——消费者清单是看出这种耦合的唯一位置。

**推演产物格式（每条 case 七字段，缺一不可）：**

| 字段 | 内容 |
|---|---|
| `id` | 临时编号（登记前） |
| `source_commit` | 原始上游 commit + 数据快照 sha256（步骤 0） |
| 上游缺陷 | 文件:函数(行号) + 坏值证据（数据行/HTML 快照） |
| 消费者清单 | 在原始代码里逐个列出（不是修复后代码） |
| 坏产物 | 每个消费者一条，沿真实代码路径；读不到标「推断」 |
| 出口 / 分级 | 四类出口 × 三级（静态可查/离线可证/需训练才现） |
| **面试版** | **从下到上重新归因**：症状（真实下游观测）→ 排除环境 → 上追 → 根因 → 修法 → 验证数字 →（第二层）反事实后果；套 §四模板 |
| 修复验证 | 修复后版本的对照实验（**只用于验证，不用于发现**） |

### 发现阶段 × 出错位置（D24，两维必须分开）

**发现阶段 = 信号第一次能被看见的地方（≠ 根因所在）；出错位置 = 根因所在的工件/组件（≠ 症状出现的地方）。**

| 发现阶段 | 含义 | | 出错位置 | 含义 |
|---|---|---|---|---|
| S0 上游取数/解析 | 爬取、六步解析、冻结 | | L1 上游解析 | HTML/JSON → 字段 |
| S1 数据清洗与构造 | 字段对账、去重、约束注入 | | L2 Tests / expected | 覆盖度、输入合法性、期望值 |
| S2 测试扩容与 validate | 边界/随机、validate、oracle 对拍 | | L3 prompt 组装 | 模型可见的输入 |
| S3 Verifier 对抗自测 | 参考解全量跑、作弊解打自己（离线 CPU） | | L4 GT 组装 | prelude + functional |
| S4 GPU 冒烟 | 短跑 + escaped/误杀两率 | | L5 Verifier 协议/赋分 | 提取、拼装、比较、档位 |
| S5 正式训练/评测 | 曲线、rollout、held-out | | L6 奖励管理器/组内 | 故障回填、掩码、标准化 |
| | | | L7 沙箱/训练配置 | 后端、超时、超参 |

归因先定 L（修哪里），叙事再定 S（怎么讲发现）。三个必讲 case 的坐标与唯一表述见 D24 与 [01 的 `end-to-end`](01_数据理解与GT构建.md#end-to-end)。

## 三、可观测出口四类 × 分级三级

| 出口 | 例子 |
|---|---|
| prompt 文本 | 翻数据行看到字面 `105` |
| 判分日志 / reward | 参考解恒 0.1；满分但审计完成数 0 |
| 组内区分度 | 同题 16 条全同分 → advantage 全 0 |
| 评测分 / held-out 差值 | reward 涨而 held-out 不涨 |

| 分级 | 含义 | 面试答法 |
|---|---|---|
| **静态可查** | grep/diff 数据行就能看见 | 「翻数据行发现」 |
| **离线可证** | CPU 探针 / 固定候选对照 / 真实判分器复演 | 「离线实测」 |
| **需训练才现** | 沿代码路径推演、未实跑 | 明说「推演」，不当实测讲 |

## 四、口述纪律

**发现顺序 ≠ 叙事顺序**：发现可以上游先（读码/预检）；讲述**永远下游先**——症状 → 排除环境 → 上追 → 根因 → 修法 → 验证数字。

**开口必须真实**——「下游开口 ≠ 训练事故开口」：

| 开口 | 例子 | 真实性 |
|---|---|---|
| ❌ 虚构训练事故 | 「训练时曲线突然掉了」 | 没跑过 GPU，一追问就穿 |
| ✅ 真实下游观测 | 「全池参考解判分时 121 题恒 0.1」「翻数据行看到 909 题的规模上界是丢上标形态（字面 104/105/106/109）」 | 预检/审计/对照的实测数字，追不穿 |

**反事实后果收第二层**：「不修会怎样」永远在被追问时才展开，不放进开口句。

**统一模板**：

> 「我在做 X（预检/审计/对照实跑）时看到 Y（真实观测）→ 先排除环境（参考解复现）→ 往上追到 Z 层 → 根因 → 修法 → 验证数字 → 如果不修会怎样（第二层）。」

## 五、完整演练：上标 105

**①定出口**：上游 HTML 转文本丢 `<sup>`，`10⁵` 冻结成字面 `105`——全库 1890 题里 909 题的规模上界含这类丢上标形态（字面 `<= 104/105/106/109`，即可复现口径；统计命令见文末维护记录）。

**②列消费者**：prompt 组装（`--append_constraints`）、perf 标定（`parse_size_bound`）、边界生成器（D17 设计中）。**耦合洞察**：原版管线无人读约束——缺陷休眠，修「缺约束」（D1）时才被激活。

**③④推坏产物并钉出口**：

| 消费者 | 拿到 105 | 坏产物 | 出口 / 分级 |
|---|---|---|---|
| prompt 组装 | 写进「1 ≤ len ≤ 105」 | 模型合法写 O(n²)（约束错三个数量级，消歧信息反着用） | prompt 文本，静态可查 |
| perf 标定 | 低于放大下限 1000 | 909 题解析关口整题跳过 → 快慢同分，reward 看不见快慢 | 标定跳过计数，离线可证 |

**口述（模板套用）**：

> 「翻数据行的时候发现 909 题的规模上界是丢上标形态——`<= 10⁵` 冻结成字面 105、`<= 10⁴` 冻结成 104，数量级说丢就丢。往上追两步：`question_title` 原文就是 105；再用探针对官网 HTML 做同样的朴素去标签，产出与冻结题面逐字一致——实锤上游转换丢 `<sup>`。有意思的是这个缺陷在原版管线里是休眠的，原版不消费约束；我们修『prompt 缺约束』时把它激活了。不拦会炸两处：prompt 告诉模型上限 105，模型合法写暴力；perf 标定读出 105 低于下限，这批题整题跳过、快慢同分。修法是消费端幂识别，两处同规则把 105 认回 10⁵，实测解析回 100000、回归 18/18；数据原文不改——第三方加哈希锁，可复现性靠冻结。」

**回流物第三件（2026-11-13 补；同日规格修正）：扩容不达标告警**——取数点在幂识别**之前**：扩容管线保留一步原生解析（不幂识别）仅供对账，`bound_raw < 1000 且难度 ≥ medium` 计数告警；生成与判分仍用幂识别值（D13 补参 / D21）。原因：幂识别把坏值在解析边界统一修好、下游全部看不见（掩盖效应）——旧写法「目标 1000 被 validate 拒到 ≤105」取的是修复后的值，在幂识别管线里永不触发（死信号）；检测必须坐在解析器之前。加上消费端幂识别回归（`parse_size_bound` 单测 + `verify_perf_round.py` 18/18）与 prompt 约束对账，该缺陷的发现从「靠人翻数据」升级为「管线自检」。
