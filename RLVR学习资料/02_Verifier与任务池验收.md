# 阶段二：Verifier 怎样给分，这个分能不能信

**资料导航：** [资料首页](README.md) · [工业主框架](RLVR工业流程.md) · [00 全程走读](00_一条记录从原始Task到训练.md) · [01 数据与 GT](01_数据理解与GT构建.md) · **02 Verifier 与任务池（当前）** · [03 Rollout 与 GRPO](03_Rollout与GRPO机制.md) · [04 训练与评测](04_真实训练与独立评测.md)

**先记机制：** Tests 说明要验什么，执行后端负责把程序跑起来，判分器把看到的结果换成 reward。三件事各要各的证据：答案对不对、程序是不是真的跑完了测试、比较规则合不合理。退出码 0 和 reward 1.1 都不能单独证明「通过」。

## 总览：02 在流程里做什么、长什么样

02 对应 [00 全程走读](00_一条记录从原始Task到训练.md#overview-00)七站里的第 ④ 站。**在全链路里，本篇是第 5–7 段（判分 → 管理器 → 交出 reward）；前四段（取数→取料→把关→封装）在 [01 的全链路顺序图](01_数据理解与GT构建.md#end-to-end)。**它完全离线，只用 CPU，判的是课程固定的 6 个候选程序，不跑模型。它要回答的问题是：一个回答怎样变成 reward，这个 reward 能不能信。

**Verifier 是怎么构建出来的——五句话**（一张图版见[全景主图](#pipeline-2)，贯穿例 wrong_empty）：

1. **原料是数据行，不是代码**：判分器本身不含任何题目知识——题面、断言、期望全在 01 交来的数据行里（`data_source` 是路由键，`GT` 装断言与前缀，`extra_info` 装旁证），换个题只换数据行。
2. **部件一·判分器**：一台通用机器，七步装配——格式门、抽代码、把断言拆成「调用＋期望」、拼 harness、交沙箱、判分方逐条比较、映射档位。期望答案永远不进被测代码的进程。
3. **部件二·执行后端（沙箱）**：把 harness 在隔离环境跑起来（禁网、限额、限时），回报结构化状态——正常、超时、运行错、判题故障分开。
4. **部件三·奖励管理器**：一步 256 条回答并发判分，判题故障先重试、仍失败单条掩码（advantage 恰为 0），分数写到回答的最后一个有效 token。
5. **两个分别验收**：判分可信（逐条比较、期望不泄漏、缺结果算失败）与执行安全（隔离、超时清理）——考场守规矩不证明卷子判得对，判卷机正确也不证明考场安全。

三个角色的输入输出卡：

- 判分器：检查格式、抽出代码、拼上测试、看执行结果，按字典序分档给出 1.1 / 0.9 / 0.7 / 0.1 / −0.1（正确性是主键，格式与超时是次键）。
- 执行后端：把拼好的程序在隔离沙箱里跑起来，回报结构化状态（正常、编译错、运行错、超时、判题故障分开）和输出。
- 奖励管理器：一批回答并发判分，判题故障先重试、仍失败单条掩码（advantage 恰为 0；全故障组才整组作废），分数写到回答的最后一个 token 上。

## 文字版导读：先把全篇顺一遍

第一次读，先把这一节读完，再按链接进细节；复习时只读这一节。

**第一节：先分清三个角色。** 判分这一站有三个角色：

- 判分器：输入是回答文本和 GT，输出是 reward 和一段日志。
- 执行后端：输入是一段拼好的程序，输出是成功与否和 stdout、stderr。
- 奖励管理器：输入是一批 256 个回答，输出是每个回答一个分数，写在最后一个有效 token 上。

执行后端像考场，限制权限、时间和资源；判分器像判卷机。考场守规矩，不证明卷子答完了；判卷机比对正确，也不证明考场安全。两件事要分别验收。详见[三个角色](#prerequisites-2)。

**第二节：判分七步。** 一个回答变成 reward，要走七步：

1. 格式门：去掉首尾空白后以 `<think>` 开头、`</answer>` 结尾 → 格式分 +0.1；不合格只记 −0.1，**不拦**——退回整段照样抽围栏代码执行。真正被挡在门外的是抽不出任何围栏代码块（none，−0.1 不执行）。
2. 抽代码：先取最后一个 `<answer>` 内部（无标签退回整段），再抽全部围栏代码块拼接。
3. 拼程序：prelude + 候选代码；受保护协议把断言拆成「调用 + 期望」，期望不进候选进程。
4. 执行：隔离沙箱（macOS sandbox-exec / Linux firejail）限时 30 秒、内存 4 GB、禁网，状态分类（超时、运行错、判题故障分开）。
5. 判定：受保护协议逐条比较输出；缺结果、缺完成事件都算失败——提前退出骗不到分。
6. 映射 reward：字典序 + 瑕疵并罚，1.1 / 0.9 / 0.7 / 0.1 / −0.1，任何对答严格高于任何错答；带性能标定的题超时降 0.9，大输入答错按错答 0.1。
7. 管理器收尾：判题故障先有限重试，仍失败单条掩码——故障样本分数＝组内有效均值，advantage 恰为 0，其余 rollout 照常给信号（全故障组退回整组作废）；分数写到最后一个有效 token。

要记住的判断：受保护协议里**比较输出发生在判分方**——子进程只交调用结果，期望答案和判定标准都在判分方手里。历史口径把断言拼进候选进程、只看退出码，才有提前退出骗满分（BC-07）。详见[判分七步](#pipeline-2)。

**第三节：reward 档位，每个数字证明了什么。**

- 1.1：对 + 标签合格 +（有性能标定时）限时内通过大输入。不证明断言真的跑完了、测试够。
- 0.9：对但一项瑕疵（无标签，或超时）。逻辑正确，格式或速度有缺口。
- 0.7：对但两项瑕疵都有。
- 0.1：错但标签合格（断言失败、报错、超时、缺库；含性能轮大输入上答错——大输入是题意合法输入，答错即错解）。
- −0.1：错或无代码，且无标签——没交出有效卷面。
- 0.0：历史口径里管理器超时/故障的兜底值，会污染组内统计（BC-10）；现版单条掩码（全故障组作废），正常流程不再出现。

课程的 6 个固定候选按 legacy 口径判（`run_demo.py` 钉 legacy，与推演基线一致）：两个正确解 1.1、两个错解 0.1、格式错 −1.1、`early_exit` 骗到 1.1——映射到现版档位的对照表见 [reward 档位](#reward-levels-2)。

**第四节：执行边界，历史口径的四个缺口（现版全堵上）。**

1. 提前退出拿满分：候选代码在断言之前 `sys.exit(0)`，退出码是 0，判 1.1。四个后端都按退出码判成功，换后端堵不住。
2. 超时不等于清理：管理器只是不再等，后台线程还在跑；源码里杀掉所有进程的那段代码被注释掉了。
3. 判题故障记 0.0：0.0 混进组内均值和标准差。同组三条错误回答各得 0.1、一条故障记 0.0 时，三条错误回答的 advantage 都是 +0.5。
4. 期望答案和候选代码在同一个进程里：候选代码理论上能读到断言。

现版的堵法：期望答案不进候选进程，子进程逐条报告输出，由判分方比较，缺结果就算失败；执行层区分超时、报错、判题故障，超时后杀掉整组进程；判题故障先重试，仍失败就把这一组作废，advantage 全为 0。详见[执行边界](#execution-gaps-2)。

**第五节：任务池，同一行数据怎样读回、怎样查错。** 判分器只认数据行里的 `data_source` 和 `ground_truth`，所以入池前要读回核对：GT 里的断言和接受的记录一一对应，隔离的记录没混进去，测试版本跟着 GT 变。训练读的是 parquet，本课的 JSONL 只演示形状。出了错按五层归因：Task、Tests、GT、Verifier、Evaluation，一条记录可能没错，也可能同时错在几层。详见[任务池](#task-pool-2)。

**第六节：三项作业和自测。** 先分清三套工具：`run_demo.py score` 是固定示范，只看不改；`practice.py score` 在你的 data-01 上判分；`practice.py blind-init` 和 `blind-grade` 是不标答案的故障定位练习。

- **2.1 看原 scorer 怎样给分。** 跑示范，挑两个结果不同的候选，从格式、代码、GT、第一个失败的断言一直追到 reward。
- **2.2 改一个条件。** 在 data-01 上先预测再判分：补一条全负输入，或者去掉回答的格式标签，看哪个候选的分数变了、为什么。
- **2.3 不看答案定位故障。** 给 8 条记录各自判断错在哪一层，再读回自己的小池。

学完脱稿讲一遍 [60 秒口述](#oral-2)，再从[面试深挖](#interview-2)里随机挑一个追问，按四句来回答：机制是什么、这个版本怎么实现、一个反例、证据能证明到哪一步。

读完导读，按顺序读下面的概念五节，再从[作业 2.1](#assignment-2-1)开始动手。

## 先分清三个角色

| 谁 | 输入 | 输出 | 源码 |
|---|---|---|---|
| 判分器 | 回答文本，加 GT 字符串 | reward（1.1 / 0.9 / 0.7 / 0.1 / −0.1，字典序分档）和一段日志 | [coder1_plus 的 compute_score_detailed](../verl/utils/reward_score/coder1_plus/__init__.py) |
| 执行后端 | 一段拼好的 Python 程序；标准输入输出题另加一条 stdin | 结构化状态（正常、编译错、运行错、超时、判题故障分开）加 stdout、stderr | [sandbox.py](../verl/utils/reward_score/coder1_plus/sandbox.py)（macOS sandbox-exec / Linux firejail；原版 firejail_exec.py 由 `CODER1_EXEC` 选） |
| 奖励管理器 | 一批回答，Code-R1 每步 16 题 × 16 个 = 256 个 | 每个回答一个分数，写在最后一个有效 response token 上 | [prime_plus](../verl/workers/reward_manager/prime_plus.py)（判题故障重试、单条掩码；原版 PrimeRewardManager） |

数据行里的 `data_source` 决定交给哪个判分器：[路由](../verl/utils/reward_score/__init__.py)把 `code_plus` 交给现版 `coder1_plus`，历史数据的 `code` 走原版 `coder1`。

执行后端像考场，限制权限、时间和资源；判分器像判卷机。考场守规矩，不证明学生答完了卷子；判卷机比对正确，也不证明考场安全。所以「沙箱安全」和「判分可信」要分别验收。

**口述：** 判分是三个角色合作：执行后端负责跑，判分器负责判，奖励管理器负责调度和兜底。哪一层出了问题，分数都会变，但修法完全不同。

| 1 格式门 | 提交协议写进 prompt，格式失败单独计数 | 正则从开头匹配，开头多一句寒暄就是 -1.1 | 无标签不拦，退回整段抽块照样执行（fallback），只扣格式分 |

### 次图③（放大主图的 ②）：提取的两级定位（标签缩围 + 围栏抽块）

提取分两级：先用 `<answer>(.*?)</answer>` **缩围**（取最后一个 answer 的内部；无标签时退回整段——fallback 的"退回"就在这一步），再用 ```` ```(?:\w+)?\n(.*?)\n``` ```` 在范围内抽**全部**围栏块拼接。格式检查与提取**相互独立**：标签不合格只扣格式分，不拦提取与执行；围栏抽不到（none）才真的不执行。

```text
⓪ strip 去首尾空白
① 格式检查 <think>.*</think>.*<answer>.*</answer>$   只看标签、不看围栏
② 缩围 <answer>(.*?)</answer> 取最后一个；无标签 → 整段原文
③ 抽块 ```(?:\w+)?\n(.*?)\n```  范围内全部块 → '\n'.join 拼接
④ 三态：strict（①合格+有代码） / fallback（①不合格+有代码，照样执行）/ none（无代码，−0.1 不执行）
```

五种典型回答的走例（verl 真实函数实测，一键复现：`python -B "RLVR学习资料/examples/maximum-subarray/extract_walkthrough.py"`）：

| 回答形态 | ①格式 | ②范围 | ③块数 | 三态 | 结果 |
|---|---|---|---:|---|---|
| A 标签+围栏齐全 | 合格 | 最后一个 answer | 1 | strict | 执行，对+标签 1.1 |
| B 无标签、有围栏 | 不合格 | **整段原文**（退回） | 1 | fallback | 照样执行，对+无标签 0.9 |
| C answer 内草稿+正文两块 | 合格 | answer 内 | 2 → **拼接** | strict | 两块都执行，见下方顺序陷阱 |
| D 标签齐全、代码裸贴无围栏 | 合格 | answer 内 | **0** | **none** | **不执行，−0.1——代码对了也没用** |
| E 标签后再说句废话 | 不合格（`$` 锚定被破坏） | answer 内 | 1 | fallback | 照样执行，只损格式分 |

**顺序陷阱（C 案例，实测）**：answer 内多块拼接后，Python 的同名类**后定义覆盖前定义**——草稿块在前、正文块在后 → 1.1（正文覆盖草稿）；正文在前、草稿在后 → **0.1**（`return 0` 的草稿覆盖了正确解）。同一份代码，块顺序对调、分数天壤之别。所以"先草稿后正文"要靠**标签**隔开（草稿放 answer 外会被缩围天然排除），不能靠围栏并列。正则与字符串的语法底座见 [CS 补充章](#cs-2)。

### 门③④内部：拼程序与调用入口（entry_point 如何接上抽取的代码）

判分不「调用」任何神秘的接口——拼一个 Python 程序，最后一行就是调用：`build_program` 按 **prelude → 候选代码 → GT 断言 → `check(入口)`** 拼接，`check(Solution().maxSubArray)` 这一行做三个动作：实例化模型写的类（`Solution()`）、**取方法本身当对象**（`.maxSubArray` 没有第二个括号——绑定方法，`self` 已绑给实例，后续调用只需传业务参数）、把它作为 `candidate` 传进考题函数；`check` 内部的 `candidate(nums=...)` 才真正执行模型代码。判分器因此不知道类名方法名（一对多）：题目特异性全在数据行的 `entry_point` 字符串里。另有一条隔离规则：模型若在回答里定义了 `ListNode` 等辅助类，exec 后会撤销其覆盖、环境定义优先——否则错误的 ListNode 会污染 `list_node`/`is_same_list`，让正确解被误判（[BC-24](bad_case登记表.md#layer-manager)）。断言（`assert 条件`）是判分点：首败即停、消息定位、结果走退出码。拼接契约的洞——期望答案在候选进程里——由受保护协议堵上：断言拆成「调用+期望」、子进程无期望只打印输出（带 nonce）、判分方进程外比较、逐条全报。完整程序实物与 `sys.exit(0)` 骗分对照见 `extract_walkthrough.py` 同目录的讨论（BC-07）。

受保护协议的事件流实物（2026-11-08 实测，贯穿题两条断言）：

```text
正确解子进程 stdout:                              early_exit 子进程 stdout:
@@.. {"event":"start","cases":2}                 @@.. {"event":"start","cases":2}
@@.. {"case":0,"status":"ok","repr":"6"}         @@.. {"event":"solution_error",
@@.. {"case":1,"status":"ok","repr":"1"}             "error":"SystemExit"}
@@.. {"event":"done"}                            （没有任何 case 结果）
judge: passed=True                               judge: completed=False，
                                                     两条 case 全 missing → 0.1
```

堵 early_exit 的关键一行是 harness 执行候选代码的 `except BaseException`——`sys.exit(0)` 抛的 `SystemExit` 是 `BaseException` 的子类，普通 `except Exception` 抓不到它；harness 把提前退出转成 `solution_error` 事件，而不是让进程带着退出码 0 溜走。期望答案物理上不在子进程程序里（实测搜不到），候选代码即使伪造结果行也对照不出正确的 repr。


三个容易错的细节：

- **函数题没有「比较输出」这一步。** 断言和候选代码在同一个程序里，断言一失败程序就带着 `AssertionError` 退出，后面的断言不再执行。判分器只看到退出码非 0。
- **标准输入输出题不是按顺序判的。** 原版把多条用例并发跑，按完成先后检查，遇到第一个失败就返回 0.1。比较只去掉首尾空白，`"1 2"` 和 `"1  2"` 仍算不同。
- **两套代码提取规则不同。** 回答里先放一段会抛异常的草稿代码、后放正确代码时，原版把两段拼在一起跑，得 0.1；原生评测器只取最长的那段，就能通过。2026-10-15 用原版判分器实跑确认。

**口述：** 判分七步：格式门、抽代码、拼程序、执行、判定、映射 reward、管理器收尾。函数题把断言拼在代码后面一起跑，只看退出码；高分还要问断言真的跑完了吗。

## reward 档位：每个数字证明了什么

| 分数 | 什么时候出现 | 证明了什么 | 没有证明什么 |
|---:|---|---|---|
| 1.1 | 对 + 标签合格 +（有性能标定时）限时内通过大输入 | 正确性 1.0 + 格式 0.1（+ 性能达标） | 不证明断言真的跑完了、测试够、也未必是独立能力（见下） |
| 0.9 | 对，但有一项瑕疵：无严格标签，或性能轮超时 | 逻辑正确；格式或速度有缺口 | 无标签时也可能是抽代码抽到了能跑的片段 |
| 0.7 | 对，但格式与性能两项瑕疵都有 | 同上叠加 | 同上 |
| 0.1 | 错 + 标签合格（断言失败、报错、超时、缺库；含性能轮大输入上答错/崩溃——大输入是题意合法输入，答错即错解） | 按提交协议交了卷 | 不区分算法错、漏写导入、超时、缺库和后端故障 |
| −0.1 | 错或无代码 + 无标签 | 没交出有效卷面 | 同上 |
| 0.0 | 奖励管理器等待超时或判题故障 | 这次判分没有完成 | 不是正确性标签；正确处理是重试后单条掩码（不浪费其余 rollout），全故障组作废 |

三条设计原则（2026-11-06/07 定案，来龙去脉见[设计定案表](设计定案表.md)）：

- **架构先说清：判分器是一对多的通用机器**。一个判分器服务全部 1890 题，题目特异性全部走**数据行字段**——GT 断言如此，每题 `time_limit_ms` 也如此（业界同构：CodeContests 数据集每题带 `time_limit` / `memory_limit_bytes` 字段，AlphaCode 评测读它；Codeforces 判题机读每题配置）。换题不换判分器，换数据行就行。
- **字典序**：正确性 1.0/0 是主排序键，格式 ±0.1 与性能瑕疵 −0.2 是次键——任何对答严格高于任何错答。性能瑕疵**只指超时**；大输入上输出不符或出错是正确性失败（0.1 档，2026-11-09 归因修正——大输入是题意合法输入，答错就是错解，留在 0.9 会让崩溃的错答与慢而对打平）。性能轮只对正确性通过者加跑（自动课程：早期全错时性能轮不激活）。**为什么错答还能是正的 0.1**：GRPO 组内标准化下绝对值平移不变、正负号中性，排序与间距才是信号——推导与实测见[03 的 reward 到 advantage](03_Rollout与GRPO机制.md#advantage-3)。
- **空间复杂度只做限额护栏**（`as=4096m` 超限=memory_error=0.1），不设奖励档——Python 解释器基线约 30MB 淹没 O(1)/O(n) 空间信号，且 LLM 写出爆内存解是低频事件，详见[补强项 10](examples/source-supplements/README.md#supplement-10)。

历史口径（−1.1/0.1/1.1 三档、格式门早退）的异常症状与识别见[bad case 库](bad_case登记表.md)；`CODER1_PLUS_REWARD=legacy` 仅供推演产物复现基线。

课程的 6 个固定候选，在示范的 8 条接受测试上，2026-10-15 实测结果：

| 候选 | 做了什么 | reward | 逐条审计完成几条 | 说明 |
|---|---|---:|---:|---|
| `reference` | 正确的 Kadane 写法，自带 `from typing import List` | 1.1 | 8 | 全部通过 |
| `correct_prefix` | 正确的前缀和写法 | 1.1 | 8 | 全部通过 |
| `wrong_empty` | 允许空子数组，全负数组返回 0 | 0.1 | 8 | 第一个失败的断言是 `diag-all-negative`，输入 `[-3,-2,-5]` |
| `wrong_sum` | 直接返回整个数组的和 | 0.1 | 8 | 第一个失败的是 `seed-1`：应得 6，返回 1 |
| `bad_format` | 只给代码块，没有 think 和 answer 标签 | -1.1 | 0 | 日志是 `Bad format detected!` |
| `early_exit` | 代码第二行就 `sys.exit(0)` | **1.1** | 0 | 一条断言都没执行，退出码却是 0 |

「逐条审计」是演示脚本另跑的一次检查：把 8 个输入逐条喂给候选、记下返回值，和原 scorer 的那次执行无关。它告诉你 `early_exit` 一条都没完成，原 scorer 自己看不到这一点。

两个要分开的「骗过判分器」：

- `wrong_empty` 是**测试不够**。原始数据只有 3 条 seed，答案都是正数，它在 seed 上全对，会拿 1.1；补一条全负输入才能抓住。这归 Tests 层，修法是补测试，见[主框架的错解表](RLVR工业流程.md#test-strength)。
- `early_exit` 是**测试根本没跑**。测试再多也没用，修法是让判分方拿到「每条测试都执行了」的证据。这归 Verifier 层。

还有一种 0.1 不是算法错：漏写 `from typing import List` 时，签名里的 `List[int]` 在 Python 3.12 上报 `NameError`，只拿 0.1；Python 3.14 改成延迟求值注解，同一份代码就能通过。这是提交契约和运行环境的问题，见[主框架的执行边界](RLVR工业流程.md#execution-boundary)。

**口述：** -1.1 是没按协议交卷，0.1 是交了但没过，1.1 是程序以 0 退出，0.0 是管理器兜底。0.1 不是通过，1.1 也不一定是通过：可能测试不够，也可能测试根本没跑。

**分值本身的坑（[补强项 9](examples/source-supplements/README.md#supplement-9) 修的）。** 原版口径里格式边际（0.1 对 −1.1，差 1.2）大于正确边际（1.1 对 0.1，差 1.0）：格式合格的错答压过格式不合格的对答，而且后者在格式门处直接 −1.1，正确的代码根本不执行；长思考被截断、没写完 `</answer>` 的正确代码同样 −1.1。补强版改成字典序：正确性 1.0 对 0，格式 ±0.1 做次级信号，四档 1.1 / 0.9 / 0.1 / −0.1，任何对答严格高于任何错答；GRPO 组内标准化下，同质组里的格式学习信号不变（排序一致）。

## 执行边界：原版的四个缺口与补强版

**缺口 1：提前退出拿满分。** 候选代码在断言之前 `sys.exit(0)` 或 `os._exit(0)`，程序以 0 结束，判 1.1。换后端堵不住：firejail、docker、CES 都按退出码判成功，kira 只看 stderr 是否为空。普通的「完成」字符串也能被候选代码自己打印出来。

**缺口 2：超时不等于清理。** 奖励管理器用 `asyncio.wait_for` 等每个回答，600 秒没结果就不再等，记 0.0。可是后台线程还在跑；`with ThreadPoolExecutor` 退出时还会等这些线程结束。源码里「杀掉所有进程」的那段写在注释里，没有生效。真正兜底的是后端自己的限时：firejail 的 `--timeout` 30 秒，docker 在 `finally` 里强制删除容器。

**缺口 3：判题故障记 0.0。** 0.0 和正常分数一起算组内均值和标准差。同组四条回答：三条错误回答各 0.1，一条判题故障记 0.0，算出的 advantage 是 +0.5、+0.5、+0.5、-1.5，三条错误回答反而被奖励。原版只有 CES 后端会对疑似服务器超时重试。

**缺口 4：期望答案和候选代码在同一个进程里。** 断言就写在候选代码后面，候选代码理论上能读到期望答案。比较规则也是写死的：题面说「任意顺序」，测试仍按列表顺序比较。

**缺口 5：reward 看不见快慢（补强项 10 修）。** 判分只测输出正确性，O(n²) 与 O(n) 的正确回答同分、组内 advantage 也相同——RL 学不会「写快」，反而可能强化容易写对的暴力解。补法见 [reward 档位](#reward-levels-2)的补强项 10 段。

**补强版怎么做。** 以 LeetCode 53 为例：

1. 判分方把 3 条断言拆成「调用」和「期望答案」，例如调用 `candidate(nums=[-2,1,-3,4,-1,2,1,-5,4])`，期望 6。
2. 子进程只拿到候选代码和 3 条调用，逐条执行，把每条输出带着一个随机标记打印出来，最后打印「完成」。
3. 判分方逐条比较输出和期望答案。缺任何一条结果、缺完成事件、某条报错或答案不同，都判失败。

所以 `sys.exit(0)` 表现为 3 条结果缺失，判 0.1；候选代码即使伪造出「通过」和「完成」，也不知道正确答案是什么。

| 候选 | 原版 | 补强版 | 补强版看到的现象 |
|---|---:|---:|---|
| 数据集参考解，不带 `typing` 导入 | 0.1 | 1.1 | 补强版先拼原始前缀，3 条都通过 |
| 返回整个数组的和 | 0.1 | 0.1 | 第一条答案错 |
| `sys.exit(0)` 提前退出 | **1.1** | 0.1 | 候选代码加载失败，3 条结果缺失 |
| `os._exit(0)` 提前退出 | **1.1** | 0.1 | 没有完成事件，3 条结果缺失 |
| 伪造通过帧和完成事件 | 0.1 | 0.1 | 伪造的答案全不对 |
| 读取仓库里的数据文件 | 0.1 | 0.1 | 沙箱拒绝读取 |

这张表里的「参考解」是数据集原样的代码，不带 `typing` 导入，所以原版只给 0.1；上一节演示里的 `reference` 自带导入，原版给 1.1。两者不是同一份程序。

执行层和故障处理也补了：

- 执行结果分成正常、编译错、运行错、内存超限、超时、被杀、判题故障几种状态，记录耗时，超时后杀掉整个进程组。macOS 用系统自带的 sandbox-exec，禁止联网、只允许写临时目录、禁止读本仓库；后端不可用时报判题故障，不会退回到不隔离的执行。
- 判题故障先有限次重试；仍失败的按 D15（设计定案表，2026-11-09 起）默认**单条掩码**：故障样本分数＝组内有效均值，advantage 恰为 0，其余已判分的 rollout 照常提供信号，另一组不受影响仍是 ±0.866；组内全部故障才退回整组作废。（2026-10-14 实测时是整组作废口径，2026-11-09 升级为单条掩码。）

以上结果在 2026-10-14 实测，2026-10-15 重跑一致。sandbox-exec 只适合本机开发；firejail 分支和补强版奖励管理器的整体运行要到 Linux 训练环境验收。

**执行量估算。** 每批 B 道题、每题 G 个回答、每个回答 M 条测试，计划执行的测试数是 B×G×M，公式见[主框架](RLVR工业流程.md#execution-boundary)。Code-R1 的函数题把所有断言放进一个程序，所以每步是 16 × 16 = 256 次程序执行，不随测试条数增加；标准输入输出题每个回答最多跑 8 次。

**口述：** 原版有四个缺口：提前退出拿满分、超时不清理、故障记 0 混进组内统计、期望答案和候选同进程。现版把判分方和执行方拆开，期望答案不进候选进程，缺结果就算失败；故障先重试，仍失败单条掩码（全故障组作废）。

<a id="bc10-fault-backfill-2"></a>

#### 完整案例 BC-10：判题故障回填 0.0 如何推高错答 advantage（S4 → S3 → L6）

```text
S4 冒烟：reward 曲线周期性尖刺/骤降；某步大量样本 0.0
   ↓
S3 复现：组内算例（离线、零 GPU）
   组 [0.1, 0.1, 0.1, 故障→0.0]
   mean = 0.075, std = 0.05 → advantage [+0.5, +0.5, +0.5, −1.5]
   ↑ 三条错答被组内标准化放大成「比故障好」的正信号
   ↓
报错分型：不是代码错，是基础设施故障（超时/异常）
   ↓
列消费者：分数列表 → 组内均值/标准差 → advantage → 策略更新
   ↓
根因（L6 奖励管理器）：0.0 不是中性值；管理器把「故障」当成了「成绩」
   ↓
修法：先重试；仍失败单条掩码（故障分 = 组内有效均值 → advantage 恰 0）
      全故障组退回整组作废
   ↓
验证：[1.1, 0.1, 0.1, 故障] → mask=0.433 → [+1.41, −0.71, −0.71, 0]
```

**三种处理的对照（同一组数据）：**

| 处理方式 | 组 `[0.1, 0.1, 0.1, 故障]` | 组 `[1.1, 0.1, 0.1, 故障]` |
|---|---|---|
| 原版：故障记 0.0 | `+0.5, +0.5, +0.5, −1.5`（**错答被奖励**） | `+1.49, −0.43, −0.43, −0.63`（故障比错答还低） |
| 旧补强：整组作废 | `0, 0, 0, 0` | `0, 0, 0, 0` |
| 现版：单条掩码（D15） | 全组同分 → ≈0（本例有效样本同分，与作废等价） | `+1.41, −0.71, −0.71, 恰 0`（故障零信号，其余照常） |

**为什么不能用别的占位值：** 记 0.2 时，`[0.1,0.1,0.1,0.2]` 下占位样本拿 `+1.5`——**全组最强正信号**。任何具体数值都在替未知质量伪造主张；掩码（=有效均值）才是「不知道」的正确表达。代价：组内尺度被均匀放大 `sqrt((n−1)/(n−2))`，方向与排序不变。

**一句话口述**：

> 「冒烟时看到 reward 曲线周期性尖刺，某一步大量样本是 0.0。我先离线用组内算例复现：`[0.1,0.1,0.1,0.0]` 标准化后 advantage 是 `[+0.5,+0.5,+0.5,−1.5]`——三条错答反而拿到正信号。报错分型：这不是代码错，是基础设施故障（超时/异常）。往上追到奖励管理器：原版把故障回填成 0.0，而 **0 不是中性值**，它进组内均值和标准差，把错答放大成『比故障好』。修法是先重试，仍失败就单条掩码——故障分设成组内有效均值，advantage 恰好 0，其余 rollout 照常提供信号；全故障组才整组作废。验证：`[1.1,0.1,0.1,故障]` 掩码后 advantage 是 `[+1.41,−0.71,−0.71,0]`。」

**发现阶段 / 出错位置**：发现 **S4 冒烟**（可 **S3** 离线组内算例复现）；出错 **L6 奖励管理器（回填 0.0）**，**L7 超时是触发条件**。不是 verifier 打分逻辑错——打分函数返回的是判题故障状态，把它当成绩是管理器干的。

**证据边界**：`[0.1,0.1,0.1,0.0] → [+0.5,+0.5,+0.5,−1.5]` 与掩码后 `[+1.41,−0.71,−0.71,0]` 是 CPU 受控演示/单测（`test_source_supplements.py` 的 `test_legacy_zero_rewards_wrong_answers`、`test_default_masks_sample_with_exactly_zero_advantage`、`test_all_failed_group_falls_back_to_void`）；`verify_reward_manager_cpu.py` 的整体运行需要 torch + tensordict（当前环境缺 tensordict，未实跑）；your-01 推演里的沙箱超时事故是**推演**，不是实测日志。

**回流件**：单条掩码/全故障作废的回归测试已入库（上列三条）；仍缺**故障率告警**——管理器已输出 `masked_samples` / `voided_groups`，但还没有「故障率超过阈值就停训排查」的门控，这是下一步要补的闭环件。

## 判分两轮：正确性轮与性能轮——离线准备什么、在线做什么

「轮」是判分内部的两个阶段，不是「离线一轮、在线一轮」：

```text
【离线·数据构造，一次性，训练前】
  ├─ 测试用例集：题面样例 + 数值边界 + 随机（过 validate 筛选）
  ├─ expected：小域 oracle 直出 / 大域参考解（信任链，见 01 的 expected 分层）
  └─ perf 标定：参考解在种子大输入上实测墙钟 ×3（系数）→ time_limit_ms
     + 大输入的 expected + 种子，全部写进数据行 extra_info.perf

【在线·verifier 判分，每个 rollout、每一步】
  门③ 提取代码 →
  ┌─ correctness 轮（正确性轮）：候选 + 全部用例执行，钟 = 沙箱整体钟
  │    （firejail 30s / 管理器 600s 兜底）；只判对错，挂 → 0.1
  └─ perf 轮（性能轮，条件触发：上轮过了且数据行带标定）：
       种子确定性重建大输入 → 用离线标好的 time_limit_ms 当 timeout 跑一次
       超时 → 0.9（对但慢）；大输入答错 → 0.1
```

离线只产三样：用例、expected、每题一个 time_limit_ms。**连钟都是离线算好带进来的**——判分时零标定，同题各步不漂移（钟漂移 = 判分标准漂移 = 又一个让 reward 说谎的口子）。**种子确定性重建**：伪随机种子固定 → 重建出逐字节相同的大输入；只存几个字节的种子、不存 MB 级本体，代价是生成器代码锁版本。

**成本按离线/在线分开：**

| 成本 | 何时发生 | 量级 |
|---|---|---|
| 用例生成+validate 筛选 | 离线，一次性 | 按 D13 分级预算（候选池 40-80/200/1000，入 GT 10~30 条） |
| expected 计算 | 离线，一次性 | 小域 oracle；大域参考解每题一条 |
| time_limit 标定 | 离线，一次性 | 每题 1 次参考解执行（墙钟 ×3 是系数，不是跑三遍） |
| correctness 轮执行 | 在线，每 rollout 每步 | 条数 × 16 rollouts × 步数 |
| perf 轮执行 | 在线，条件触发 | 每题每 rollout 1 次大输入执行 |

注：上标丢失时 `parse_size_bound` 解析出 105 < 1000 → 该题不做标定，「perf 轮执行」这一行不发生；correctness 的 accepted 条数也被 106~1000 的丢弃截断（完整见 [BC-25](01_数据理解与GT构建.md#bc25-superscript-1)）。

**三套钟的对比**（LeetCode 一列为平台通识，仓内无证据文件）：

| 系统 | 钟的粒度 | 谁定的 | 判什么 |
|---|---|---|---|
| LeetCode | 每用例一个钟（语言乘数） | 平台按参考解标定 | 对错 + 快慢混在一起；TLE 二值 |
| 我们 correctness 轮 | 程序级一个钟（firejail 30s / 管理器 600s） | 沙箱配置 | 只管对错；钟是兜底 |
| 我们 perf 轮 | 每题一个钟 `time_limit_ms` | 离线标定：参考解墙钟 ×3，下限 500ms | 专管快慢 |

**为什么不学 LeetCode 每用例一个钟。** ① 判别力重复——correctness 轮不判快慢，用例级钟的唯一用途（区分「对但慢」）已由 perf 轮专管且更准（10⁵ 规模 + 题级标定钟）；② RL 的 reward 需要「对但慢」的 0.9 中间档，LeetCode 的二值 TLE 给不了组内排序信号，快慢混进每用例二值判定会把性能瑕疵和正确性失败搅在一起；③ 诊断粒度没丢——受保护协议逐条上报，「挂在第几条」照样看得见。一句话：**LeetCode 是人交卷、判一次、verdict 给人看；我们每步 16 份卷、判几万次、reward 喂优化器——拆两轮、分档输出，钟只配在判快慢的那一轮。** 超出题面约束的输入按 D21 用例级隔离（`beyond_contract`，不参与计分）。完整无损版见[讨论结论库第 11 条](讨论结论库.md#lib-two-rounds-cost)。

**这条路在数据侧会踩的第一个坑：长度上界上标丢失。** 扩容解析和 verifier 解析会把 `10⁵` 统一读成 `105`：correctness 随机扩容 106~1000 被 validate 按用例级拦掉，perf 因标定 105<1000 整题跳过——全链路停在 105，`10⁵` 从未出现。完整推演、三层口径与证据边界见 [01 的 BC-25 案例](01_数据理解与GT构建.md#bc25-superscript-1)；它也说明**validate 门读约束，correctness/perf 打分不读**。

**判分粒度的三种「不罚」——单位不同，不能混用：**

| 粒度 | 机制 | 归属场景 |
|---|---|---|
| **用例级丢弃 / 隔离** | 超上界或超约束的**单条输入**不参与判定：构造期判 invalid 丢弃；运行时记 `beyond_contract` 仅供诊断 | 承诺外输入；BC-25 的 106~1000 随机扩容 |
| **样本级掩码（D15）** | 故障样本分=组内有效均值 → advantage 恰 0 | 判题基础设施故障 |
| **题级跳过** | 整题不判：性能轮标定解析上界 < `MIN_PERF_SIZE`(1000) → 没有快慢维度，进跳过计数（909 题） | 约束值过小/解析错误 |

0 分 = 「考了且判错」= 还是罚；掩码是样本级、管组内 advantage；题级跳过是「这题没有这个维度」。**用例数 ≠ 题数**，归因时不能混用。

**口述：** 判分内部分两轮：正确性轮只判对错，钟是沙箱兜底；性能轮判快慢，钟是离线标定好带进来的每题 time_limit_ms——判分时零标定，同题各步不漂移。

## 任务池：同一行数据怎样读回、怎样查错

判分器只认数据行里的两样东西：`data_source` 决定用哪个判分器，`reward_model.ground_truth` 决定怎么判。一行的完整字段见 [01 的字段字典](01_数据理解与GT构建.md#metadata-fields)。

入池前读回核对三件事：

- GT 解码后，每条断言都对应一条接受的记录，`case_id` 和 `extra_info.case_index` 一致。
- 隔离和待审核的记录没有混进 GT。
- 测试版本跟着 GT 变：补一条测试，`test_version` 就换一个。

导出成功只证明格式能读回，不证明答案对。

训练入口还有三处要核对：

- **格式。** 训练加载器用 `pd.read_parquet` 读 parquet，见 [rl_dataset.py](../verl/utils/dataset/rl_dataset.py)。本课的 JSONL 只演示行的形状，不能直接交给训练入口。
- **路径。** 预处理写到 `data/code-r1-{N}k-leetcode2k-taco/`，[main_grpo.sh](../main_grpo.sh) 读的是 `data/code-r1-12k/`，两者不会自动对上。
- **TACO 的划分和测试裁剪。** [coder1.py](../examples/data_preprocess/coder1.py) 的 `taco()` 先把所有行按 train 写好再切分，之后那个循环改的是临时字典，所以 test 行的 `extra_info.split` 仍然写着 train。标准输入输出题还经过 `minimize_stdio`：按输入大小排序只留最小的 8 条，跳过超过 4 KB 的输入，输入输出条数不等时 `zip` 会悄悄截断。大输入全被裁掉，复杂度问题就测不出来。

出了错，按五层归因。下表是作业 2.3 题包里的字段：

| 层 | 题包里看哪些字段 | 怎么查 |
|---|---|---|
| Task | `entry_point` | 是不是 `Solution().maxSubArray` |
| Tests | `input`、`expected` | 输入是否合法；expected 是否等于完整枚举的结果 |
| GT | `gt_expected` | 是否和 expected 一致 |
| Verifier | `scorer_reward`、`observed_cases`、`required_cases`、`claims_correctness`、`actual_values` | 声称正确时，结果是否齐全、reward 是否 1.1、实际输出是否等于 expected |
| Evaluation | `n`、`c`、`k`、`reported_pass_at_k` | 是否满足 1 ≤ k ≤ n；报告的 pass@k 是否等于公式结果，公式见[主框架的评测](RLVR工业流程.md#evaluation) |

一条记录可能没错，记 `none`；也可能同时错在几层。expected 本身错了，先算 Tests 的错，不能拿它指控候选。

**口述：** 入池前读回三查：断言和接受记录一一对应，坏记录没混进来，测试版本跟着变。训练读 parquet，路径要对上。出了错按 Task、Tests、GT、Verifier、Evaluation 五层归因，一条记录可以有多层错。

## 传统 CS 知识补充：进程、资源与沙箱术语串讲

给不是传统 CS 科班的读者的背景补给：把本篇判分与沙箱出现过的术语集中给一遍「定义 + 人话」，统一用「隔离考场」的场景——判分就是把模型生成的不可信代码当作考生送进独立考场答卷。已熟的读者可跳过；后续各篇遇到的新术语按同样格式补进各篇自己的补充章，本篇定义过的不再重复。

### 进程与派生（本节统一场景：考生怎么进考场）

| 术语 | 定义 | 人话 |
|---|---|---|
| 进程（process） | 操作系统里一个正在运行的程序实例，有独立的内存和资源 | 考场里的一个座位：每位考生一份草稿纸（内存），互不共用 |
| 子进程（subprocess） | 由当前程序另起的一个独立进程 | 监考员不替考生答卷，把卷子发给考生自己做——判分就是「拼好程序 → 开子进程跑它」，跑砸了不连累判分器自己 |
| fork | Unix 创建进程的系统调用：把当前进程复制一份 | 细胞分裂：考生自己又可以分裂出「随从」帮他干活——fork 炸弹就是无限分裂，把座位挤爆 |
| ★进程 vs 线程 | 进程各占一块独立内存；线程是同一进程内的多条执行流，共享内存 | 独立座位 vs 一个人同时干几件事。本仓库判分**并发**用的是线程池（几个监考员同时收卷，`prime.py` 的 `ThreadPoolExecutor`），被judged的**回答**各自是子进程（考生）；两者别混 |
| 进程组（process group） | 主进程和它派生的全部子孙进程绑成一组，有一个共同的组号 | 连坐户口本：考生带进场的随从也算这一家的。超时后**杀整组**（`killpg`）才不会漏掉躲藏的孙进程——只杀主进程，随从还在场里占资源 |

### 文件描述符与文件系统（本节继续用考场的场景：随身物品管理）

| 术语 | 定义 | 人话 |
|---|---|---|
| 文件描述符（fd） | 进程每打开一个文件/管道/网络连接，操作系统发一个整数编号 | 寄存处的**取件号**：打开文件领一个号，读写全凭号。每个进程生来有三个默认号：`0`=标准输入、`1`=标准输出、`2`=标准错误——所以「程序把结果写到 1 号」就是平时说的 print 到标准输出 |
| nofile 限额 | 同时持有取件号的数量上限 | 考生最多同时开 32 个柜子（`--rlimit-nofile=32`）。不设限的恶意代码可以狂开文件把系统取件号耗光，别人什么都打不开 |
| fsize 限额 | 单个文件最多能写多大（`--rlimit-fsize=2m`） | 草稿纸最多写两页：防考生无限写把仓库（磁盘）塞爆 |
| 白名单目录 / `--private` | 沙箱里只挂载一个干净临时目录，其余文件系统不可见或只读 | 考场里只发一张空白草稿纸：看不到考卷库（仓库源码）、看不到监考员的记分册（GT 与判分器文件），写了也只写在自己的草稿纸上，散场（超时/结束）整张纸销毁 |

### 资源限额 rlimit 家族（本节统一场景：考场五道闸）

rlimit 不是劝告，是**内核执行的物理围栏**：进程越线，操作系统直接杀，程序自己拦不住。firejail 判分后端的五道闸（`firejail_exec.py:38-49`），每道对应一种真实作恶方式：

| 限额 | 参数 | 拦截的作恶 | 人话 |
|---|---|---|---|
| 进程数 | `--rlimit-nproc=32` | fork 炸弹：指数级分裂进程拖垮机器 | 考生最多带 32 个随从进场 |
| 取件号数 | `--rlimit-nofile=32` | 狂开文件耗尽全系统的文件描述符 | 同时最多开 32 个柜子 |
| 单文件大小 | `--rlimit-fsize=2m` | 写爆磁盘 | 草稿纸限两页 |
| 地址空间 | `--rlimit-as=4096m` | 无限要内存把邻居 OOM | 座位面积上限 4 GB |
| 墙钟时间 | `--timeout=00:00:30` | 死循环、sleep 拖时间占住并发位 | 考试限时 30 秒，到点收卷 |

三个容易混的时间与内存概念：

- **墙钟时间 vs CPU 时间**：墙钟是真实世界经过的时间（`timeout` 按它算——`sleep(60)` 一秒 CPU 不用也超时）；CPU 时间是处理器实际花在这个进程上的时间（`RLIMIT_CPU` 按它算）。判分限的是墙钟：死循环和赖着不动都拦。
- **三层时限各管什么**：firejail 30 秒（单个程序的判分上限）→ 奖励管理器 600 秒（单个回答的兜底，含排队等沙箱）→ 补强项 10 的 `time_limit_ms`（**每题**标定的性能轮上限）。一层比一层外圈。
- **地址空间（as）vs 物理内存**：地址空间是进程「被允许使用的最大内存地图」（虚拟内存的上限），物理内存是机器真实插着的条子。限 as 是在地图层面画界——进程要的地图超过 4 GB 就直接被拒，不用等真的占满物理条子把别人挤死。

### 沙箱与隔离后端（本节统一场景：考场的三种建法）

| 术语 | 定义 | 人话 |
|---|---|---|
| 沙箱（sandbox） | 限制程序能做什么（文件、网络、内存、进程、时间）的隔离执行环境 | 独立考场：锁死门窗、限定随身物品、限时收卷。同词不同物要分清——Shopping-Agent 的「交易沙箱」隔离的是**钱**（测试凭据、不接真支付），这里隔离的是**代码对主机的副作用** |
| firejail | Linux 的沙箱程序，用命名空间和 seccomp 限制进程 | 本仓库 Linux 判分的默认考场 |
| seccomp | Linux 内核级的系统调用过滤器：直接拒绝进程发出某些请求 | 门口的安检机在**内核层**把「开网络」这类请求直接拒收——不是贴告示劝阻，是物理封路。`--seccomp=socket` 就是封死 socket（网络）这条路 |
| sandbox-exec | macOS 自带的沙箱程序（补强版在本机开发用的后端） | macOS 版的考场门禁：`deny network*` 禁网、只许写临时目录 |
| Docker 容器 | 用容器技术做更重的隔离：整套独立文件系统加资源限额 | 整栋独立考楼 vs 一间隔音考室。原版可选 `CODER1_EXEC=docker`，但**它不封网络**——原版的已知缺口之一 |

三种隔离机制各管一个维度，别混着说：「rlimit 管资源**量**（几个进程、多少内存）、seccomp 管**动作**（能不能开网络）、白名单管**视野**（能看哪些文件）」。三道都上，才算防住了常见作恶。

### 提取的语法底座：正则与字符串（本节统一场景：在卷面上定位答案）

判分器只靠两个正则和两个字符串操作完成代码提取——它们值得逐个认识：

| 符号 | 定义 | 人话 |
|---|---|---|
| 正则表达式 | 用小型「模式语言」描述文本形状、在文本里找匹配 | 按长相搜卷面：描述"答案长什么样"，引擎负责找 |
| `.` / `\w` / `\n` | 任意一个字符 / 一个字母数字下划线 / 一个换行 | 三个单字符占位符：随便什么字、单词字、换行字 |
| `*` `+` `?` | 前面元素重复 0+ 次 / 1+ 次 / 0 或 1 次 | 有多少吃多少 / 至少一个 / 可有可无 |
| `(...)` 捕获组 | 把匹配的一部分装进编号盒子，`group(1)` 按左括号顺序取 | 搜到后把要的部分摘出来：`findall` 只返回盒子内容——提取代码全靠它 |
| `(?:...)` 非捕获组 | 只捆绑施加量词、不装盒 | `(?:\w+)?` = 语言名整体可有可无，但我们不要它的内容 |
| ★`.*` vs `.*?` | 贪婪（能多则多）vs 非贪婪（能少则少） | 提取标签对必须非贪婪：`<answer>(.*?)</answer>` 遇到最近的闭合就停，每对标签各自成匹配，才谈得上"取最后一个"；贪婪版会从第一个 `<answer>` 一口吞到最后一个 `</answer>`，语义全坏 |
| `re.DOTALL` | 让 `.` 连换行也吃 | 代码是多行的，不开它 `.*` 在第一行行尾就断 |
| `$` | 锚定"此处必须是结尾" | 格式检查要求 `</answer>` 是最后一个字符——尾随废话即不合格 |
| `r'...'` 原始字符串 | 反斜杠不被 Python 先解释一层 | `r'\n'` 是两个字符交给正则；`'\n'` 先变成真换行 |
| `strip()` / `'\n'.join(列表)` | 去首尾空白 / 用换行当胶水把列表粘成一个字符串 | 拼接全部围栏块就是 join 干的活 |

正则速成走例与五形态走图的交互演示：`extract_walkthrough.py`（examples/maximum-subarray/，调 verl 真实函数打印每步中间态）。

### 确定性与标定（本节统一场景：考卷怎么印得每场一样）

补强项 10（[性能轮](examples/source-supplements/README.md#supplement-10)）引入的两个工程概念：

| 术语 | 定义 | 人话 |
|---|---|---|
| 确定性种子（seed） | 给伪随机数发生器的初始值；同一种子生成的序列完全相同 | 印卷的模板：`Random(20261107)` 生成的十万元素大数组，标定那天和判分那天**一个字节都不差**——所以大输入不用存进数据行，判分时用种子当场重印 |
| 标定（calibration） | 用已知标准物给测量工具定刻度 | 用尺子之前先拿标准米尺对一遍：性能轮的 `time_limit_ms` 就是拿「参考解实测量出的耗时 ×3」定出来的刻度 |
| 正对照 / 负对照 | 证明测量工具两个方向都准：标准物必须测出对、已知坏样本必须测出错 | 尺子要验证两头：参考解（快）必须限时内通过，**故意构造的 O(n²) 慢解必须超时**——只测「好的能过」不等于尺子准，这是 Codeforces Polygon 出题标定时限的惯例 |

顺带定位一个容易混的点：**复杂度约束写在 prompt 里只是「提示」，不是训练信号**——RL reward 只看判分结果，prompt 里写 `len ≤ 10^5` 模型也未必照做；要让「快」变成可训练的信号，必须像补强项 10 这样把它接进判分器（timeout 成为 reward 的一部分）。判分器认的才是训练信号，判分器不认的 prompt 措辞都只是引导采样。

## 60 秒口述

判分这一站有三个角色：执行后端负责把程序在隔离沙箱里跑起来，判分器按受保护协议逐条比较、给出字典序分档的 reward，奖励管理器负责并发调度，判题故障先重试、仍失败整组作废。一个回答要过七步：格式门、抽代码、拼程序、执行、判定、映射、管理器收尾。分档里正确性是主键：对答 1.1 / 0.9 / 0.7（无标签或超时是瑕疵），错答 0.1 / −0.1，任何对答严格高于任何错答；带性能标定的题大输入答错按错答 0.1。分数不能直接当「通过」：`wrong_empty` 在 3 条正数答案的 seed 上拿满分，是测试不够——测试强度要单独验收。`early_exit` 骗满分是历史口径的缺口（断言拼在候选进程里、只看退出码）；现版协议里期望答案不进候选进程，提前退出=结果缺失=失败，判题故障单条掩码——故障样本零信号、不浪费其余 rollout（全故障组作废）。入池前读回核对断言和接受记录一一对应，出了错按 Task、Tests、GT、Verifier、Evaluation 五层归因。

| 判题故障为什么不能直接记 0？ | 0 会进入组内均值和标准差。三条错误回答各 0.1、一条故障记 0.0，三条错误回答的 advantage 都是 +0.5。应该先有限重试，仍失败就隔离；现版把这一组的 advantage 全设为 0，并输出故障统计 | [infra_policy.py](../verl/workers/reward_manager/infra_policy.py)，[主框架的实际奖励](RLVR工业流程.md#reward-mapping) |
| 怎样设计一个挡得住提前退出和伪造的判题协议？ | 判分方和执行方分开：期望答案不进候选进程，子进程只拿到调用，逐条报告输出，判分方比较；缺结果、缺完成事件都算失败。伪造「通过」也不知道正确答案。代价是要能把每条断言拆成调用和期望答案 | [protocol.py](../verl/utils/reward_score/coder1_plus/protocol.py)，[反向补充源码](examples/source-supplements/README.md) |
