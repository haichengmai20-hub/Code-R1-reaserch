## 第三段：模型输入构造——prompt 装什么（1.5 分钟）

```text
━━ ③A 模型输入构造（prompt = 模型唯一能看到的东西）━━━━━━━━━━━━━

  模型看到的完整 prompt：

  [system]
  You are a helpful programming assistant...
  ...enclosed within <think>...</think> and <answer>...</answer> tags.

  [user]
  Please solve the programming task below using a
  self-contained code snippet in a markdown code block.

  Given an integer array nums, find the subarray with     ← 描述（题面第一段）
  the largest sum, and return its sum.

  Please complete the following python code precisely:
  ```python
  class Solution:                                          ← 函数签名（来自 starter code）
      def maxSubArray(self, nums: List[int]) -> int:
  ```

  Explicit task constraints:                               ← 约束段（--append_constraints）
  - 1 <= nums.length <= 100000.                              从题面 Constraints 解析追加
  - -10000 <= nums[i] <= 10000.

  ─────────────────────────────────────────────────────

  三给三不给：
  ✅ 描述     ← 题面第一段（模型知道题意）
  ✅ 签名     ← starter code（模型知道接口契约：类名/方法名/参数类型）
  ✅ 约束     ← Constraints 解析（模型知道数值边界）
  ❌ 样例     ← 永不给！test=题面样例=判分依据，给了=递答案
  ❌ imports  ← 在 GT.prelude 里，模型看不到
  ❌ 辅助函数  ← 同上（ListNode/tree_node 等在 prelude，模型看不到）

  模型要生成什么：
  → 完整的 class Solution 实现（含签名重写+函数体逻辑）
```

**口述**：

> 先讲模型看到什么。两条消息：系统消息要求用 think 和 answer 标签；用户消息是描述加签名加约束。
>
> **核心决策是"三给三不给"**。给：描述、签名、约束——让模型知道题意、接口契约、数值边界。不给：**样例永远不给**——LeetCode 的 test 就是题面样例，1890 题每题断言数等于样例数。给了样例等于把判分答案明文递给模型，照抄三条输入输出就白拿满分。这是硬红线。
>
> 另外一样东西模型看不到但判分需要——**前缀 prelude**，包含 imports 和树/链辅助函数。121 道树/链题的测试要调前缀里的辅助函数，丢了前缀正确解也只拿 0.1。签名在 prompt 里给模型照着写，但前缀模型看不到——执行时判分器自动拼上。
>
> 一句话总结归属：**给模型看描述加签名加约束；模型不用管 imports 和辅助类；模型必须写完整的 Solution 实现。**

**过渡**：模型看到的是 prompt，判分器看到的是 GT——同一条数据行里完全不同的两个东西。下面讲 GT。

## 第四段：GT 构造——判分器用什么（1.5 分钟）

```text
━━ ③B GT 构造（GT = 判分器唯一消费的东西，模型看不到）━━━━━━━━━

  GT JSON 字符串，两个字段：

  {"prelude": "from typing import *          ← 运行环境
               from functools import *
               ...
               class ListNode:                ← 树/链辅助函数
                   def __init__(self, val=0, next=None):
               def list_node(values): ...
               def is_same_list(p1, p2): ...",

   "functional": "def check(candidate):       ← 考题（判分依据）
                    assert candidate(nums=[-2,1,-3,4,...]) == 6
                    assert candidate(nums=[1]) == 1
                    assert candidate(nums=[5,4,-1,7,8]) == 23

                check(Solution().maxSubArray)"} ← 调用入口

  ─────────────────────────────────────────────────────

  判分时拼成一个完整程序（自上而下执行）：

  ┌─────────────────────────────────────────┐
  │  prelude（环境）                         │ ← 定义 imports、ListNode、
  │                                         │    list_node、is_same_list
  │  模型代码（实现）                         │ ← class Solution: ...
  │                                         │    （从回答的围栏里提取的）
  │  functional（考题）                       │ ← def check(candidate): assert...
  │                                         │    check(Solution().maxSubArray)
  └─────────────────────────────────────────┘
         执行 → 断言逐条跑 → 退出码 → reward

  ─────────────────────────────────────────────────────

  TACO stdio 题的 GT（另一形态）：
  {"inputs": ["5", "100", "-3"],            ← 竞赛自带测试数据
   "outputs": ["10", "200", "-6"]}           ← 不需要构造 assert

  统一化改造：函数题 _deep_eq 收编进 prelude
            stdio 题走补强项 8 受保护协议
            → 判分器只认三件套、不感知来源

  ─────────────────────────────────────────────────────

  归属铁律：给模型看描述+签名+约束 | GT装环境+考题 | 模型必须写完整实现
```

**口述**：

> GT 是一个 JSON 字符串，两个字段。
>
> **prelude** 是运行环境——imports 头加树/链辅助函数。121 道树/链题靠它才能跑通，这是我发现并修复的第一个缺陷：原版 GT 只取测试不取前缀，正确解在 Code-R1 判分下必然 NameError 只拿 0.1。
>
> 补充一句怎么发现的——不是跑训练撞出来的，是读源码时把「测试里调用的函数名」和「判分时能拿到的定义」对了一遍，发现 121 道题的测试调用了只存在于原始前缀里的 `tree_node`、`is_same_tree`。然后挑一题做对照实跑：同一份正确参考解，Code-R1 拼法报 `NameError`、原生拼法通过，才确认。这 121 题占训练集 6.4%，等于格式信号把正确性信号整个盖掉了。
>
> **functional** 是考题——样例变成 assert 断言，最后拼上 `check(入口)` 调用。判分器把 prelude、模型代码、断言拼成一个程序跑：prelude 在前提供环境，模型代码在中提供实现，断言在后验证行为。
>
> 对 TACO 的 stdio 题，GT 形态不同——是输入字符串列表加期望输出列表，不需要构造 assert。因为竞赛就是交完整程序从 stdin 读从 stdout 写。我在做统一化：把 TACO 也收编到三件套契约，函数题的容差比较器收编进 prelude，stdio 题走受保护协议，最终判分器只认三件套、不感知来源。
>
> **归属铁律一句话**：给模型看"描述加签名加约束"；GT 装"环境加考题"；模型必须写完整实现。同一条数据，两个消费者，各取所需。

**追问补充（GT 出口自检，C2）**：判据只有一条——**参考解必须拿 1.1**。拿参考解当「最认真的回答」全量跑一遍，它拿不到满分就是环境坏了，与模型无关；BC-01 的 121 题就是这么暴露的。同一次全量扫描还捞出两件事：BC-04 的 14 题缺库（`ModuleNotFoundError`，与前缀缺失的 `NameError` 报错不同，30 秒能分开）；BC-03 的 `word-ladder-ii` 同解多 seed 时过时不过——参考解返回顺序随哈希种子变，测试却按列表顺序比，6 个 seed 只过 3 个，修法是 GT 加 `compare=unordered_outer`。

**追问补充（每题测试样例扩容放在哪）**：方案在 `设计定案表.md` D13（2026-11-09 收录《测试扩容方案_v1.md》）、D16 傻解法 oracle、D17 扩容工作流；实现落 `coder1_plus_tests.py`（变异审计）、`coder1_plus_oracles.py`（generate/validate/oracle 三件套）、`coder1_plus.py --augment_cases`（只追加 accepted 用例）；教学在 `01_数据理解与GT构建.md` 作业 1.2。现状**只有 7 题示范**（每题随机补 10 条 + 变异体引导补测），全量按 D13 阶段 A（7 题）→ B（100 题）→ C（分批）→ D（训练复审）铺开。

**过渡**：模型生成了回答之后，Verifier 怎么判分——这是我贡献最大的一块。

## 第五段：Verifier 七道门与五处修复（2 分钟）

```text
━━ ④ Verifier / 沙箱（七道门）━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  模型回答 → 门⓪ 路由（data_source=code_plus）
          → 门① 契约（GT 有 prelude？）
          → 门② 口径（CODER1_PLUS_REWARD?）
          → 门③ 格式/提取：
              strict   = <think>开头 + </answer>结尾 + 有围栏代码
              fallback = 标签不合格 → 退回整段抽全部围栏块照样执行
              none     = 抽不出围栏 → −0.1 不执行
          → 门④ 协议：
              断言拆「调用+期望」→ 期望物理不进候选进程
              子进程逐条执行调用 → 带 nonce 上报输出
          → 门⑤ 沙箱：
              firejail: nproc=32, nofile=32, fsize=2m,
                       as=4096m, timeout=30s, 禁网
          → 门⑥ 判定：
              逐条比较输出 vs 期望
              缺结果/报错/不符 → 失败
          → 门⑦ 性能轮（正确性通过后）：
              种子重建大输入 + 每题 time_limit_ms
              超时 → 0.9 性能瑕疵
              大输入答错 → 0.1 正确性失败
          → 档位合成

  ─────────────────────────────────────────────────────

  修五洞：
  ① 前缀缺失：121 题正确解 0.1 → prelude 修复 → 1.1
  ② sys.exit(0) 骗满分：退出码0≠断言跑完 → BaseException拦截+逐条上报 → 0.1
  ③ 格式倒挂：格式边际1.2 > 正确边际1.0 → 字典序四档 → 任何对答>任何错答
  ④ 故障回填0：0进组内均值→错答advantage变正 → 单条掩码(组内有效均值→advantage恰0)
  ⑤ 命名空间污染：模型写错ListNode覆盖环境 → exec后恢复保留名 → 环境优先

  最终档位：1.1 / 0.9(慢) / 0.7 / 0.1 / −0.1
```

**口述**：

> 一个回答从进判分器到变成 reward，过七道门。我发现了**五处真实缺陷**并全部修复。
>
> **第一，GT 不拼前缀**——121 道树/链题正确解必挂。修法是存进 GT 的 prelude 字段，执行时拼上。
>
> **第二，sys.exit(0) 骗满分**——判分器只看退出码，候选代码第二行退出、断言没执行也拿 1.1。更糟的是原版单测把 `early_exit` 的期望值写成了 1.1，等于测试把作弊固化成"正确"。修法是受保护协议：断言拆成「调用表达式 + 期望答案」，**期望答案物理不进候选进程**；子进程逐条调用、带 nonce 上报每条用例的输出；缺完成事件、缺某条结果、报错、不符都判失败；`except BaseException` 兜住 SystemExit。实测四种作弊样本——`sys.exit(0)` 1.1→0.1、`os._exit(0)` 1.1→0.1、伪造通过帧 0.1、读仓库数据文件 0.1——protected 口径全拦，参考解 1.1，正确解 7/7 三路径零误拒（LeetCode 53，2026-10-14）。
>
> **第三，格式边际倒挂**——原版格式边际 1.2 大于正确边际 1.0，整洁的错答压过不整洁的对答。修法是字典序四档：正确性 1.0 是主键，格式 ±0.1 是次键，任何对答严格高于任何错答。
>
> **第四，判题故障回填 0**——0 不是中性值：`[0.1,0.1,0.1,0.0]` 组内均值 0.075、样本标准差 0.05，advantage 变成 `[+0.5,+0.5,+0.5,−1.5]`，三条错答被放大成"比故障好"的正信号。换任何占位值都不行——记 0.2 时占位样本拿 +1.5，成了全组最强正信号。修法是单条掩码（D15，2026-11-09）：故障样本分数设为组内有效均值，`[1.1,0.1,0.1,故障]` 下掩码值 0.433 → advantage `[+1.41,−0.71,−0.71,恰好 0]`，不浪费其余 rollout；全故障组退回整组作废。代价是组内尺度被均匀放大 `sqrt((n−1)/(n−2))`，方向与排序不变。
>
> **第五，命名空间污染**——模型写错的 ListNode 覆盖环境定义，正确解被判 0.1。修法是 exec 后恢复环境保留名。
>
> 修复后档位 1.1 / 0.9 / 0.7 / 0.1 / 负 0.1。性能轮归因两分：超时是性能瑕疵 0.9，大输入答错是正确性失败 0.1——大输入是题意合法输入，答错就是错解。

**过渡**：reward 出来了，怎么变成参数更新。

## 第六段：GRPO 训练闭环 + 从纯 RL 到 SFT 冷启动的发现（1.5 分钟）

```text
━━ ⑤ GRPO ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
16题×16答 → uid → 组内标准化(±0.866)
→ PPO-clip + KL + 熵 → AdamW(lr 5e-7) → 新权重回 vLLM

推演发现：Base 起步的三层限制
① 前 64 步 80% 增益是格式（20% 预算学格式）
② 全错组 advantage=0 → 零梯度信号
③ Base 代码能力不足以在组内产生"好坏分化"

结论：Verifier 修复解决"信号不可信"
     但没解决"信号不存在"→ 需要 SFT 冷启动
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

对策：SFT → 课程学习 RL
┌─────────────────────────────────────────┐
│ SFT 冷启动（query→response，教格式+基本解题）│
│   LeetCode sft split 945 题 + doocs 参考解  │
│   → SFT 后简单题能做对 → 组内有正确回答      │
│   → 非零 advantage → 有效梯度              │
├─────────────────────────────────────────┤
│ RL 课程学习（按代码复杂度分档）              │
│   简单：单循环/基础结构 → 建立置信度         │
│   中等：DP/贪心/双指针 → 有效学习区间       │
│   困难：图论/高级DP → 挑战上限             │
│   晋升条件：上档 pass@k 达预注册阈值        │
└─────────────────────────────────────────┘
```

**口述**：

> GRPO 核心是不要 critic，用同题其他回答当基线。每步 16 题每题采 16 个回答，组内标准化得到 advantage。
>
> 做完推演后发现一个结构性问题：**从 Base 模型直接做纯 RL，无法稳定获得收益**。三层原因——第一，前 64 步八成增益是格式学习，等于 20% 预算花在教模型"怎么交卷"而不是"怎么解题"。第二，全错组没有梯度信号——16 个回答全错时组内标准差为零，advantage 全零，GRPO 完全学不到东西。第三，Base 的代码能力不足以在组内产生好坏分化，而 GRPO 恰恰需要这种分化来提供信号。
>
> **我的 Verifier 修复解决了"信号不可信"的问题，但没解决"信号不存在"**——后者不是判分器的 bug，是训练范式的结构性限制。对策是先 SFT 冷启动教会模型基本格式和解题模式——这样 RL 阶段组内至少有正确回答提供正向信号。然后 RL 阶段做课程学习，按代码复杂度从简单（单循环）到中等（DP 贪心）到困难（图论），每档的 pass@k 达到预注册阈值才晋升下一档。
>
> 推演数字：SFT+课程学习后贪心 pass@1 从 Base 的 38% 提到 63.5%，held-out 从 13.4% 到 31.7%——这是推演，GPU 没实跑。

**过渡**：训练完怎么证明有效——关键是指标怎么选。

## 第七段：评测体系（1 分钟）

```text
━━ ⑥ 评测 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  训练监控（不是效果评测！）：
  val/test_score = 贪心单回答 raw reward 均值
  ⚠️ 不是通过率！三条格式合格但全错 → 均值仍 0.1

  ─────────────────────────────────────────────────────

  独立效果指标：pass@k（按题记 (n,c)）
  公式：pass@k = 1 - C(n-c,k)/C(n,k)

  为什么用 pass@k 不用单次 pass@1：
  · 采样波动（3 seed 标准差 0.5-1.5 点）
  · pass@8 看出"会做但不稳"的题（Base 0.768→run-02 0.907）

  双口径：
  · 贪心 = 确定性锚点（跨 step 可比）
  · 采样 3 seed = 噪声尺度 + 真实能力分布

  ─────────────────────────────────────────────────────

  dev vs held-out：
  · dev 选 checkpoint → 偏乐观（选择偏差）
  · held-out 只评一次 → 无偏
  · 实测差距：dev +23.5 点 / held-out +11.3 点
    （三个原因：dev 测试弱 + 同源 + 格式增益在同源兑现最多）

  配对净胜 > 百分比相减：
  · 同一批题两版本逐题对分（赢/输/平）
  · 消掉题目难度混杂变量
  · run-02 vs run-01 在 dev 净胜 4 题（分不开）
    但 held-out 净胜 10 题（能分开）
```

**口述**：

> 训练中的验证指标是贪心单回答的 raw reward 均值——不是通过率。三条格式合格但全错的回答均值还是 0.1，这是常见误区。
>
> 独立效果指标用 **pass@k**。为什么不用单次 pass@1——采样有波动标准差 1 个点左右，单次分不清差异和运气。pass@8 还能看出"会做但一次不一定做对"的题。
>
> 贪心和采样**双口径**——贪心做确定性锚点，采样 3 个 seed 给噪声尺度。
>
> **dev 和 held-out 分开**——dev 选 checkpoint 所以偏乐观（选择偏差），held-out 只评一次无偏。实测 dev 加 23.5 个点但 held-out 只有 11.3——三个原因：dev 测试弱、和训练同源、格式增益在同源上兑现最多。
>
> **配对净胜比百分比相减可信**——同一批题两版本逐题对分，消掉了题目难度这个混杂变量。

**过渡**：如果效果不好，怎么定位是环境问题还是策略问题。

## 第八段：Bad Case 分层归因（1 分钟）

```text
━━ ⑦ bad case 分层归因（25 条登记）━━━━━━━━━━━━━━━━━━━━━━

  归因铁律：
  reward 异常 → 先拿参考解复现
              → 参考解同分 = 环境实锤（模型无关）
              → 才排除往策略查

  ─────────────────────────────────────────────────────

  25 条 BC 按发现时机逐条判定：

  ┌────────────────────────────────────────────┐
  │ 完全前移训练前（零 GPU）  20 条             │
  │ ├─ a·数据预检：参考解全量跑+契约对照     7条│
  │ ├─ b·verifier对抗：变异审计+mock注入    10条│
  │ └─ c·冒烟门控：配置核对                 3条│
  ├────────────────────────────────────────────┤
  │ 部分可前移（根因静态可推，影响需训练看） 3条│
  │ 口径/设计事实                        2条│
  │ 必须等训练                           0条│
  └────────────────────────────────────────────┘

  三层防线 = 三个检查点：
  C2 数据出口（参考解全量跑）→ C3 判分器出口（作弊解打自己）→ C4 配置出口（读源码核运行态）
  训练中曲线只做兜底告警 → 训练后只查策略层

  冒烟门控（D19）：
  escaped 率（满分回答在 held-out 审计输入上的失败比例）
  + 误杀率（正确解被拒，必须 0）
  达标才晋升正式训练
```

**口述**：

> 归因铁律：**reward 异常先拿参考解复现**——参考解同分即环境实锤，模型无关，才排除往策略查。
>
> 我登记了 25 条已知判分异常，按五层分类。逐条判定后发现：**20 条可以完全前移到训练前发现，零 GPU 成本；0 条必须等训练**——因为它们的根因全是"环境/数据/配置静态决定"，不是"模型行为涌现"。
>
> 最优策略三层防线：训练前做数据预检（参考解全量跑）、verifier 对抗审计（注入作弊解、错误辅助类、边界样本）、冒烟门控（escaped 率加误杀率达标才上正式训练）。训练中曲线降级为兜底告警，训练后归因只查"排除环境后剩下的策略层问题"。

## 收尾（15 秒）

```text
方法论总结：

  先给信息再罚不达标 · 正负对照双向验证（Polygon）
  离线固化保证判分标准不漂移
  bad case 发现前移到训练前（20/25 零 GPU）

  一句话：先证明信号可信，再谈优化
  —— 不管 reward 是学出来的(RLHF)、测出来的(RLVR)、
     还是追出来的(Agentic RL)，都是同一件事
```

**口述**：

> 总结方法论：**先给信息再罚不达标；正负对照双向验证；离线固化保证判分标准不漂移；bad case 发现前移到训练前。** 这套"先证明信号可信再谈优化"的方法论，不管 reward 是学出来的（RLHF）、测出来的（RLVR）还是追出来的（Agentic RL），都是同一件事。
