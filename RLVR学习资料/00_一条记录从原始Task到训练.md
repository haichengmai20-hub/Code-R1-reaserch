## 纵览：一步训练做什么，七站分在哪几篇

Code-R1 每一步训练做这些事：

- 取 16 道题，每题让模型写 16 个回答，逐个放进沙箱判分。
- 同一道题的 16 个分数互相比较，得到每个回答的相对分，也就是 advantage。
- 用相对分加权模型生成每个 token 的概率，反传并更新参数。
- 把新权重装回采样引擎，开始下一步。

本文把这一步拆成七站，用 LeetCode 53 这一条记录走完。每站进来什么、出去什么、在哪篇细学：

| 站 | 进来 | 出去 | 在哪篇细学 |
|---|---|---|---|
| ① 原始记录 | LeetCodeDataset v2 RL 第 143 行 | 14 个字段，真正进训练的只有题面、测试、入口、题号 | 01 |
| ② 训练样本行 | 原始记录 | parquet 一行：prompt、GT 字符串、extra_info | 01 |
| ③ 采样 | 16 道题的 prompt | 每题 16 个回答，同一道题共享一个 uid | 03 |
| ④ 判分 | 一个回答加 GT | reward：-1.1、0.1 或 1.1 | 02 |
| ⑤ advantage | 同 uid 的 16 个 reward | 组内标准化的相对分，铺到回答的每个 token | 03 |
| ⑥ loss 与更新 | advantage，加 old、ref、new 三份 logprob | PPO-clip loss，反传后 AdamW 更新参数 | 03 学机制，04 实跑 |

## 一张图记住全程

```text
① 原始记录（JSONL 一行）
        │  leetcode2k()：题面 + 系统提示 + 约束 → prompt；test + check(入口) → GT（JSON 字符串）
        ▼
② 训练样本行（parquet：prompt / reward_model.ground_truth / extra_info）
        │  RLHFDataset：套聊天模板 → token id，左填充到 2048
        ▼
③ 一步训练取 16 题，vLLM 给每题采 16 个回答（温度 1.0，最长 4096 token）
        │  这条记录的 16 个回答共享一个 uid
        ▼
④ 每个回答：格式检查 → 抽代码 → 拼上 GT → 沙箱执行 → reward ∈ {-1.1, 0.1, 1.1}（管理器异常回填 0.0）
        │
        ▼
⑤ reward 放在回答最后一个有效 token；同 uid 的 16 个回答做 (r - mean) / (std + 1e-6) → advantage，广播到该回答所有 token
        │
        ▼
⑥ 重算 old logprob、ref logprob（无梯度）；actor forward 得 new logprob（有梯度）
   ratio = exp(new - old)；PPO clip 0.2 + 0.001·low_var_KL − 0.001·entropy → loss → backward → AdamW（lr 5e-7）
        │
        ▼
⑦ 新权重同步进 vLLM → 下一步采样；每 16 步贪心验证；每 64 步保存 checkpoint
```

一句话版本：**题目和断言是数据，模型写代码是行为，沙箱跑断言是判卷，同题 16 份卷子互相比出相对分，相对分去加权模型自己生成每个 token 的概率，反传更新，再把新模型装回采样引擎。**

## 第 ① 站 原始记录：一行 JSONL 里有什么

这一行有 8 个顶层键，`meta` 里再有 7 个子字段。口述时先记 5 个：

| 字段 | 这条记录的真实内容（已截短） | 它是什么 |
|---|---|---|
| `task_id` | `maximum-subarray` | 题目身份 |
| `meta.query` | `Given an integer array nums, find the subarray with the largest sum, and return its sum.` + `Please complete the following python code precisely:` + 签名 `class Solution: def maxSubArray(self, nums: List[int]) -> int:` | **给模型看的题** |
| `entry_point` | `Solution().maxSubArray` | 判题时调用谁 |
| `test` | `def check(candidate):` 下 3 条 `assert candidate(nums=...) == 6 / 1 / 23` | **判题依据**，后面会变成 GT |
| `completion` | Kadane 算法的参考实现（7 行） | 参考解，**不参与判分** |

另外三个容易误会的字段：`prompt` 是一串 `from typing import *` 之类的 imports 前缀，树和链表题还带辅助函数定义，不是题目；`meta.question_title` 是完整题面——**它的第一段描述与 `meta.query` 一字不差**，多出来的是 Examples、Constraints 和 Follow-up：描述和签名取自 `meta.query`，**约束给了**（`--append_constraints` 从这里解析、`105`→`100000` 自动修复后追加进 prompt），**样例永不给**——它就是判分依据；`meta.response` 是一段历史模型回答，不是本轮 rollout。

**为什么这样取、该不该补：** 判分器根本不读题面，只认签名和测试；而 LeetCode 的 `test` 就是题面样例（1890 题断言数=样例数），**给样例等于把判分依据明文递给模型**，照抄三条输入输出即可白拿 1.1——原版只取 `meta.query` 是代码数据集惯例的继承，客观上堵住了这条路。代价是约束缺失造成语义歧义（第 ④ 站 `wrong_empty` 的坑）和 121 题前缀缺失。结论是三条边界：**描述给全、约束该给、样例永不给**，详见 [01 的 actor prompt](01_数据理解与GT构建.md#actor-prompt) 与[主框架的 Task 清洗](RLVR工业流程.md#task-preparation)。

三条断言的输入输出：`[-2,1,-3,4,-1,2,1,-5,4] → 6`、`[1] → 1`、`[5,4,-1,7,8] → 23`。注意它们的答案全是正数，这个事实在第 ④ 站会变成一个坑。

**口述：** 原始记录里「给模型看的题」和「判题用的断言」是两个字段，参考解只是旁证。给模型的是描述、签名和约束；样例永不给——它就是判分用的测试。真正进入训练的只有题面、测试和入口，外加用于去重的题号。

源码：读取方式见 `LeetCodeDataset/leetcote/data.py` 的 `read_jsonl()`。全部 14 个字段的含义见 [01 的 metadata 字段字典](01_数据理解与GT构建.md#metadata-fields)。

## 第 ② 站 变成训练样本行：`coder1_plus.py` 做了三件事

预处理器 `examples/data_preprocess/coder1_plus.py` 把这一行变成训练样本行（下面是真实产物的截短版）：

```json
{
  "data_source": "code_plus",
  "prompt": [
    {"role": "system", "content": "You are a helpful programming assistant. ... <think>...</think> and <answer>...</answer> ..."},
    {"role": "user",   "content": "Please solve the programming task below ... ```python\nclass Solution:\n    def maxSubArray(self, nums: List[int]) -> int:\n```\n\nExplicit task constraints:\n- 1 <= nums.length <= 100000.\n- -10000 <= nums[i] <= 10000."}
  ],
  "ability": "coding",
  "reward_model": {"style": "rule", "ground_truth": "{\"prelude\": \"from typing import * ...\", \"functional\": \"def check(candidate):\\n    assert candidate(nums = [-2,1,-3,4,-1,2,1,-5,4]) == 6\\n ...\\n\\ncheck(Solution().maxSubArray)\"}"},
  "extra_info": {"split": "train", "index": 142, "reference": "class Solution: ...", "prompt": "...", "dataset": "LeetCodeDataset",
                 "task_id": "maximum-subarray", "question_id": 53, "source_file": "...v2-rl-problems.jsonl", "source_line_1_based": 143,
                 "gt_contract": "prelude+solution+functional/v1", "test_version": "leetcode-examples", "added_case_ids": [],
                 "perf": {"spec": {"arg": "nums", "size": 100000, "seed": 20261107, "lo": -10000, "hi": 10000},
                          "entry": "Solution().maxSubArray", "time_limit_ms": 500, "expected": "2532688"}}
}
```

三件事：

1. **造 prompt**：系统提示要求 `<think>…</think><answer>…</answer>`；用户消息 = 固定一句话「用自包含代码块解题」+ `meta.query`（描述+签名）+ **约束段**（`--append_constraints` 从完整题面解析、`105`→`100000` 自动修复，1890 题成功 1846 题）。不拼 imports，模型必须自己写 `from typing import List`；**样例永不拼进 prompt——它就是判分依据**。边界与理由见[第 ① 站](#station-1)和 [01 的 actor prompt](01_数据理解与GT构建.md#actor-prompt)。
2. **造 GT**：GT 带 `prelude`（原始前缀，树/链表题的辅助函数在这里）+ `functional`（`test` 断言 + `check(入口)`），整体 `json.dumps` 成字符串放进 `reward_model.ground_truth`。GT 是「断言 + 调用入口」，不是参考代码。`data_source=code_plus` 让判分路由到补强判分器。
3. **记履历**：`extra_info` 存 12 个字段——原版 5 项（split、index、参考解、纯文本 prompt、来源名）加追溯 7 项（`task_id`、`question_id`、来源文件与行号、GT 契约版本、测试版本、追加用例清单），标定过的题再加 `perf`（每题时限等，见[第 ④ 站](#station-4)）。`index` 是过滤去重后的训练集位置，不是原文件行号。这正是「判分器一对多、题目特异性走数据字段」的活例子：GT 如此，每题时限也如此。生成链路：`coder1_plus_perf.py` 标定出 `perf-index.jsonl` → `coder1_plus.py --perf_index` 并进数据行。

同时做去重和划分：合并 v2 RL 与 v2 SFT，排除 v2 test 的 `question_id`，同 ID 只留第一次出现，得到 1890 道题；训练读 parquet 前注意目录名与脚本路径要对齐（见[bad case 库 BC-06](bad_case登记表.md#layer-data)）。

**口述：** 预处理把「题面+约束」交给 prompt、把「前缀+断言+入口」打包成 GT 字符串、把「参考解与全程追溯」放进履历；三者消费者不同，不能混用。

源码：`coder1_plus.py` 的 `build_row`/`build_ground_truth`；上游对照 `coder1.py:leetcode2k()` 的历史差异见[bad case 库](bad_case登记表.md)。数据准备流水线（取料、把关、封装三段）见 [01 的全景](01_数据理解与GT构建.md#pipeline-1)。

## 第 ③ 站 采样：这条记录在一步训练里变成 16 个回答

`main_grpo.sh` 的设定：每步取 `train_batch_size=16` 道题，vLLM 对每题生成 `rollout.n=16` 个回答，温度 1.0，回答最长 4096 token。一步共 256 个回答，这条记录贡献其中 16 个，它们共享同一个 `uid`。

进入模型前，`RLHFDataset` 把两条聊天消息套上 Qwen2.5 的 ChatML 模板，大致是：

```text
<|im_start|>system
You are a helpful programming assistant. ...<|im_end|>
<|im_start|>user
Please solve the programming task below ... class Solution: ...<|im_end|>
<|im_start|>assistant
```

模型从 `assistant` 之后开始生成。一个格式合格的回答长这样（课程演示用的固定候选，不是真实采样）：

```text
<think>Fixed teaching candidate; no model generation.</think><answer>```python
class Solution:
    def maxSubArray(self, nums):
        ...
```</answer>
```

采样后只保留 token 序列；回答是自然停止还是被 4096 截断，当前版本不单独记录，只能从有没有 EOS 推断。

**口述：** 一题多答是 GRPO 的前提；同题回答靠 `uid` 认亲，不靠在 batch 里的相邻位置，因为后面会按 token 数重排。

源码：`verl/trainer/ppo/ray_trainer.py` 的 `fit()`（`:914-942`：生成、分配 uid、`repeat(16)`、`_balance_batch`）；`verl/workers/rollout/vllm_rollout/vllm_rollout_spmd.py`。

## 第 ④ 站 判分：一个回答怎样变成 reward

`PrimeRewardManager`（现版 `prime_plus`：判题故障先重试、仍失败单条掩码）用线程池对 256 个回答逐个调用判分器，每个回答走四步：

| 步骤 | 做什么 | 失败时 |
|---|---|---|
| 1 格式检查 | strip 后必须以 `<think>` 开头、`</answer>` 结尾 | 无标签 → 退回整段、抽全部代码块拼接，格式记 −0.1 |
| 2 抽代码 | 先取最后一个 `<answer>` 内部、抽其中全部代码块拼接；无标签时退回整段照此抽全部块 | 抽不出任何围栏块 → none，直接 −0.1、不执行 |
| 3 拼程序 | `prelude + 候选代码 + 断言`（受保护协议：期望答案不进候选进程，子进程逐条上报） | |
| 4 沙箱执行 | 正确性轮：固定限额——30 秒、4 GB 内存、禁网；带 `perf` 字段的题通过后再跑性能轮：墙钟换成本题标定的 `time_limit_ms`（内存限额不变，空间只做护栏） | 见下表 |

**档位（字典序 + 瑕疵并罚）：正确性是主键，格式与性能是次键。**

| 档位 | 条件 |
|---:|---|
| 1.1 | 对 + 标签合格 +（有性能标定时）限时内跑完大输入 |
| 0.9 | 对，但有一项瑕疵：无严格标签，或性能轮超时 |
| 0.7 | 对，但两项瑕疵都有 |
| 0.1 | 错 + 标签合格（断言失败/报错/超时都是这档；含性能轮大输入上答错/崩溃——大输入是题意合法输入，答错即错解，2026-11-09 归因修正） |
| −0.1 | 错或无代码 + 无标签 |
| 0.0 | 管理器兜底：判题基础设施故障——不是成绩，正确处理是重试后单条掩码（全故障组作废） |

任何对答严格高于任何错答。性能轮只对正确性通过者加跑（错答不触发；无 `perf` 标定的题也不跑）——早期全错时性能轮自动不激活；每题 `time_limit_ms` 来自数据行字段（判分器是一对多的通用机器，题目特异性全在数据行），离线标定、同题各步不漂移。判题故障、提前退出骗分、格式边际倒挂等已知异常的识别方法见[bad case 库](bad_case登记表.md)。

课程有 6 个固定候选（`run_demo.py` 演示钉 legacy 口径与推演基线一致，映射到现版档位如下；课程的 GT 在 3 条 seed 之外补了 5 条诊断断言）：

| 候选 | 做了什么 | legacy 实测 | 现版档位 | 判分日志里的证据 |
|---|---|---:|---:|---|
| `reference` | 正确的 Kadane 写法 | 1.1 | 1.1 | `Test Execution Passed!` |
| `correct_prefix` | 正确的前缀和写法 | 1.1 | 1.1 | `Test Execution Passed!` |
| `wrong_empty` | 允许空子数组，全负数组返回 0 | 0.1 | 0.1 | `AssertionError: diag-all-negative`（输入 `[-3,-2,-5]`，期望 -2） |
| `wrong_sum` | 直接返回整个数组的和 | 0.1 | 0.1 | `AssertionError: seed-1`：应得 6，返回 1 |
| `bad_format` | 只给代码块（内容是**完全正确的参考解**），没有标签 | -1.1 | **0.9** | legacy：`Bad format detected!`；现版 fallback 抽出代码照样执行——对+无标签，补强项 9 的招牌案例 |
| `early_exit` | 代码第二行 `sys.exit(0)` | **1.1** | **0.1** | legacy：没有任何断言执行但退出码 0；现版受保护协议下结果缺失判失败——补强项 4 的招牌案例 |

两个值得口述的坑：

- **测试覆盖不足 → reward 假阳性（错赋）。** 错误模式：判分器本身没算错——是**测试没问到错解出错的场景**，语义错误的代码在没被覆盖的输入上恰好都对，于是错解拿 1.1。`wrong_empty`（允许空子数组，语义错）在 3 条 seed 上恰好全对，因为 seed 答案全是正数（6、1、23）、没覆盖全负输入；补上 `[-3,-2,-5] → -2` 才暴露。这是系统性的数据属性：1890 题的测试全是题面样例，中位数只有 2 条。补强版用独立 oracle 核对后给这道题补了 10 条测试（全负/单元素/零/边界），wrong_empty 才被判 0.1——修法是**扩测试覆盖**，不是改判分器。
- **退出码 0 不等于跑完了断言。** `early_exit` 在 `check()` 之前就退出，判分器只看到成功。要堵这个洞需要「测试完成证据」，不是换个沙箱就能解决。源码补强版的受保护判题协议已经堵上：期望答案不进候选进程，结果缺失就判失败。

**口述：** 判分 = 格式与提取（标签可 fallback、围栏硬性）+ prelude/候选/断言拼程序进沙箱 + 受保护协议逐条判定 + 性能轮加赛；0.1 不是通过；拿 1.1 还要问三句——断言真的跑完了吗、断言本身够不够、限时内跑完大输入了吗。

## 第 ⑤ 站 reward 变成 advantage：同题相比，再铺到每个 token

先放位置：每个回答的 reward 是一个标量，写在该回答**最后一个有效 token**上，其余位置为 0。用课程里的教学长度画一个回答（长度 7，最大长度 8）：

```text
token 位置        0    1    2    3    4    5    6    7
eos_mask          1    1    1    1    1    1    1    0
token_level_reward 0    0    0    0    0    0   1.1   0
```

再分组归一化。用 6 个候选里的 4 个算法候选 `reference`、`correct_prefix`、`wrong_empty`、`wrong_sum` 代替真实的 16 个回答：

```text
同 uid 的 reward      [1.1, 1.1, 0.1, 0.1]
均值                  0.6
样本标准差（除 N-1）  0.57735
advantage            [+0.866, +0.866, -0.866, -0.866]
```

然后把 +0.866 复制到第一个回答的全部 7 个有效 token 上，-0.866 复制到失败回答的全部 token 上。推理部分和代码部分拿到的是同一个数：这是粗粒度的 outcome 信号，不区分哪一步推理对了。

三个边界：

- 16 个回答全对或全错，std = 0，advantage 全 0，这题这一步没有相对信号（KL 和 entropy 项仍可能有梯度）。
- 一次基础设施异常回填 0.0 会改变全组：`[0.1,0.1,0.1,0.0]` → `[+0.5,+0.5,+0.5,-1.5]`，三个同样失败的回答突然得到正信号。现版奖励管理器先重试，仍失败就单条掩码：故障样本的分数设为组内有效均值，advantage 恰为 0，其余已判分的 rollout 照常提供信号（全故障组才整组作废）。
- 组内只有 1 个回答时，源码用 mean 0、std 1。

**口述：** GRPO 不要 critic，用同题其他回答当 baseline；reward 先放末 token，求和后按 uid 分组标准化，再广播到整个回答。

源码：`prime.py:144`（末 token 赋值）；`verl/trainer/ppo/core_algos.py` 的 `compute_grpo_outcome_advantage`（`:111-154`）；`ray_trainer.py:978-991`（`use_kl_loss=True` 时 `token_level_rewards = token_level_scores`，再算 advantage）。

## 第 ⑥ 站 loss 与更新：advantage 怎样变成参数变化

需要三份 logprob，都是「模型对自己已生成 token 的对数概率」：

| 名字 | 谁算 | 什么时候 | 有梯度吗 |
|---|---|---|---|
| old | 当前 actor，`eval()` + `no_grad` | 采样之后、更新之前重算，不用 vLLM 的值 | 否，常量 |
| ref | 冻结的参考模型（初始权重，bf16，CPU offload） | 同上 | 否，常量 |
| new | 当前 actor，`train()` | 更新时 forward | **是** |

每个有效 token 上：

```text
ratio = exp(new - old)
pg    = max( -A·ratio , -A·clip(ratio, 0.8, 1.2) )
loss  = mean_over_tokens(pg) - 0.001·entropy + 0.001·low_var_kl(new, ref)
```

然后 `loss.backward()`，`clip_grad_norm_(1.0)`，AdamW 以 lr 5e-7 走一步。判题程序不可微也没关系：梯度只经过「固定 advantage × 当前模型 logprob」这条路回到参数。

用 `mechanism_lab.py` 的两标量 toy 看方向：两个候选 token 的 logits `[0, ln3]`，概率 `[0.25, 0.75]`，模型生成了第二个，A = +0.5，old = new 所以 ratio = 1，loss = -0.5。对 logits 的梯度是 `[+0.125, -0.125]`，学习率 0.1 走一步后第二个 token 的概率从 0.75 升到 0.7547。把 A 改成负数，方向反过来。

两个常见误区：

- loss 数值等于 0 不代表没梯度；ratio = 1 时导数仍是 -A。
- clip 裁的是目标函数的有利方向，不是梯度范数；A>0 且 ratio>1.2 时这个 token 的 PG 梯度为 0。

在 `main_grpo.sh` 的配置下（`ppo_epochs=1`，每步每卡只有一个 mini-batch），更新用的权重就是算 old 的权重，ratio 基本恒为 1，clip 几乎不触发；这一点是源码推断，训练日志里的 `actor/pg_clipfrac` 可以验证。

**口述：** 固定 old、ref、advantage，只对 new 求导；PPO 的 ratio 和 clip 是为了复用旧样本时不走太远；KL 项把模型拴在参考模型附近。

源码：`verl/workers/actor/dp_actor.py` 的 `compute_log_prob`（`:168-224`，no_grad）与 `update_policy`（`:226-327`）；`core_algos.py` 的 `compute_policy_loss`（`:272-303`）、`kl_penalty`（`:351-383`）；`verl/workers/fsdp_workers.py:119-120`（mini-batch 按题数乘 16 再除以卡数）。

## 第 ⑦ 站 同步、验证、保存：训练「最后」留下什么

- **权重同步**：下一步生成前，sharding manager 取 actor 的 `state_dict()` 装进 vLLM（新版本走 `wake_up` + 加载权重，旧版本走 `sync_model_weights`），生成完再卸载。每次生成都同步一次，包括验证。
- **验证**：每 16 步跑一次 `_validate()`，对验证集每题**贪心生成 1 个回答**，用同一个判分器打分；`val/test_score/code` = 这些 reward 的均值。它是 raw reward 均值，不是通过率：三个格式合格但全错的回答平均也是 0.1。
- **保存**：每 64 步在 `models/code-r1-12k-grpo/global_step_N/` 写 actor 分片、optimizer、lr scheduler、RNG，以及 dataloader 状态 `data.pt`。训练结束时的「最后」就是最后一个 `global_step_N/actor`，可以用 `scripts/model_merger.py` 合并成 HF 格式。
- **日志**：wandb 里看 `critic/score/mean`（本步 reward 均值）、`actor/pg_loss`、`actor/kl_loss`、`actor/entropy_loss`、`response_length/mean`、`val/test_score/code`。

**口述：** 更新完要证明三件事分开成立：参数真的变了、下一轮采样用的是新参数、保存的状态能恢复；效果好不好另用固定协议评。

源码：`verl/workers/sharding_manager/fsdp_vllm.py` 的 `__enter__/__exit__`；`ray_trainer.py` 的 `_validate()`（`:609-690`）、`_save_checkpoint()`（`:759-790`）。

## 传统 CS 知识补充：数据与训练底座术语串讲

给不是传统 CS 科班的读者的背景补给：把本篇七站出现过的传统术语集中给一遍「定义 + 人话」，最后用一张图串回贯穿题 LeetCode 53。已熟的读者可跳过；判分与沙箱层的术语（子进程、退出码、沙箱、限额）在 [02 的补充章](02_Verifier与任务池验收.md#cs-2)详写，这里不重复；后续各篇遇到的新术语按同样格式补进各篇自己的补充章。

### 数据的形状（本节统一场景：食品厂质检包装线的单据）

| 术语 | 定义 | 人话 |
|---|---|---|
| JSON / JSONL | JSON 是用键值对与列表表示数据的文本格式；JSONL 是「一行一条 JSON」的变体 | 标准装箱单 vs 一摞独立小卡片：JSONL 每行自成一卡，坏一行不影响别的行。第 ① 站的原始数据集就是 JSONL |
| Parquet | 列式存储的表格文件格式，按列而不是按行组织数据 | 档案柜换了摆法：同一栏（字段）的全部值放一起。批量读少数几列快、省空间，但要用各自的加载器读，不能只改扩展名（详解见 [01 的补充章](01_数据理解与GT构建.md#cs-1)） |
| schema | 对数据形状的声明：有哪些字段、各是什么类型 | 装箱单的模板：先定栏目再填内容。第 ① 站「8 个顶层键、meta 里 7 个子字段」说的就是这条记录的 schema |
| 聊天模板 | 把对话角色与内容拼成模型约定输入格式的模板 | 信纸格式：抬头（system）、正文（user）各就各位，模型只认这种排版的信 |
| token / token id | 模型读写的最小文本单位；token id 是它在词表里的编号 | 模型的「字」和这个字的字典页码。第 ② 站套完模板后就是把文字换成页码 |
| 左填充（padding） | 把短序列前面补空位、对齐到统一长度 | 铅笔盒里短的铅笔前面垫海绵，盒盒等长好装箱。第 ② 站「左填充到 2048」 |
| ★uid | 一步训练里同题多答的批内分组身份 | 同一张考卷的 16 份答卷共用一个档案号——批卷时靠它认亲，不靠卷子摞在一起的顺序（第 ③ 站） |

### 训练的运行底座（本节统一场景：班次与存档）

| 术语 | 定义 | 人话 |
|---|---|---|
| 温度 | 采样时调节概率分布「陡峭程度」的参数：低温偏向高概率项，高温更平均 | 放飞程度旋钮：训练采样温度 1.0 是正常放飞；拧到 0 就只剩最有把握的一个答案（贪心） |
| 贪心 | 每步都选概率最高的输出（温度 0） | 标准答案模式：不许抖机灵。第 ⑦ 站每 16 步的验证就是贪心单回答 |
| checkpoint | 训练到某步保存的完整状态存档 | 班末存档柜：模型参数、优化器进度整箱封存，出了事故按存档回滚重开。第 ⑦ 站每 64 步存一次（存档里有什么、为什么要存随机数状态，见 [04 的补充章](04_真实训练与独立评测.md#cs-4)） |
| 前向 / 反传（forward / backward） | 前向=按当前参数算出输出；反传=从损失出发算出每个参数该改多少 | 先做题、后对答案改方法：forward 是照现在的思路做题，backward 是顺着错处把思路的每一步该改多少都标出来（第 ⑥ 站） |

## 60 秒口述版

一条 LeetCode 记录里，给模型的是描述、签名和约束（样例永不给——样例就是判分用的测试），三条断言打包成 GT 字符串，参考解只做旁证。训练每步取 16 题，vLLM 给每题采 16 个回答。每个回答先过格式门，再把代码和断言拼成一个程序丢进 firejail 跑，退出码 0 得 1.1，失败 0.1，格式错 -1.1。标量 reward 写在回答末 token，同题 16 个回答做均值方差标准化得到 advantage，广播到整个回答。然后固定 old 和 ref 的 logprob，用当前模型重新 forward 得 new logprob，算 ratio、PPO clip、加一点 KL 和熵，反传、AdamW 一步。新权重装回 vLLM 进入下一步；每 16 步贪心验证，每 64 步存 checkpoint。整个闭环里最脆弱的是判分：断言不够、退出码骗过判分器，都会把错误行为奖励进模型；补强版在同一闭环上加了字典序分档和性能轮。

## 面试追问六条

| 追问 | 一句话答 |
|---|---|
| GT 是参考代码吗 | 不是。GT 是 `check(candidate)` 断言加入口调用的 JSON 字符串；参考解在 `extra_info` 里，判分不读它 |
| 为什么失败是 0.1 不是 0 | 0.1 是格式分；格式错才是 -1.1；0.0 是管理器超时或异常的兜底值，三者含义不同 |
| 退出码 0 就是通过吗 | 不是。`sys.exit(0)` 在断言前退出也得 1.1；原始三条断言的答案全是正数，抓不住「允许空子数组」的错解 |
| 16 个回答怎么变成信号 | 同 uid 组内 (r − mean)/(std + 1e-6)，广播到回答所有 token；全同分组信号为 0 |
| 梯度从哪里来 | 不经过沙箱；固定 advantage 加权当前模型的 token logprob，反传到参数；old 和 ref 是无梯度常量 |
| `val/test_score/code` 是通过率吗 | 不是，是贪心单回答的 raw reward 均值，LeetCode 和 TACO 合在一起 |
