- 给模型看的 prompt。
- 给判分器用的 GT。

## 文字版导读：先把全篇顺一遍

第一次读，先把这一节读完，再按链接进细节；复习时只读这一节。

**第一节：先分清三个输入输出。** 同一道题里有三处输入和输出：

- 模型：输入是题目，输出是一段带代码的回答。
- 候选程序：输入是一个数组，比如 `[-3,-2,-5]`，输出是整数 -2。
- 判题程序：输入是候选代码和 GT，输出是执行状态和 reward。

测试里的 -2 是程序应该返回的值，不是让模型模仿的回复。这正是 RLVR 和 SFT 的根本区别：SFT 让模型学一份标准回复，RLVR 只检查模型写出的程序行为对不对。详见[三个输入输出](#prerequisites-1)。

**第二节：九步流水线。** 这是 01 的骨架。用 LeetCode 53 走一遍：

1. 收集：锁定 v2 RL 文件的第 143 行，记下来源文件、行号和 hash。
2. 抽取 metadata：先读数据里已有的字段，不让 LLM 去猜。Code-R1 只用了五个字段：题号、题面、测试、入口和参考解。
3. 规范化：不管来自哪个数据源，都写成同一种行，顶层固定五个字段。GT 里用一个键区分题型：函数题用 `functional`，标准输入输出题用 `inputs` 和 `outputs`，KodCode 用 `pytest`。
4. 校验：检查格式和对齐，比如能不能解析、入口在不在、测试是不是空的。Code-R1 处理 LeetCode 时几乎没做这一步。
5. 内部审查：拿手里已有的材料互相对照。比如用参考解跑测试、用暴力枚举对拍、看已知的错解能不能被测试抓住。
6. 外部审查：引入流水线之外的依据。比如对照官方题面、人工抽检、和评测集去重。Code-R1 基本没做。
7. 过滤：去掉坏题、跑不通的题、重复题和过长的 prompt。Code-R1 没有按难度过滤。
8. 封装写入：通过审查的测试加上调用入口，用 JSON 存成一个字符串，这就是 GT。再把它写成 parquet 里的一行。
9. 构造 actor prompt：只放题意、函数签名、约束和输出格式。

原版缺的几步，补强版补了相应的工具：内部审查有变异审计，以及用 oracle 核对后再补测试的工具；外部审查有评测集去重；过滤有按实测通过率筛题；封装写入多存一份运行前缀。

这一节要记住三个判断：

- **内部审查全部通过，也可能整体错得一致。** 如果参考解和测试出自同一个错误理解，互相对照是查不出来的，所以还需要外部审查。
- **01 里有一个实测发现。** LeetCode 训练题里有 121 道树和链表题，它们的测试要调用一些辅助函数，而这些函数只定义在原始数据的运行前缀里。Code-R1 拼接代码时不带这段前缀，所以这些题一定报错，正确答案也只拿 0.1。测试本身没错，出问题的是执行时的拼接方式。补强版把前缀存进 GT 的 `prelude` 字段，判分时按「前缀、候选代码、测试」的顺序执行，121 题全部从 0.1 变成 1.1。
- **测试够不够，不看条数，看能不能抓住确认过的错解。** Code-R1 的 1890 道 LeetCode 训练题，测试全是题面样例，中位数 2 条，最多 5 条。补强版的变异审计在 2014 道题的参考解上做了 17316 处小改动，样例测试抓住了 81%。抓住率高也不等于够：LeetCode 53 的 9 个变异体全被抓住，「允许空子数组」的错解照样拿 1.1；用独立 oracle 核对、补上 10 条测试后，它才降到 0.1。

出了错，看错在哪一层：

- 一条测试错了，只隔离这一条。
- 测试依赖的东西缺失，就修封装方式，或者把这批题隔离出去。补强版修的是封装方式。
- 题意或接口本身有冲突，才隔离整道题。

字段存在、JSON 能解析、hash 对得上，都只证明格式和对齐没问题，不证明答案正确。详见[全景](#pipeline-1)和[内部审查和外部审查怎么分](#internal-external-review)。

**第三节：metadata 字段字典。** 同一道题有三层表示。每层记住真正起作用的那几个字段就够了：

| 层 | 字段数 | 真正起作用的 |
|---|---|---|
| 原始记录 | 14 | 题面进 prompt；测试和入口进 GT；题号用来去重 |
| Code-R1 训练行 | 10 | `prompt` 决定模型看到什么；`data_source` 决定用哪个判分器；`ground_truth` 决定怎么判 |
| 演示扩展 | 20 | 回答四个问题：是哪道题、从哪来、用哪个版本的测试判、能不能进训练 |

最容易错的有三处：

- 原始数据里的 `prompt` 字段是一串 imports，不是题目。
- `meta.response` 是一段历史回答，不是这一轮采样的结果。
- `extra_info.index` 是去重以后的位置，不是原文件里的行号。

详见[字段字典](#metadata-fields)。

**第四节：actor prompt。** 模型最终看到两条消息：

- 系统消息要求它先在 think 标签里推理，再在 answer 标签里作答。
- 用户消息先是一句「用自包含的代码块解题」，后面接题面第一段、函数签名，再接自动解析追加的约束段；样例永不给（它就是判分依据）。

该放进 prompt 的是题意、签名、约束和输出格式。不能放的是测试里的期望值、参考解、历史回答和 metadata。

面试常问四个坑：

1. **格式要求直接决定能不能进入判分。** 回答去掉首尾空白后必须以 `<think>` 开头、以 `</answer>` 结尾。开头多一句寒暄会破坏 `</answer>` 收尾锚定——但不再一票否决：退回整段抽围栏块照样执行（fallback），只扣格式分；真正被硬挡在门外的是抽不出任何围栏代码块（none，−0.1 不执行）。
2. **「自包含」曾经有真实后果，现在被 prelude 缓和。** 上游 GT 不拼 imports 时，漏写 `from typing import List` 在 Python 3.12 报 NameError 只拿 0.1、3.14 却能通过——同一份代码的判分随解释器版本漂移，这正是环境噪声。现版 prelude 已含这些导入，漏写不再必然判错；这句 prompt 要求随之降格为建议（写了不冲突）。
3. **约束进 prompt，模型才知道要 O(n)。** 先给信息、再罚不达标——性能轮（补强项 10）的超时惩罚以此为合法性前提。
4. **样例不进 prompt。** LeetCode 的 test 就是题面样例，给了就能照抄期望值骗过判分；要更多测试靠独立 oracle 生成，不靠公开样例。

详见 [actor prompt](#actor-prompt)。

**第五节：三项作业。** 先分清两套工具。`run_demo.py` 是固定示范，只看不改。`practice.py` 是你的练习台，每次提交都会生成一个新目录，旧结果会保留。

- **1.1 清洗题目和 metadata。** 先跑示范的 prepare，对照原始记录和整理后的那一行。关键是先别看字段字典，自己写出「原字段、整理后的字段、谁来用它」三列，再对照字典修正。最后口答三道题。
- **1.2 逐条核对测试。** 先预测，再运行。
  - 先拿原始的 3 条 seed，预测接受、隔离、待审核各有几条，然后运行 check。
  - `prediction.json` 里的 `wrong_empty_reward` 先留空，02 跑 score 时再填。check 只看三个数量和 `why`。
  - 接着自己加一条正确的配对，再加一条故意配错的，观察错的那条被单独隔离、正确的那条留下。
  - 判定靠三条规则：小输入用完整枚举来核对；hash 只证明输入对得上；有限的对照只能覆盖对照过的范围。
- **1.3 追到 GT。** 先独立推出一个新输入的答案，再解码 GT，确认三件事：只有被接受的记录变成了 assert，编号一一对应，错的记录没有混进去。

**第六节：自测。** 学完做两件事：

- 脱稿讲一遍 01 的 [60 秒口述](#oral-1)。
- 从[面试深挖](#interview-1)表里随机挑一个追问，按四句来回答：机制是什么、这个版本怎么实现、一个反例、证据能证明到哪一步。

读完导读，按顺序读下面的概念四节，再从[作业 1.1](#assignment-1-1)开始动手。

## 先分清三个输入输出

同一道题里有三处「输入、输出」，最容易混：

| 谁在运行 | 输入 | 输出 |
|---|---|---|
| Actor 语言模型 | actor prompt：编程题与提交要求 | 一段回答，里面有候选代码 |
| 候选程序 | `nums=[-3,-2,-5]` | 整数 -2 |
| Verifier 判题程序 | 候选代码加 GT | 执行状态、判定和 reward |

测试里的 -2 是候选程序该返回的值，不是模型要模仿的回复。SFT 才让模型学一份目标回复；RLVR 只检查模型写出的程序行为对不对。

开始只需要会读 Python 的函数调用、列表与字典、`assert`、`json.loads/dumps`。JSONL 是一行一条 JSON，Parquet 是列式表格文件，两者要用各自的加载器读，不能只改扩展名。

**自测：** 不看表复述这三行，再解释为什么 -2 不是 SFT 的目标回复。若仍混淆，先读[主框架的贯穿题](RLVR工业流程.md#running-example)。

### 从网页到 Code-R1 三件套（六步解析的直白版）

网页上一道题有这些原料：**题面 HTML**（描述 / 样例 / 约束）、**starter code**（imports 头 + 函数签名）、题解（付费墙后）、题号与难度。

Code-R1 一条训练数据只要三样东西：

| 三件套 | 装什么 | 给谁用 |
|---|---|---|
| **prompt** | 固定话术 + 描述第一段 + 函数签名 + 约束段 | **模型**（照着写代码） |
| **GT**（`reward_model.ground_truth`） | `prelude`（imports 头 + 树/链辅助函数） + `functional`（样例变 assert + `check(入口)`） | **判分器**（拼成程序跑分） |
| **extra_info** | 参考解 `reference`、来源、契约/测试版本、`perf` 标定 | 人与工具（追溯）；**判分不读** |

网页原料的每一块去哪了（前 → 后）：

| 网页上的东西 | 怎么处理 | 变成 | 谁用 |
|---|---|---|---|
| 题面第一段描述 | HTML 去标签 → 取第一段 | prompt 的开头 | 模型 |
| Constraints 段 | 解析 + 修上标（`105`→`100000`） | prompt 的约束段 | 模型 |
| **样例 Input/Output** | 加 assert 壳 | **GT.functional 的断言（判分依据）** | 判分器 |
| starter 的 imports 头 | 原样保留 | **GT.prelude** | 判分器（执行前拼上） |
| starter 的函数签名 | 提取 | prompt 的签名 + **entry_point** | 模型照着写 / 判分器照着调 |
| 题解 | 与社区题解交叉核对 | `extra_info.reference` | 不参与判分 |
| 题号 / 难度 | 原样 | `meta` / `extra_info` | 追溯 |

三个必须记住的点：

1. **test 就是题面样例**——网页 Example 被包成 assert 直接当判分标准。所以**样例绝不能给模型**：给了等于把判分答案递过去。这也是为什么"样例永不给"是硬红线。
2. **prelude 来自 starter 的 imports 段**（含树/链辅助函数）——121 道题的正确解靠它才能跑通；丢了就是必挂（补强项 1 修复）。
3. **签名出现在两个地方**——prompt 里给模型照着写，`entry_point` 里给判分器照着调；两边对齐，模型的代码才能接进判分器。

一条数据的流向：

```text
网页（HTML 题面 + starter code）
   │ 六步解析
   ├─ 描述/签名/约束 ──→ prompt ────────────→ 模型生成回答
   ├─ 样例 ──加 assert 壳──→ GT.functional ──→ 判分器
   ├─ imports/辅助函数 ──→ GT.prelude ──────→ 判分器（执行时拼）
   └─ 题解 ──→ extra_info.reference ────────→ 只追溯，不判分
```

LeetCode 是本仓主线数据（贯穿题与全部教学例子都来自它）；TACO 的过滤与判定规则见本节末尾。

### 实测验证（2026-11-08，探针与快照见 [examples/upstream_probe/](examples/upstream_probe/upstream_probe.py)）

用 LeetCode 官网 GraphQL API（`POST https://leetcode.com/graphql`，`question(titleSlug:...)` 查询，经代理 + Referer/UA 头）真实抓取贯穿题并走六步：**questionId=53 / difficulty=Medium / content 为 HTML 且含 `10<sup>5</sup>` / starter code——四项与仓库一致；第 1 步朴素去标签产出的 `105` 与仓库 question_title 逐字相同（上标丢失成因闭环）；examples 三对全解析；entry_point 一致；描述与话术结构一致**。签名的差异（官网现为 `list[int]`、数据集冻结 `List[int]`）暴露了数据集的时间快照性。

### 爬虫工程四问：爬哪些、得到什么、怎么验收、怎么处理（2026-11-08 实测）

**① 爬哪些（遍历策略）**：入口是题目列表接口（GraphQL，现存 `problemsetQuestionListV2`——实测旧名 `problemsetQuestionList` 已下线，错误提示给出五个候选继任者）；按 `limit/skip` 分页遍历全量题目（约 3600+ 题），每页拿到 `{slug, 题号, 难度, isPaidOnly}`；**过滤 `isPaidOnly=true`**（订阅题的题面/题解拿不到）；再对每个 slug 调 `question(titleSlug:...)` 取详情（本仓探针实测通的那个查询）。

**② 得到什么（响应 → 数据集字段的映射）**：

| GraphQL 响应 | → 数据集字段 | 实测 |
|---|---|---|
| `questionId` | `meta.question_id` | ✓ 53 |
| `titleSlug` | `task_id`（URL slug） | ✓ |
| `difficulty` | `meta.difficulty` | ✓ Medium |
| `content`（HTML） | 第1步 → `meta.question_title` | ✓ 含 `<sup>` |
| `codeSnippets[lang=Python]` | 第3步 → 签名 / `entry_point` / `lang_code` | ✓ |
| content 内的 Example 段 | 第2步 → `examples` → `test` | ✓ 3 对 |
| （官网无来源） | `completion` / `meta.response` | ✗ 来自题解库与生成文本 |

**③ 怎么判断拿到的就是想要的（三层验收）**：
- **结构层**：字段存在性与类型断言——slug 非空、content 非空、存在 Python snippet；缺失即跳过或重试（不进库）。
- **内容层**：交叉源核对——与 doocs/leetcode 开源题解对照（上游 README 的做法）；解析完整性对账——HTML 里 Example 段的条数必须等于解析出的 `examples` 条数。
- **行为层（最强）**：抽参考解跑「examples 生成的 assert」——全过则题面↔样例↔参考解**三角自洽**；仓库 v2 test 参考 pass@1=0.995 正是这类验收的规模版。对账失败按层隔离：一条样例错只隔离该条，题面冲突隔离整题。

**④ 怎么处理（后处理管线）**：六步解析拼装（见上文）→ 清洗（上标丢失等转换缺陷在**消费端**做幂识别兼容，不改上游冻结文件）→ 划分（按 `question_id` 排序取大者作 test；训练/评测题号不相交）→ **冻结入库**（jsonl 固定版本——官网会改版，可复现性靠冻结不靠上游）。

### 爬虫实测结果（2026-11-08 v2，10 题全流程）

`crawler.py`（同目录）实现列表分页 → 逐题详情 → 六步解析 → 三层验收，首轮 10 题实测：

- **抓取**：10/10 免费题成功（断点续爬：二跑命中缓存零请求；限速 1s/请求）
- **解析**：结构断言 10/10、Example 条数对账 10/10、entry_point 10/10、可生成 test 10/10
- **题型**：value 9 / list 1 / tree 0
- **行为层验收（最强）**：用仓库参考解跑我们爬出的 test —— **3/3 PASS**，链表题生成的 `is_same_list(candidate(l1 = list_node([...]), ...), list_node([...]))` 与仓库 test **逐字一致**

**首轮抓到的两个真 bug（v1→v2 修复，正好是爬虫工程的典型坑）**：
1. **entry_point 误取注释**：链表题 starter 的注释块里有 `# def __init__(self, val=0, next=None)`，正则直接匹配到 `__init__`——修复：按行过滤注释后再找 `class Solution` 内的 def。
2. **链表/树返回值比较**：直接 `==` 比较 ListNode 对象永远不等——修复：检测 starter 里的 ListNode/TreeNode，参数用 `list_node`/`tree_node` 包装、比较用 `is_same_list`/`is_same_tree`，并在 prelude 补齐定义（与仓库原版前缀对齐）。
3. 附带的稳健化：多参数输入（`l1 = [...], l2 = [...]`）改按顶层逗号分割，不再依赖贪婪正则"碰巧"语法正确。

另发现**题面漂移**：two-sum 的官网现题面（"You are given an array..."）与仓库冻结版（"Given an array..."）不同——同题重抓 ≠ 同数据，进一步印证快照性。

### TACO 的获取与处理（源码：`coder1.py:taco()`）

**获取**：`datasets.load_dataset("likaixin/TACO-verified")["train"]`——HuggingFace 上已清洗的 TACO 版本，原版从 26K 中筛出约 10K 进入训练池。

**过滤**（在 `process_fn` 里逐条返回空占位即跳过）：
- 来源为 `geeksforgeeks` / `leetcode` 的整条跳过——前者题面质量参差，后者与 LeetCode 数据重复；
- 题面去掉非字母数字后不足 100 字符——太短，题意不全；
- 题面含 `image` 字样或 Markdown 图片——需要看图才能做，纯文本模型无法处理。

**按题型分支**（判据是 oracle 里有没有 `fn_name`，`:94`）：

| 题型 | 判据 | 比较方式 | 用例裁剪 |
|---|---|---|---|
| **函数题** | 有 `fn_name` | 生成 `_deep_eq(...)` 断言写进 GT（`fn_name` 按来源适配：leetcode/hackerrank 用 `o`，codewars 用 `o[0]`） | 不裁 |
| **stdio 题** | 有 `inputs`/`outputs` | 逐条喂 stdin、比较 stdout | `minimize_stdio` 裁到 ≤8 条 |

**函数题的通用比较器 `_deep_eq`**（`:102-108`）：所有函数题都用它，浮点只是其中一个分支——浮点走 `math.isclose(rel_tol=1e-5, abs_tol=1e-5)`，整数/字符串走 `==`，**容器递归**。容器递归是它最容易被忽略的设计，三个点各防一种真实失效：

| 设计 | 为什么 | 不这样会怎样（2026-11-08 实验对照） |
|---|---|---|
| `isinstance(a, (list, tuple))` 分派 + 递归 | 答案可能是矩阵/嵌套列表/混合结构，容差必须渗透到每个叶子 | 只比顶层：`[[1.0000001,2],[3,4]]` 与 `[[1.0,2],[3,4]]` 用 `==` 为 False、递归容差为 True |
| 先 `len(a) != len(b)` | `zip` 以短列表为准**静默截断** | `[1,2]` vs `[1,2,3]` 会误判相等（放行错解） |
| 逐元素 `_deep_eq(x,y)` | 把浮点/容器分派带到下一层 | 用 `==` 逐元素：`[1.0000001,2.0]` vs `[1.0,2.0]` 为 False，正确解被误杀 |

局限：自定义对象（ListNode/TreeNode）无解——`object() == object()` 恒 False，所以链表/树题必须用 `is_same_list`/`is_same_tree` 转成值比较（仓库链表题 GT 即如此）。

**stdio 题的 `minimize_stdio`**（`:27-47`）：→ 类型归一（行列表 join 成字符串）→ 丢 >4KB 的单条 → 按 `sys.getsizeof` 升序保留最小的 8 条。三个已知缺陷：`zip` 不等长静默截断；`stdout.replace("\r\n","\n")` **没有赋值回去**（CRLF 归一实际未生效）；`getsizeof` 含对象头开销，排序接近随机。

**血缘细节**：验证用 `solutions[-1]`、保存的 reference 是 `solutions[0]`——两者不是同一份程序（见[bad case 库 BC-05](bad_case登记表.md#layer-data)）。

### 真实难点（面试常问）

1. **GraphQL schema 会变**：探针两次 400 才试对字段（codeSnippets 无 `slug`、只有 `lang`/`code`）——上游 API 不是稳定契约，抓取代码要对着当时的 schema 写。
2. **反爬与网络**：需代理与请求头（Referer/User-Agent）；本题一次通过是幸存者偏差，大规模抓取会遇频控/Cloudflare。
3. **HTML 转换的选择即数据质量**：`<sup>` 的正确处理是转成 `^`，朴素去标签把 `10<sup>5</sup>` 变 `105`——**转换器的一个决定变成全库的永久缺陷**（下游只能做幂识别兼容，本仓 perf 解析即为此）。
4. **时间快照性**：官网 starter 已从 `List[int]` 改版为 `list[int]`，今天重抓同一题会得到不同签名；数据集的可复现性靠冻结的 jsonl 文件，不靠上游。
5. **Example 解析的鲁棒性**：本题 3 对 Input/Output 全中是因为它是简单题；多参数、矩阵、画图题的 Example 格式各异，解析器会碎。
6. **题解在付费墙后**：官方 solution 接口要登录/会员——`completion` 只能来自社区题解（doocs/leetcode 开源库）交叉核对，这正是上游 README 提到对照的由来。
7. **断言文本的格式漂移**：语义相同的 assert 文本格式因人而异（`nums = [...]` 的空格风格）——数据集内部一致性来自单一作者的单一管线，换人重做会引入文本级漂移（对判分无影响，对 diff/对账有）。


本仓数据链的源头 `LeetCodeDataset` 不是我们构建的；以下按证据强度分层重建它的获取方法（实锤来自其 README 与数据实测，推断已标注）：

- **来源与 schema（实锤）**：题目来自 LeetCode 官网——`task_id` 即官方 URL slug、`question_id` 官方题号、`difficulty` 官方分级；字段结构效仿 OpenAI HumanEval（README：Consistent with human-eval problem file format）。
- **各字段的产出方式（实锤+强推断）**：题面 HTML 转文本得 `question_title`（★上标 `<sup>` 在转换中丢失——字面 `105` 即 10^5 的成因，也是题面源自 HTML 的证据）；Example 段解析成 `examples`、再加 assert 壳得 `test`（README 的 Evaluation 节）；starter code 得签名与 `entry_point`；`meta.query` = 描述第一段 + 固定话术 + 签名的拼装物（`src` 字段存拼装前原文）；`completion` 参考解与 doocs/leetcode 题解交叉核对；`meta.response` 是讲解式"correct response"（SFT 教材，README：query→response 训 LLM）。
- **划分（实锤）**：v1 按 `question_id` 排序取大者作 test（1570/175）；v2 把同一题库按用途重划为 rl(945)/sft(945) 两个互不重复的 split，test(200) 与训练 `question_id` 不相交。
- **纯推断（无直接证据）**：抓取具体走官网 GraphQL API 还是 HTML 爬虫、response 是 LLM 生成还是题解改写——行文风格像 LLM 生成，未实锤。

## 全景：一条原始 Task 怎样变成数据集里的一行

本阶段讲工业数据准备的前半段：从原始题目，到训练数据集里的一行，再到模型最终看到的 actor prompt。先记下面九步，三项作业都落在其中几步上。

```text
1 收集原始 Task         LeetCodeDataset v2 的 JSONL；另有 TACO、KodCode 等来源
2 抽取 metadata         读已有字段，记来源文件、行号、版本
3 规范化到统一 schema    不同来源都写成同一种行：prompt / reward_model / extra_info
4 校验                  字段齐全、JSON 可解析、入口存在、测试非空、读回一致
5 内部审查              用手里已有的材料互相核：字段一致、依赖齐全、参考解跑测试、暴力对拍、错解能被抓
6 外部审查              引入流水线外的依据：官方题面与数据、人工抽检、评测集去污染、许可
7 过滤                  质量差、跑不通、重复、与评测集重叠、prompt 过长、太易或太难
8 封装 GT 并写入数据集    已接受的测试变成 GT 字符串，写成 parquet 的一行
9 构造 actor prompt     只给题意、签名、约束和输出格式；测试与答案藏起来
```

顺序表示依赖，不是严格串行：校验、内部审查、外部审查和过滤会交错、反复进行。构造 actor prompt 在代码里和规范化是同一个函数完成的，单列是因为它决定模型看到什么。这里的 1 到 9 是九步的编号；① 到 ⑦ 只用来指 00 的七站。

| 步骤 | 工业上要做到 | Code-R1 实际做了什么 | 本课演示补了什么 |
|---|---|---|---|
| 1 收集 | 记录来源、版本、许可 | 本地 v2 RL 与 v2 SFT 的 JSONL；TACO 从 Hugging Face 下载 | 锁定 v2 RL 第 143 行，记文件、行号、hash、commit |
| 2 抽取 metadata | 先读已有字段，缺的再用规则或 LLM 补，每个字段记来源 | 只取 `question_id`、`query`、`test`、`entry_point`、`completion` 五个字段 | 另存原难度、原划分、题号等 20 个扩展字段 |
| 3 规范化 schema | 异构来源统一成一种行，GT 用类型键区分 | 所有来源都写成 `data_source="code"` 的同形行，GT 有三种形状 | 同形行，外加 `case_index`、`test_version` |
| 4 校验 | schema、类型、可解析、入口、非空、读回 | LeetCode 分支只要求能解析、字段取得到，不检查内容 | hash、JSON 往返、读回比对；空 GT、重复 case_id 直接拒绝 |
| 5 内部审查 | 参考解跑测试、多解互证、依赖齐全、小输入暴力对拍、错解检出、题面质量 | TACO 用 `solutions[-1]` 跑测试，不过就删题；LeetCode 不执行，因此没发现下面的前缀依赖问题 | 每条测试做完整枚举、独立 Kadane、已审参考解三方核对；780 个小输入对拍；两个错解必须失败。源码补强版另有变异审计和用 oracle 核对的补测试工具 |
| 6 外部审查 | 对照官方题面与数据、人工抽检、对评测集去污染、许可合规 | 基本没有：不对照官方题面，不对 README 里的评测集 LCB、HumanEval+、MBPP+ 去污染。TACO 选了第三方发布的 `TACO-verified`，但仍自己执行一遍 | 约束按 LeetCode 官方题面补写，记录官方 URL；源码补强版有评测集去重工具，按题号和措辞重叠两种依据查 |
| 7 过滤 | 质量、执行、去重、train/eval 隔离、长度、难度 | TACO 去掉 geeksforgeeks 与 leetcode 来源、短题面、含图片的题、跑不通的题，标准输入输出题只留最短 8 条测试；LeetCode 按题号排除 v2 test 并去重；训练加载时 prompt 超过 2048 token 的题被丢掉；没有难度过滤 | 标 `split=diagnostic`、`train_ready=false`，不进训练；源码补强版有按实测通过率筛题的工具 |
| 8 封装写入 | GT 序列化、数据集版本化、manifest | `json.dumps` 生成 GT；逐条 map、合并、`shuffle(seed=666)`、写 parquet | 写 JSONL 并读回比对，不写 parquet；源码补强版把运行前缀也存进 GT |
| 9 actor prompt | 题意、签名、约束、输出格式；不含测试与答案 | 系统提示要求 think/answer，用户消息是一句要求加 `meta.query` | `--append_constraints` 解析 Constraints 追加（1890 题成功 1846），样例永不给 |

**口述：** 数据准备把一道原始题变成三样东西：给模型看的 prompt、给判分器用的 GT、给人追溯用的 metadata。校验、审查、过滤保证这三样各自可信。

<a id="schema-1"></a>

### 统一 schema 骨架

不管来源是 LeetCode、TACO 还是 KodCode，最后都写成同一种行。记住这个骨架就记住了规范化和封装写入两步：

```text
data_source    "code"                          判分路由键
prompt         [system 消息, user 消息]          给模型看的
ability        "coding"                        标签，训练不读
reward_model
  style        "rule"                          规则判分
  ground_truth JSON 字符串，三种形状之一：
               {"functional": "def check(candidate): ...  check(入口)"}   函数题：LeetCode、TACO 函数题
               {"inputs": [stdin, ...], "outputs": [stdout, ...]}       标准输入输出题：TACO
               {"pytest": "from solution import * ..."}                pytest 题：KodCode，未接入主脚本
extra_info     {split, index, reference, prompt, dataset}             履历，判分基本不读（原版 5 字段）
               补强版再存 task_id/question_id/来源行号/GT 契约版本/测试版本，
               标定过的题多一个 perf（每题 time_limit_ms 等，补强项 10）
```

<a id="internal-external-review"></a>

### 内部审查和外部审查怎么分

这两个词没有统一标准，本课这样用：

- **内部审查**只用流水线里已有的材料互相对照。例如签名和入口是否一致、测试依赖的东西判分时是否都在、参考解能否通过测试、两个独立实现在小输入上是否一致、已知错解能否被测试抓住。它查材料之间有没有矛盾。
- **外部审查**引入流水线之外的依据。例如对照官方题面补约束、人工专家抽检、和评测集做 n-gram 或语义去重、确认数据许可。它查材料和外部世界是否一致。

内部审查全过，也可能整体错得一致：参考解和测试来自同一个错误理解时，互相对照查不出来，只能靠外部依据。外部审查成本高，通常抽样做。

**一个真实的内部审查发现（2026-10-13）。** 把每道题 `test` 里调用的函数名，和判分时能拿到的定义对一遍，会发现：LeetCode 训练部分 1890 题里，有 121 道树和链表题的测试调用 `tree_node`、`list_node`、`is_same_tree`、`is_same_list`。这些辅助函数只定义在原始 `prompt` 前缀里。原生评测器先拼前缀，所以能跑；Code-R1 的 GT 只取 `test`，模型看到的题面也从不提这些函数。结果是这 121 题在 Code-R1 里拿不到 1.1：格式合格的回答不管对错都是 0.1，组内没有正确性信号，只剩格式信号，等于白白消耗采样。用其中一题做了对照：同一份正确参考解，按 Code-R1 的拼法运行报 `NameError: name 'is_same_tree' is not defined`，按原生拼法运行通过。验证集 v2 test 的 200 题没有这种依赖。

**已反向补充进源码（2026-10-14）。** 新增的补强版 `coder1_plus` 把原始前缀存进 GT 的 `prelude` 字段，判分时按「前缀、候选代码、测试」的顺序执行。原版的预处理和判分文件不改，判分路由里多了一个 `code_plus` 分支。同一批正确参考解重新判分，这 121 题全部从 0.1 变成 1.1。改法、代价和剩余问题见[反向补充源码](examples/source-supplements/README.md)。

README 说 LeetCode 的测试「generally reliable」。测试本身确实没错，错在执行契约换了：同一份测试离开它依赖的运行前缀，就变成了永远失败的 GT。

<a id="error-layers-1"></a>

### 出错时在哪一层处理

- 一条测试的 expected 错了：只隔离这一条，同输入的正确行保留。作业 1.2 练这个。
- 测试依赖缺失，例如上面的前缀辅助函数：修 GT 的封装方式，或者把这批题隔离，不能算模型做错。本课已在源码补强版里修了封装方式。
- 题意、接口或来源整体冲突：隔离整道题。
- 字段存在、JSON 能解析、hash 对得上：只证明格式和对齐，不证明答案正确。

## metadata 字段字典

同一道题在流水线里有三层表示。三张表用的都是最大子数组和这条记录的真实值。

### 第一层：原始记录，14 个字段

LeetCodeDataset v2 JSONL 的一行有 8 个顶层键，其中 `meta` 是个字典，里面再有 7 个子字段；把 `meta` 展开，共 14 个字段。

| 字段 | 这条记录的值 | 含义 | Code-R1 用不用 |
|---|---|---|---|
| `task_id` | `maximum-subarray` | 题目 slug，稳定身份 | 不用，也不保存。入池后只能靠 `index` 和 prompt 文本追溯回来 |
| `prompt` | `from typing import *` 等十几行 imports；树和链表题还带 `TreeNode`、`tree_node`、`is_same_tree` 等定义 | 原生评测器拼在代码前的运行前缀，不是题目 | 不用。模型代码要自己写 imports；依赖前缀辅助函数的 121 题因此跑不通 |
| `entry_point` | `Solution().maxSubArray` | 判题时调用谁 | 用，拼进 GT 的 `check(...)` |
| `test` | `def check(candidate):` 加 3 条 assert | 判题依据 | 用，是 GT 主体 |
| `completion` | Kadane 参考实现 | 参考解，不含 imports 前缀 | 存进 `extra_info.reference`，判分不读 |

| `src` | 与 `meta.query` 完全相同，945 题都是 | 来源题面文本 | 不用 |

<a id="actor-prompt"></a>

## actor prompt：模型最终看到什么

**先给结论：prompt 装三样——描述给全、约束给、样例永不给。** 描述与签名来自 `meta.query`；约束由 `--append_constraints` 从完整题面解析、规范化（`105`→`100000` 自动修复）后追加进 prompt——数值约束是语义消歧的真信息（`wrong_empty` 的「空子数组」歧义就是缺 `-10^4 ≤ x` 与非空约定所致），复杂度约束作采样提示；**样例永不给**（LeetCode 的 test 就是题面样例——给样例=把判分依据明文递给模型，照抄三条输入输出即可白拿 1.1）。判分器不读题面、只认签名和测试：签名锁接口、描述锁语义、约束锁边界、样例锁死不给。课程 `run_demo.py` 的 `ACTOR_PROMPT_APPEND` 是同一方案的示范：5 条约束 + 死守 GT/test/参考解不进 prompt。

### Code-R1 原版

系统消息：

```text
You are a helpful programming assistant. The user will ask you a question and you as the assistant solve it. The assistant first thinks how to solve the task through reasoning and then provides the user with the final answer. The reasoning process and answer are enclosed within <think>...</think> and <answer>...</answer> tags, respectively.
```

用户消息：

````text
Please solve the programming task below using a self-contained code snippet in a markdown code block.

Given an integer array nums, find the subarray with the largest sum, and return its sum.
 
Please complete the following python code precisely:
```python
class Solution:
    def maxSubArray(self, nums: List[int]) -> int:
```

Explicit task constraints:
- 1 <= nums.length <= 100000.
- -10000 <= nums[i] <= 10000.
````

数据加载器用模型自带的聊天模板把两条消息拼成一段文本。以 `main_grpo.sh` 用的 Qwen2.5 为例，格式如下，模型从最后一行之后开始生成：

````text
<|im_start|>system
You are a helpful programming assistant. ...<|im_end|>
<|im_start|>user
Please solve the programming task below using a self-contained code snippet in a markdown code block.

Given an integer array nums, ...
```python
class Solution:
    def maxSubArray(self, nums: List[int]) -> int:
```<|im_end|>
<|im_start|>assistant
````

这段按 Qwen2.5 模板格式写出，本机没有加载 tokenizer 实测。拼好后超过 `max_prompt_length=2048` 个 token 的题，在加载时就被丢掉。

### 本课演示版

在用户消息末尾追加一段约束与返回值说明，依据是官方题面：

```text
Explicit task constraints and return contract:
- nums is a non-empty List[int].
- 1 <= len(nums) <= 100000.
- For every element x in nums, -10000 <= x <= 10000.
- Return an int: the maximum sum of a non-empty contiguous subarray of nums.
- Empty subarrays are not allowed.
```

### 放什么，不放什么

| 放进 actor prompt | 不放进 actor prompt |
|---|---|
| 题意与函数签名 | **样例**（LeetCode 的 test 就是题面样例，给了即泄露判分依据——没有"公开样例可选"这回事，见坑 4） |
| 约束与返回值要求（`--append_constraints` 自动追加） | `test` 里的 assert 和 expected |
| 输出格式：think/answer 标签、markdown 代码块、自包含 | 参考解 `completion`、历史回答 `meta.response` |
| | 难度、题号、来源等 metadata |
| | imports 前缀——它在判分侧 GT 的 `prelude` 字段里，模型看不到 |

四个和 prompt 有关的坑，面试常问：

1. **格式要求直接连着判分门。** 判分器要求回答去掉首尾空白后以 `<think>` 开头、以 `</answer>` 结尾。聊天模板没有预填 `<think>`，模型开头多一句寒暄会破坏收尾锚定——现版下走 fallback（整段抽围栏照样执行）只扣格式分；硬挡的只有抽不出围栏（none，−0.1）。
2. **「自包含」曾把判分绑在解释器版本上。** 上游 GT 不拼 imports 时，漏写 `from typing import List` 在定义类时报 `NameError` 只拿 0.1；Python 3.14 注解延迟求值，同一份代码又通过了——判分结果随运行环境漂移是环境噪声。现版 prelude 把环境固定下来（含 imports），漏写不再必然判错。
3. **约束给了，规模惩罚才站得住。** 题面含 `1 <= n <= 10^5`，模型知道需要 O(n)。原则是**先给信息，再罚不达标**：prompt 没给约束却用大输入惩罚超时，就是题目没说清先算题目错；约束进了 prompt（`--append_constraints`），性能轮（补强项 10 的每题 timeout）的惩罚才合法——顺序不能反。
4. **样例永不给——本题没有「公开样例」这回事。** LeetCode 的 test 就是题面样例：本题 3 条 seed 与 3 个样例逐字相同，「公开样例」与「隐藏测试」在本数据下是同一份东西，给样例=把判分依据明文递给模型。（CodeContests 确有 public/private tests 之分、public 可给模型；本数据没有这层区分，不能套用。）要更多测试靠独立 oracle 生成，不靠公开样例。

**口述：** actor prompt 只回答「做什么、怎么交」：题意、签名、约束、输出格式。判分用的测试和答案必须藏起来，否则奖励可以被抄出来。


然后在自己的练习台上做，不改固定的示范输出：

1. 初始化练习，只含原始 3 条 seed。已经初始化过就跳过：

   ```bash
   $PY -B RLVR学习资料/examples/maximum-subarray/practice.py init --run data-01 --mode seed
   ```

2. 打开 `practice_runs/data-01/prediction.json`，预测 `accepted`、`quarantined`、`pending` 各几条，也就是接受、隔离、待审核，并在 `why` 里写理由。`check` 只看这三个数量和理由；`wrong_empty_reward` 留到 02 跑 `score` 时再填。然后检查：

   ```bash
   $PY -B RLVR学习资料/examples/maximum-subarray/practice.py check --run data-01
   ```

3. 在 `cases.json` 末尾追加一条自己选的小数组和手算的 expected，用新的 `case_id`；再追加一条同输入、故意配错 expected 的记录。更新预测后再次 `check`。

每次 `check` 都生成新的 `attempt-NNN/`，旧的预测和结果都保留。`origin` 可以写推导依据；`input_sha256` 可以不填，工具会算，填了就必须和输入一致。练习最多 64 条记录、每条最多 64 个元素；合法但更大的输入标为待审核 `pending`，不算非法。没有接受的记录时不生成 GT。新增的正确配对都会进 GT，不受示范「8 条」的限制。文件格式和退出码见[操作说明](examples/maximum-subarray/EXERCISES.md#data-exercise)。

**一条配对怎样判定：**

| 记录 | 判定依据 | 处理 |
|---|---|---|
| `[-3,-2,-5]` 配 -2 | 六个非空子数组的和是 `-3,-5,-10,-2,-7,-5`，最大 -2；完整枚举与已审实现一致 | 接受 |
| 同一输入配 6 | 6 是别的输入的结果；本输入独立算出来是 -2 | 只隔离这一行，正确行保留 |
| `[1]` 配 1、2 或 23 | 唯一的非空子数组和是 1；先记录冲突，再按输入重新求解 | 保留 1，配 2 和配 23 的两行分别隔离 |
| 空数组、字符串或 bool 元素、越界 10001 | 不满足题目的输入约束 | 隔离输入，不拿它指控候选算法 |

**三条证据规则：**

- 小输入用完整枚举：它直接对应题意，还能手算核查；参考实现结果一致是额外证据。两个相似程序或几次模型回答一致，不足以单独认证答案。
- hash 只证明输入对齐，不证明答案对：同一个输入配错 expected，hash 照样正确。
- 有限对照只覆盖对照过的范围：780 个小数组全对，不代表所有合法输入都对，更不代表性能达标。大输入要有可信的正式结果、已审的高效实现或充分的判定依据。

示范里原 3 条 seed 是从 assert 的语法树里提取的，再和同源的 `examples` 核对数量和内容；这是来源一致性检查，不是两份独立证据。重复的 `case_id`、hash 与输入不符、seed 与 examples 数量不等，都会在执行参考解之前报错。只错一条 expected 就定位这一条、升测试版本、重验受影响的 GT；题意、入口或来源整体冲突才隔离整题。

**交付：** 在 `notes.md` 里展示一条记录的输入、原 expected、你独立算的值、参考解的值和接受或隔离的理由，链接前后两次 attempt，说明同输入的正确行仍然保留。再分清四种情况：输入非法、答案配错、题目规格有问题、超出练习的计算预算。数量对上只是机械验收，手算有没有覆盖题意按[评分依据](examples/maximum-subarray/ANSWERS.md#data-rubric)核对。

**扩展：** 主框架 [A5 的错解表](RLVR工业流程.md#test-strength) 还列了「只返回最大元素」「前缀和漏掉空前缀」「O(n²) 暴力」三种错解，可以自己写出来，看哪条测试能抓住它们；随机与性能输入同样作为扩展。每个变异体先找合法反例确认它真的错；测试多不等于检出能力强，随意缩短超时也不构成算法反例。源码补强版已把这套逐条审核推广到一般函数题，并配了变异审计，见[反向补充源码](examples/source-supplements/README.md)。

## 作业 1.3：独立检查——从接受的测试追到 GT

**目的：** 在一个示范没展开过的输入上独立论证配对，再确认封装没有串位。对应九步里的封装写入，并复查 actor prompt。

先自己选一份合法的小数组，暂时不看参考输出：写出所有非空子数组的和、expected、为什么输入合法、答案从哪来，再用另一种方法核对。两边不一致时，写出该隔离哪条记录、下一步查什么。

然后检查你最新 attempt 里的 `prepared_task.json` 和 `data_pool.jsonl`：只有接受的记录会变成 `def check(candidate)` 里的 assert，每条 assert 带着自己的 `case_id`，最后调用 `check(Solution().maxSubArray)`，整体用 `json.dumps` 存进 `reward_model.ground_truth`。示范的 8 条只用来对照，验收看你自己这次接受了几条。

**操作：**

1. 解码自己的 GT，逐条核对 assert 的输入、expected、`case_id` 与 `extra_info.case_index` 一致；确认自己新增的正确输入真的出现了，坏行没有进去。
2. JSON 往返、JSONL 读回后，同一行没有变化；封装只改存储形式，不重新生成答案。
3. 看这次的测试能抓住哪些已确认的错解，解释抓不住的是哪种覆盖缺口；补上可信的全负输入后，`wrong_empty` 应该失败。空 GT、隔离行混进 GT 都会被拒绝。
4. 来源、用途、测试版本与原始 metadata 的对应都还在；actor prompt 里只有题目和约束。

**交付：** 一条独立输入的论证，加一条完整追踪：接受的记录、对应的 assert、GT 字符串、小池里的那一行。分开说明三件事：答案审核、封装回归、判分后端是否可信。`train_ready=false` 的原因是诊断用途、原判分器有提前退出的缺口、未知代码的执行环境没验收，不代表那 8 条答案错了。

**交接：** 阶段二继续用同一题、同一组测试和 GT。真要做训练或开发验证小池时，从现有来源抽少量完整任务，核对题面、接口和 seed；复用已审的测试和新增、修改 expected 的检查强度不同，不要求每个新任务都重写一套独立求解器。最终评测要留出没参与开发的题。多来源小池的准备见[训练准备](examples/training/README.md#pool-preparation)：它按源记录封装 train 和 dev，原始 seed 仍待逐题审核；不同题号、schema 能读回、`train_ready=false` 分别说明身份、接口和未完成的验收，不能互相替代。

## 传统 CS 知识补充：数据入库与判定的术语串讲

给不是传统 CS 科班的读者的背景补给：把本篇出现过的数据处理与判定术语集中给一遍「定义 + 人话」，统一用「图书馆编目入库」的场景——一条题目的原始记录要编目（schema）、查重（主键）、分库（split）、验真（断言），才能进训练库。格式与 [00 的补充章](00_一条记录从原始Task到训练.md#cs-00)一致，那里定义过的不再重复。

### 入库与查重（本节统一场景：图书馆编目）

| 术语 | 定义 | 人话 |
|---|---|---|
| 主键 / 去重 | 能唯一标识一条记录的字段；按它保留首次出现、丢弃后续重复 | 每本书的 ISBN：同号的书到货多次只入一本。本仓库用 `question_id` 当主键——v2 RL 与 v2 SFT 合并时同题只留第一份，1890 题就是这么来的 |
| split / 划分 | 把数据分成互不重叠的用途桶：train 训练、dev 调参、test 评测 | 一馆三室：阅览室（训练）、编目室（调参）、珍藏室（评测）各用各的书，**同一本书不能同时进两室** |
| ★数据泄漏 | 评测用的信息以任何形式参与过训练，评测分数因此虚高 | 珍藏室的书提前流进了阅览室：考卷混进了课本，分数再高也不算数。v2 训练集排除 v2 test 的 question_id、评测集再与 v1 test 去重（61 对同题号），都是在堵这个 |
| 脏数据 / 数据清洗 | 字段存在但内容有错（格式损坏、编码丢失、语义过时）；清洗=逐条核对修正 | 入库时书页粘连印错字：字段存在不等于内容已审核。消费端要么按官方原文核对补写，要么在解析层做兼容，不能靠全局替换去「修」 |
| 列式存储（接 00 的 parquet） | 按列组织：同一字段的全部值连在一起存 | 卡片柜按「书名抽屉、作者抽屉」分开摆：只要书名和年份两栏时，不用翻每张卡片，抽两个抽屉就走。代价是插入一整行要动所有抽屉，且 JSONL 与 parquet 各有加载器，**改文件名不能变格式** |

### 判定与验证（本节继续用编目的场景：验真）

| 术语 | 定义 | 人话 |
|---|---|---|
| assert（断言） | 程序里「声明必须为真」的语句：条件不成立立刻抛 `AssertionError`、进程以非 0 退出 | 验真盖章员：`assert candidate(nums=[...]) == 6` 就是「这份答卷在此题必须是 6」，不是就当场掀桌报警。GT 的 `check(candidate)` 全由它组成；报警后进程退出码非 0，正好接上[判分器的退出码判定](02_Verifier与任务池验收.md#cs-2) |
| ★浮点容差比较 | 计算机的小数有精度极限，判「相等」要给误差带：`abs(a-b) <= 1e-5` | 两把都有刻度误差的尺子比长度：差在头发丝内算相等。TACO 的 `_deep_eq` 用 1e-5 容差；Python 里 `0.1 + 0.2 == 0.3` 是 False，所以**永远不要用 `==` 判浮点相等** |
| 独立实现交叉验证 | 拿两份互相独立写出的实现对答案，不一致的条目隔离待审 | 两个编目员各自独立编同一批书，抄目对不上的一律挂起：补强项 3 的「独立 oracle 核对生成答案」就是这个思想，防一份实现错了全员跟着错 |
| 变异测试 | 对参考解做小的确定性改动造出已知错解，看测试能不能抓住；抓住率=测试强度 | 往书里故意印错几个字，看校对员（测试）能不能发现。补强项 2 的 17316 个变异体、样例测试只杀 81%——校对员漏了将近两成的错字 |

**断言（assert）展开讲**——GT 的每一分每一秒都在它身上，值得多花两分钟：

- **语法与行为**：`assert 条件` 声明「此刻必须为真」；不成立立刻抛 `AssertionError`，进程以退出码 1 结束。可带消息：`assert candidate(nums=[-3,-2,-5]) == -2, 'diag-all-negative'`——判分日志里看到的 `AssertionError: diag-all-negative` 的最后一段就是这条消息，它是**定位到「哪条用例挂了」的唯一线索**。
- **★首败即停**：一条断言炸了，它后面的断言**不再执行**。所以判分日志只能告诉你「第一条失败的用例」，不是全部失败清单——`wrong_sum` 死于 `seed-1`，它挂在后三条会怎样没人知道，也不需要知道（补强版受保护协议改成逐条上报，才能看到全部结论，见 [02 的执行边界](02_Verifier与任务池验收.md#execution-gaps-2)）。
- **assert 与 if…raise 的区别**：`if not cond: raise ValueError(...)` 是永远生效的业务校验；`assert` 是「自我检查」，**用 `python -O` 优化模式运行时会被整体跳过**（编译期剔除）。所以生产代码不该拿 assert 当输入校验。判分程序敢全靠 assert，是因为沙箱用固定参数起子进程（`-I -B`，从不开 `-O`），执行环境受控——**同一个写法换个运行环境，语义可能整个消失**，这是环境与代码互为前提的活例子。
- **与单元测试的关系**：一个测试函数的本体就是「准备输入 → 调用 → assert 预期」；GT 的 `check(candidate)` 就是一张只含断言的考卷。变异审计（补强项 2）测的是「这张考卷的断言够不够狠」。

### 一张图把术语串回贯穿题

```text

    |
    |  编目：读 schema → 主键 question_id 查重（同号只留第一份）

    v
leetcode2k() 产出 parquet 一行（列式入库）
    |  验真（判分时才发生）：
    |     GT 的三条 assert 盖章（不是 6/1/23 当场报警，退出码非 0）
    |     补强项 2：对参考解做变异测试，量出「校对员」的漏检率 81%
    |     补强项 3：独立 oracle 交叉验证，补进 accepted 的新用例
    v
```

## 60 秒口述

数据准备把一道原始题变成三样东西。给模型看的 prompt 是描述、签名（`meta.query`）加解析补进的约束。给判分器用的 GT 是 `test` 里的 assert 加上 `check(入口)`，用 `json.dumps` 存成字符串。给人追溯的 metadata 记来源、版本和用途。中间有四类把关：校验管格式和对齐；内部审查用手里的材料互相对照，比如参考解跑测试、暴力枚举对拍；外部审查拿官方题面、人工抽检和评测集来核；过滤去掉坏题、重复题和超长 prompt。Code-R1 原版在这一步留过三个坑：约束没进 prompt（现由 `--append_constraints` 补）；三条 seed 的答案全是正数，抓不住允许空子数组的错解；GT 不拼原始前缀，121 道树和链表题必然失败（已由补强版 prelude 修）。处理原则是哪层错修哪层：一条测试错只隔离这一条，题意冲突才隔离整题，测试改了就升版本。

| Code-R1 的 LeetCode 测试够吗？ | 不够。1890 题的测试全是题面样例，中位数 2 条、最多 5 条；答案经过交叉核对是对的，但覆盖很少，允许空子数组的错解也能拿满分。够不够不看条数，看能不能抓住确认过的错解：工业界用标好对错的提交衡量测试的准确率，再专门补边界、对抗和大规模输入。补强版的变异审计：2014 题、17316 个变异体，样例测试杀死 81%；但杀死率高不等于够，LeetCode 53 杀死 9/9 仍放过 wrong_empty，用 oracle 核对补 10 条后才抓住 | [主框架 A5](RLVR工业流程.md#test-strength)，[LeetCodeDataset README](../LeetCodeDataset/README.md)，[反向补充源码](examples/source-supplements/README.md) |
| 25 个 metadata 字段都要背吗？ | 不用。主线记四件事：身份、来源、用途、测试版本，其余按问题查。原版 `extra_info` 只有 5 个字段，演示扩展了 20 个。`prompt`、`index` 这类已有消费者的字段不能随意删 | [字段字典](#metadata-fields)，[scorer](../verl/utils/reward_score/coder1/__init__.py)，[RLHFDataset](../verl/utils/dataset/rl_dataset.py) |

不要把有限小域上的一致说成所有合法输入都正确。

## 本阶段完成记录

学完这一篇，应该能从原始 JSONL 说清四件事：题目让模型写什么、已有测试检查什么、答案为什么可信、GT 怎样进入判分器。

| 项目 | 完成证据 | 尚未完成时的处理 |
|---|---|---|
| 来源、字段和划分 | 自己写的字段表、版本、调用关系、交集统计及原因 | 补字段，或隔离冲突任务 |
| Tests 逐条审核 | 原配对、合法性、手算或独立计算、错行原因 | 候选结果待审；隔离错行，保留已接受记录 |
| GT 封装 | 编解码读回、入口核对、正负程序结果 | 修封装，或退回题意和测试检查 |

本阶段只用 CPU 和已检查过的小规模代码，不要求 GPU；未知的模型代码留给验收过的隔离环境执行。已有的可信结果可以直接复用，参考解和新输入可以交错审核。进入下一阶段时写清哪些已经接受、哪些仍待审核。
