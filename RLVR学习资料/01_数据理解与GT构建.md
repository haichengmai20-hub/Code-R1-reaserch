# 阶段一：从真实 Task 准备可解释的 Tests 与 GT

**资料导航：** [资料首页](README.md) · [工业主框架](RLVR工业流程.md) · **01 数据与 GT（当前）** · [02 Verifier 与任务池](02_Verifier与任务池验收.md) · [03 Rollout 与 GRPO](03_Rollout与GRPO机制.md) · [04 训练与评测](04_真实训练与独立评测.md)

**阶段位置：** 四个阶段中的第一阶段。先弄清题目、测试和判定依据，再进入评分与训练。

**本阶段学习内容：** 用真实 Hot 100「最大子数组和」整理 Task 与 metadata，逐条核对测试的 input/expected，再把接受的 Tests 封装为 Code-R1 的 GT。原始和入池记录是同一道题的不同表示；Oracle 只解释为求解或核对答案的方法。

**本阶段的产物：** 同一演示的 [原记录](examples/maximum-subarray/outputs/raw_task.json)、[逐条测试记录](examples/maximum-subarray/outputs/cases.json)、[整理后的 Task](examples/maximum-subarray/outputs/prepared_task.json)、[JSONL 小池](examples/maximum-subarray/outputs/data_pool.jsonl)与[报告](examples/maximum-subarray/outputs/report.json)。阶段二继续使用它们，不换一套未经说明的任务。JSONL 是教学 schema/读回示范；真实 trainer 仍需 Parquet 与路径适配。

**主框架：** 查[最小闭环与共同题目](RLVR工业流程.md#mvp-overview)、[Task 清洗](RLVR工业流程.md#task-preparation)、[逐条测试审核](RLVR工业流程.md#tests)和[GT 封装](RLVR工业流程.md#gt-packaging)。先跑一题完整示范，再改变一个条件，最后独立检查新输入。

文档职责分开：工业流程说明机制和规则，本文件组织这一阶段的项目阅读与作业。作业中的文件名是建议交付物，本次整理文档没有代替你完成这些作业。对仓库缺少的工业环节，先交付缺口与设计说明；不要求为证明学会而补建全部工业系统。

**先记机制：** 先固定题意与接口，再逐条判断输入合法、答案可信，最后保存为评分器消费的GT。metadata解释身份与履历；它不能替代答案证据。错一条配对就处理该条，Task本身有规格冲突才隔离整题。

## 前置自测与三个输入输出

能读Python函数调用、列表/字典、`assert`与`json.loads/dumps`即可开始。JSONL是一行一条JSON，Parquet是表格列式文件；两者需要各自加载器，不能只改扩展名。

| 当前是谁在运行 | 输入 | 输出 |
|---|---|---|
| Actor语言模型 | 编程题与提交要求 | 一段候选回答/代码 |
| 候选程序 | `nums=[-3,-2,-5]` | 整数-2 |
| Verifier | 候选代码与GT/执行规则 | 执行状态、判定与reward |

不看表复述这三行，再解释测试里的-2为什么不是SFT目标回复。若仍混淆，先读[主框架的贯穿题](RLVR工业流程.md#running-example)，再做1.1；不用先学全部RL理论。

## 学到什么才算完成

你应能从原始 JSONL 解释：题目让模型写什么、已有测试检查什么、答案为什么可信、GT 如何进入评分器。尤其要把三件事分开：某个字段已经存在、内容能够运行、内容有足够正确性证据。

Task 带题意、接口、Tests 和 metadata；测试里 input/expected 是程序调用与返回值，GT 是这些检查在评分接口中的表示。模型的输入是编程题目，输出是候选代码；测试的输入是 `nums`，输出是一个最大和整数。测试整数答案不是 SFT 的模型目标回复。

同一行 JSONL 有这些字段，只证明它们被存下，不证明已审核。metadata 记录来源/用途，不能代替答案证据；原始 `meta` 与整理后的 `extra_info` 不形成一种新 Task。

## 作业 1.1：完整示范——清洗 Task 与记录 metadata

**目的：** 从真实原记录追到整理后的同一任务，解释每个字段的来源和消费者。

在项目根目录执行：

```powershell
Set-Location -LiteralPath 'D:\RL及harness\code-r1'
python RLVR学习资料/examples/maximum-subarray/run_demo.py prepare
```

**操作：**

1. 记录两个本地仓库的 commit，查看 `raw_task.json` 的原始行、来源文件和 hash，定位 `maximum-subarray`、入口和 3 条 seed。
2. 核对非空连续子数组的题意、`maxSubArray(nums)` 签名、整数返回值、非空/范围约束和 Python 提交契约。原始 imports 前缀不是自然语言题目。
3. 对比 `meta.query` 与完整题面；补入已核对约束时记录适配，不全局替换转义或数字而改变原文语义。actor prompt 不包含隐藏 Tests 或参考答案。
4. 保留原 `meta.split=rl`、源文件和 revision；本课记录 `diagnostic` 用途。metadata 是身份/履历，不自动给答案认证。
5. 查 `leetcode2k()` 的 v2 RL/SFT 合并、v2 test ID 排除和首次 ID 保留。题面/接口不可解释的任务先隔离；一条测试错配在测试层处理。
6. 查看 `taco()` 的来源、过短/图片题面过滤和执行验证。完整语义去重/家族审查作为扩展，不要求先建设工业数据系统。

**交付与验收：** 一份阶段说明，给出 `原字段 → 整理后字段 → 消费者`，引用共同演示报告；分别解释题面、Tests/入口与 `extra_info`。可追溯原记录且读回一致；JSON 可解析只证明格式，不能单独证明答案正确。

**扩展保留：** 原五题的断言分布 `2/2/2/2/3`、v1/v2 交集和疑似同义题可继续查。已用于调试的题保留 diagnostic 用途，不能再当未见测试；不同 ID 只证明身份不同。题卡/schema/dedup/manifest 文件在全量审核需要时补充。

**检查是否学会：** 不看字段表，说明为何原 `prompt`、`meta.query`、`meta.response` 不能混用，metadata 的原始划分和本次用途有什么区别，再指出一个源码实际过滤条件与其覆盖范围。

## 作业 1.2：条件变化——逐条核对 input 与 expected

**目的：** 明确输入与答案如何取得，定位一条坏配对而不污染整题。

```powershell
python RLVR学习资料/examples/maximum-subarray/run_demo.py verify
```

上面是固定8/7示范。学生自己的变更使用下面这条路径，不修改固定 `outputs/`：

```powershell
python -B RLVR学习资料/examples/maximum-subarray/practice.py init --run data-01 --mode seed
```

从项目根打开 `RLVR学习资料/examples/maximum-subarray/practice_runs/data-01/cases.json` 与同目录 `prediction.json`。先只用3条seed，预测接受/隔离/待审核数量并写理由，再运行：

```powershell
python -B RLVR学习资料/examples/maximum-subarray/practice.py check --run data-01
```

随后在 `cases.json` 追加自己选的一份小数组及手算expected，使用新的case_id；再追加同输入的一条故意错配。更新预测后再check。输出进入新 `attempt-xxx/`，旧预测与结果保留；程序消费的是你编辑的配对，不重建8/7固定集。JSON记录可带 `origin` 说明推导位置，hash由工具计算；手填hash时必须与输入一致。

练习最多64条、每条最多64元素的穷举审核。合法大输入标pending、等待合适依据，不因超过教学预算就判题目非法。空GT拒绝；新增正确配对可进入GT，没有“必须恰好8条”的限制。详细文件格式、退出码见[操作说明](examples/maximum-subarray/EXERCISES.md#data-exercise)。

**示范的证据链：** 原 3 条 seed 从 assert AST 提取原子配对，并与同源 examples 核对数量及内容；这是来源一致性检查，不是两份独立正确性证据。新增合法小输入由人工/程序构造，期望值先按题意手算或完整枚举非空子数组，再与独立 Kadane 和已审 reference 对照。逐条记录实际结果，不靠异步返回顺序拼接输入和输出。

每条记录绑定 `case_id / input / expected / origin / input_sha256`，另存状态和核对依据。hash 用于识别输入，不证明 expected 正确；相同 input 配错 expected 仍可能有完全正确的 hash。

| 记录变化 | 判定依据与处理 |
|---|---|
| `[-3,-2,-5]` 配 -2 | 六个非空子数组和 `-3,-5,-10,-2,-7,-5`，最大 -2；完整枚举与已审实现一致后接受 |
| 同一输入配 6 | 6 是别的输入的结果；当前独立值是 -2，隔离该错行，保留正确行 |
| `[1]` 配 1、2 或 23 | 唯一非空子数组和为 1；记录冲突、重新求解，保留 1，分别隔离错行 |
| 空数组、字符串/bool 元素、越界 10001 | 不满足本任务的输入规则；隔离输入，不据此指控合法域中的候选算法 |

示范得到 8 条接受与 7 条隔离记录。CaseID 重复、input hash 与 input 不符、seed/examples 数量不等会在 reference 执行前失败。若问题属于题意/入口/来源整体冲突，再隔离 Task；若只错一条 expected，则定位该条、升测试版本并重验受影响 GT。不会只说“这题的 GT 不行”。

**怎样相信具体输出：** 对本课小输入，完整枚举全部非空连续子数组直接对应题意，可手算检查是否漏项。参考实现和独立方法一致是额外证据。两个相似程序或模型回答相同、结果在合理范围内，不足以单独认证；780 个长度 1—4、值域 -2—2 的有限对照也不证明全部合法输入或性能条件。大输入须另有可信正式结果、已审高效实现或充分判定依据。

**交付与验收：** 在 `data-01/notes.md` 展示一条input、原expected、独立计算值、reference值和接受/隔离原因，链接两次attempt；展示同输入正确行仍保留。区分输入非法、答案错配、Task规格问题与教学预算不足。自动数量检查通过只是机械验收，手算是否覆盖题意按[答案评分依据](examples/maximum-subarray/ANSWERS.md#data-rubric)核对。

**扩展保留：** 五题的独立求解器、多类随机/性能输入和错解矩阵移为扩展。每个变异体先找合法反例确认错误；测试数多不等于检出能力高，任意缩短超时不构成算法反例。

## 作业 1.3：独立检查——从接受的测试追到 GT

**目的：** 在一个未在示范表中展开的输入上独立论证配对，再检查封装没有串位。

自行选择一份合法小数组，暂不看参考输出，写出所有非空子数组和、expected、输入合法性和答案来源；再用独立方法核对。若分歧，指出应隔离哪条记录及继续查什么。这个练习检验迁移，不要求再造一个通用 Oracle 系统。

随后检查你的最新attempt里的 `prepared_task.json` 与 `data_pool.jsonl`：只有accepted Case进入 `def check(candidate)`，以各自input/expected形成assert；断言消息保留case_id，最终调用 `check(Solution().maxSubArray)`，再用 `json.dumps` 放到 `reward_model.ground_truth`。固定示范的8条仅用于对照，验收你的实际接受数量。

**操作：**

1. 解码自己的GT，核对每个assert的输入、expected和case_id，与 `extra_info.case_index` 逐项一致；确认自己新增的正确输入真的出现，坏行没有进入。
2. JSON 往返和 JSONL 读回确认同一 Task 未被改变；封装不重新生成答案。
3. 观察本次Tests检出哪些已确认错误程序，解释未检出的覆盖缺口；补入可信全负输入后再要求wrong_empty失败。固定示范有两个错解失败及GT变异回归；它们不替代你这次实际测试。空GT、隔离行进入GT均被拒绝。
4. 保留来源、用途、测试版本与原 metadata 的对应，检查 actor prompt 只有题目与约束。

**交付与验收：** 一条独立输入的论证，以及 `接受 Case → assert → GT → 小池记录` 的具体追踪。数据答案审核、装配回归和评分后端可信分别解释。当前 `train_ready=false` 的原因是诊断用途、原 scorer 已知绕过与未知代码环境未验收，不表示 8 条已接受的答案错了。

**交接：** 阶段二继续用同一 Task/Tests/GT。真正需要训练/开发验证小池时，从既有来源抽取少量完整任务并核对题面、接口和 seed；复用已审测试与修改/新增 expected 的检查强度不同，不要求每个新任务重写五种求解器。最终评测保留未参与开发的题目边界。

可运行的不同来源小池准备见[训练准备](examples/training/README.md#pool-preparation)。它按源记录封装train/dev，原始seed仍待逐题审核；distinct IDs、schema读回和 `train_ready=false` 分别说明身份、接口与未完成的验收，不互相替代。

| Tests 逐条审核 | 原配对、合法性、手算/独立计算和错行原因 | 候选结果待审；隔离错行，保留已接受记录 |
| GT 封装 | 编解码读回、入口核对、正负程序结果 | 修封装或退回题意/测试检查 |

本阶段主要使用 CPU 和已经检查过的小规模代码，不要求 GPU。对未知模型候选的执行留给验收过的隔离环境。已有可信结果可以先复用，Ref Code 与新输入可以交错审核；正式进入下一阶段时，交付物应明确哪些已经接受、哪些仍待审核。
