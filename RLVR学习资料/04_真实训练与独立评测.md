# 阶段四：沿工业框架学习 Code-R1 的真实训练与独立评测

**资料导航：** [资料首页](README.md) · [工业主框架](RLVR工业流程.md) · [01 数据与 GT](01_数据理解与GT构建.md) · [02 Verifier 与任务池](02_Verifier与任务池验收.md) · [03 Rollout 与 GRPO](03_Rollout与GRPO机制.md) · **04 训练与评测（当前）**

**阶段位置：** 四个阶段中的第四阶段。

**本阶段学习内容：** 先锁资源与评测协议、建立 baseline，再按资源完成真实 Actor Update、Weight Sync 与保存恢复，最后做独立评测与故障归因。CPU 固定候选可先完成指标和判定机制；GPU 训练另以实际运行证据验收。

**主框架：** 从[最小闭环](RLVR工业流程.md#mvp-overview)进入[策略更新](RLVR工业流程.md#policy-update)、[评测](RLVR工业流程.md#evaluation)与[故障归因](RLVR工业流程.md#layer-attribution)。框架决定要回答的问题，源码和运行记录决定结论强度；可靠工程扩展按需要补充，不要求先补齐工业系统。

**输入：** 同一个最大子数组和 Task、Tests（源码 GT 字段）、候选代码与已检查的 Verifier，以及第三阶段的 reward/advantage/logprob 合同。版本、划分和运行配置是 Task 与实验的属性。**输出：** 一份阶段说明与同一演示报告；有资源实跑时，再补 baseline、真实更新/同步/恢复与固定协议评测证据。

最终测试边界在第一阶段规划，本阶段在训练前锁定。已用于修改 Task、prompt、Tests 或选择方案的题与样例保留开发用途；新增最大子数组和反例验证覆盖，不代表未见题泛化。正确 GT 也不单独证明 scorer 可信。

**先记机制：** 参数变化证明发生了更新，下一轮引擎使用这些参数证明同步，恢复状态证明续训链；固定独立协议才用于判断效果。它们需要不同证据。CPU课程先验收你能否独立贯通与归因，真实运行和能力提升按实际证据分别记录。

## 学到什么才算完成

CPU 主线要求能解释指标的分母、训练 reward 与正确性通过的区别，能独立判断应修 Task、Tests、Verifier、环境还是模型。有资源完成真实训练时，还须证明参数更新发生、下一轮 rollout 使用更新后的参数，并核验保存与恢复。

配置表示运行意图；源码表示实现；日志、checkpoint、候选和结果关联起来才证明实际运行。单步跑通证明闭环可运行，不证明泛化提升；固定候选的 pass@k 只演示算法，不能写成实际 policy 性能。本阶段不默认购买算力或改动现有训练代码。

### 三个必须先核对的评测口径

1. 本版本 `RayPPOTrainer._validate()` 设置 `do_sample=False`；vLLM 对应分支设 `temperature=0`、`n=1`。它是每个 Task 一条贪心回答的训练中验证，不能直接作为独立多候选 pass@k 实验。
2. `val/test_score/{data_source}` 对逐条 token reward 求和后取 `np.mean`，是 raw reward 均值。本预处理器将 LeetCode/TACO 均记为 `data_source="code"`，所以 `val/test_score/code` 会合并这些来源；它既不是 LeetCode 独立通过率，也不是二值 accuracy。比如三条格式合格回答全测试失败仍可得到均值 0.1。
3. 原生 `eval_lct` 经 `evaluate(version, split)` 调用 `get_problem_file()`，按 release 的完整 problem_file 读取 Tests，并断言完整题库都被尝试。它不读取我们的 Parquet 或包装 GT，也不接混合 TACO 小池。将当前扩充 GT 的候选直接喂该 CLI，会回到旧 release 的 Tests/题集口径，不能用来验证这次新增 Tests。

**当前小池的做法：** 使用当前 Task 的 `ground_truth` 与原 scorer 完成判定，额外保存“Tests 是否完整执行、是否通过、格式/运行/infra 状态”；按 task_id 统计 `(n,c)`，只复用原生 `estimate_pass_at_k()` 的公式做聚合。CPU 演示以标准库计算同一公式，不导入原 CLI 的题库与执行器。`c` 由可信的实际正确性状态确定，不能只用 `reward>0`，也不能仅用 `reward==1.1`：报告的 `early_exit` 得 1.1，但 `audit_completed_case_count=0`、`correctness_pass=false`。教学 `data_pool.jsonl` 不是 trainer 输入的 Parquet；实际训练前须转换并核对路径和 schema。

## 作业 4.1：先锁协议，再分别记录 CPU 演示与真实 baseline

**目的：** 训练前建立可比较的参照，避免结果出来后挑有利题集或删失败。

**完整示范：** 在 `D:/RL及harness/code-r1` 执行：

```powershell
python .\RLVR学习资料\examples\maximum-subarray\run_demo.py evaluate
```

查看同一 [report.json](examples/maximum-subarray/outputs/report.json) 的正常组：最大子数组和 4 个固定候选中 2 个正确，`n=4,c=2`。公式为：

$$
\widehat{\mathrm{pass}}@k = 1-\frac{\binom{n-c}{k}}{\binom{n}{k}}.
$$

得 pass@1=1/2、pass@2=5/6、pass@4=1。只有所有纳入的 Task 都有 `n>=k` 时才报告该 k。报告另列包括 `bad_format`、`early_exit` 的全部六个固定候选：`n=6,c=2`，pass@1=1/3。四个算法候选是预选的教学组；真实模型生成时不能仿照这个分组把格式失败排除。这里没有模型推理，因此数字证明指标聚合正常，不是 baseline checkpoint 的成绩。

**协议与资源检查：**

1. 沿第一阶段划分确认训练、诊断、开发验证与最终测试用途，检查同题跨版本和疑似家族泄漏。学习演示的 `diagnostic`、`train_ready=false` 表示实际判题/训练环境尚未验收，不表示已接受的 Tests 答案错误；单条错误测试隔离后，其余合格 Tests 仍可用于诊断。
2. 第三阶段已在真实 rollout 前明确模型、Linux backend 和预算；这里确认是否足够支持 baseline 加最小更新。固定 checkpoint、tokenizer、Task/Tests、Verifier/runtime、温度、seed、每题候选数、token 上限及停止条件。没有 GPU 时保留“真实 baseline/训练待实跑”，不补造数字。
3. 在生成前写清所有分母与 infra 政策。格式失败、空回答、提取失败、逻辑错误、超时且确认属于候选问题等都属于策略失败，占生成候选分母。infra 另报数量、重试与成本，按预先登记的重试/停跑/不可比较规则处置，不能后验删除失败提高 pass@k。
4. 环境可用且已验收后，对 baseline 真正生成并用当前 GT 判定。保存逐题 `(n,c)` 与结果、配置和成本；最终测试锁定后不参与调试、调参或修复选择，日常回归使用开发验证集。

**一条件变化：** 只改变每题候选数：A 题 1/1、B 题 0/9。按题平均 pass@1 为 1/2，全部候选成功率为 1/10。解释两者用途与为何不能互换；再说明若只生成 1 个候选，为什么不能报告 pass@4。

**交付与验收：** 一份阶段说明与同一 demo 报告；有实际推理时补 baseline 逐题记录和完整协议。pass@k 是同题选 k 个候选至少一个通过的估计，不是 k 条 test case 的通过比例。独立检查时自行改变一组 `(n,c,k)` 重新计算，并指出复现数字所需字段；不要把给定的 `n=4,c=2` 原样抄为独立验证。训练中看过的 v2 Task 不能用于未见 v1 性能证明。

## 作业 4.2：完成项目最小真实更新、同步与恢复

**目的：** 有实际资源后，把第三阶段机制落实到 Code-R1 参数更新；没有资源时先完成源码追踪与运行准备，真实更新明确待实跑。

**操作：**

1. 用已选择的模型与资源制定小配置，核对数据路径、GPU/batch 关系、生成长度、判题并发、保存频率和退出条件，保留配置快照；不照抄原作者硬件设置。先完成 baseline，再更新。
2. 从一个批次追到真实生成、当前 GT 判定、advantage 与 actor update，关联 run_id、step、candidate/reward 记录及前后 checkpoint。`update_actor()` 进入 `DataParallelPPOActor.update_policy()` 的 forward/backward/optimizer 路径，但调用或 loss 数字不能单独证明实际参数变化。
3. 追下一次 `generate_sequences()`：worker 进入 sharding manager，`__enter__()` 取 actor `state_dict()`，按 vLLM 版本走 `sync_model_weights()` 或 wake_up/加载权重分支；`__exit__()` 再卸载或 sleep。实际同步内容与 policy 版本须核对，不能仅凭函数名和注释宣称使用了新参数。
4. 保存并恢复一次，核对 checkpoint、global step、优化器/随机数/dataloader 等实际保存的关键状态，以及固定开发验证的执行结果。哪些状态有保存由源码与产物决定，不能预先保证完整位级复现。
5. 先验收单步闭环，再决定是否扩大。测量耗时、显存/内存、token 和执行成本；规划估算与实测分开。

操作桥接见[训练准备与具体Linux命令](examples/training/README.md)。标准库命令已经能导出6条不同来源记录的JSONL、来源manifest和具体batch算术；目标环境有pyarrow时再导出并读回Parquet。模型/环境/逐题审核未完成时，状态明确为prepared_not_admitted，不因导出成功就允许可信效果实验。该示例与源码时序对齐，但本机未运行Linux/CUDA训练。

一个可手算的配置：Q=4、G=4、world=2、输入M=4、每GPU micro=2、TP=1、SP=1。全局16条回答、每rank8条；本版本worker归一化mini为M×G/world=8，固定累积4次。只看输入M或原脚本算术断言不够；默认TP=2在单卡不成立。用准备脚本先检查完整mini/micro与并行可整除，再谈显存、吞吐和效果。

**交付与验收：** 一份阶段说明链接本次配置、run_id/step、前后 checkpoint、实际参数变化、下一轮推理同步与恢复证据。关联 candidate → reward → advantage → 更新 → 下一轮生成，排除“actor 更新但 rollout 仍用旧参数”的解释。保存/恢复结果与固定开发验证可核对，GT 和 scorer 确实参与闭环。

**资源边界：** 受控 CPU 演示没有 actor 参数、梯度、权重同步与训练状态，不是训练复现；它也不是安全执行任意未知代码的 sandbox。真实任务须使用已验收的隔离后端与适合的 GPU/runtime。尚未跑则写待实跑；单步成功证明执行链，不宣称泛化提升，不要求先修完整工业系统才能开展一个小闭环。

## 作业 4.3：固定协议评测与 Bad Case 归因

**目的：** 从结果回到应修的环节，并用条件变化与独立迁移检验判断。

**有真实运行时：** 使用与 baseline 相同协议评更新模型，按 Task 聚合 pass@k，另列格式、逻辑、复杂度、运行和 infra 失败。记录所有生成候选、拒绝/重试、token、耗时与成本。开发验证用于日常回归，最终报告使用未参与方案选择的测试集。小题集或单步实验只支持其范围内结论。

效果实验在运行前登记：同一Task上的baseline/更新模型配对比较、固定生成seed列表或重复次数、按题与家族汇总、成本与停止标准。checkpoint仅用开发集选择；最终测试不参与选择。共同seed是协议记录，不消除采样与小题集波动；至少报告逐题差异和重复结果分布。需要更强结论时再做按题重采样区间或相应统计分析，不能把单次较好seed认作提升。预训练见过Hot100也可能影响结果，train/eval ID隔离不自动排除预训练污染。

**CPU 也可完成的条件变化：** 固定 `wrong_empty`，比较漏掉全负输入的 Tests 与补入 `[-3,-2,-5]→-2` 后的判定。只改变 Tests、冻结候选与 scorer，说明为什么分数变化说明覆盖/判定口径变化，不能归因为模型学习。再检查该 case 若被错写为 6 时，应该隔离错误 case 而不是用它奖励错误代码。保留前后版本与旧结果，重新验证 Tests 和 Verifier。

**无提示的独立迁移：** 自己设计一个未在示范中给出的合法输入和一种新的候选错误，独立推导 expected output、预测旧/新 Tests 的判定并给出区分检查；不得照抄已有反例。先纸面检查，实际执行未知代码需隔离环境。把诊断结果与最终未见题泛化结论分开。

再完成一次跨题迁移，使用真实v2 RL第556行“两数之和”：

```powershell
python -B RLVR学习资料/examples/maximum-subarray/practice.py transfer-init --run transfer-01
```

查看 `material.json` 的原题、接口、seed与三个固定候选，先独立写出题意允许的输出条件；只填写 `prediction.json` 的legacy/semantic预测和理由，再提交：

```powershell
python -B RLVR学习资料/examples/maximum-subarray/practice.py transfer-grade --run transfer-01
```

工具校验你看的材料与实际执行材料相同，随后比较原列表相等与语义合法性，运行并保存新 `semantic_ground_truth.json` 与同一Task的新 `prepared_task.json`。同题换判定规则需要新test_version；源码原始Tests不改。语义判定解决多合法排列，不认证通用完成协议或Sandbox。细节见[迁移操作](examples/maximum-subarray/EXERCISES.md#transfer-exercise)，提交后查[评分与答案](examples/maximum-subarray/ANSWERS.md#transfer-rubric)。

至少分析一个 Bad Case 的完整证据链：从 Task 与 prompt、合法输入、expected output、测试覆盖、比较规则、runtime 查起，才讨论模型和训练。给出竞争性解释及最小对照，例如训练 reward 提高而开发验证不变，分别检查覆盖不足、已见题优化、分布差异与策略退化，不直接认定其中一个原因。

**交付与验收：** 一份阶段说明保存逐题结果、条件变化、独立迁移与局部修复建议。建议写清预期收益、验证办法和停止条件。Task 错误修 Task，Tests 错误修 Tests，Verifier 或执行环境错误先修相应层；确认模型/训练问题后才讨论 SFT、reward 或继续 RL。判定改动需升版本并重验；只改 Tests/Verifier 而没训练，不称为模型能力提升。最终测试参与修复或选择后改记开发用途，并重新保留独立测试边界。

| 数据与GT | 自选且不同于教材已展开输入；完整答案依据，新GT含该条，坏行隔离且正确同输入保留 | 把hash当正确性证明，或新增配对没有实际进入GT |
| 判分与故障 | 用未知类别包指出责任层、具体字段与最小对照；能识别无错误与多层问题 | 将reward>0/退出0/计数齐全直接当正确 |
| 训练机制 | 独立算logprob/梯度变式、冻结量、clip两侧、uid重排、EOS和micro权重 | 梯度经判题程序、old/ref可随本次new求导、温度/位置错配 |
| 跨题迁移 | 从Two Sum题意推导完整合法性，原版与新GT均实执行，解释判定假阴性 | 只sort/set就宣布完整合法，或把材料替换当同一实验 |
| 评测与证据 | 正确算另一个(n,c,k)，区分reward/correctness/按题指标，说明开发与最终测试边界 | 固定池/改Tests/换k被讲成模型能力提升 |

0分=未完成或关键机制错误；1分=能在提示后修正但证据或独立推导不足；2分=独立解释、操作证据与反例齐全。机制通关需至少8/10，前四项均不得为0，且返工触发中的关键错误全部修正。程序退出0不自动授予通关；文字解释依[人工评分依据](examples/maximum-subarray/ANSWERS.md#graduation-rubric)。

最后不看文档，用三分钟讲“题意/测试→判定→相对信号→token概率→更新→独立评价”；再回答两个随机深挖问题，并现场定位函数。能记住抽象、又能用具体实现和反例补足，才达到本课的学习目标。
