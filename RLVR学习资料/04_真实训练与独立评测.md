# 阶段四：怎样证明训练真的有效——更新、同步、恢复与独立评测

**资料导航：** [资料首页](README.md) · [工业主框架](RLVR工业流程.md) · [00 全程走读](00_一条记录从原始Task到训练.md) · [01 数据与 GT](01_数据理解与GT构建.md) · [02 Verifier 与任务池](02_Verifier与任务池验收.md) · [03 Rollout 与 GRPO](03_Rollout与GRPO机制.md) · **04 训练与评测（当前）**

**先记机制：** 「训练有效」要拆成四件事，各要各的证据：参数真的变了，是更新；下一轮采样用的是新参数，是同步；保存的状态能接着训，是恢复；固定协议下比 baseline 好，才是效果。loss 非零、随机回答变了、目录里有文件、训练 reward 涨了，都不单独证明其中任何一件。

## 总览：04 在流程里做什么、长什么样

04 对应 [00 全程走读](00_一条记录从原始Task到训练.md#overview-00)七站里的 ⑦ 同步、验证、保存，加上 ⑥ 的真实运行。它要回答的问题是：怎样证明训练真的有效。答案落在四种证据上：

- 更新：同一参数前后有差异，且差异来自 optimizer step；本 fork 第一步学习率是 0，只跑一步参数不变。
- 同步：每次生成前 sharding manager 取 actor 的 `state_dict()` 装进 vLLM，包括验证时；要核对装进去的是哪一版。
- 恢复：checkpoint 里有模型分片、optimizer、lr scheduler、RNG 和 dataloader 状态 `data.pt`，没有 vLLM 的生成随机数。
- 效果：训练前锁协议和 baseline，训练后同协议评；dev 用来选 checkpoint，held-out 只评一次。

## 文字版导读：先把全篇顺一遍

第一次读，先把这一节读完，再按链接进细节；复习时只读这一节。

**第一节：四种证据。** 更新、同步、恢复、效果各自的证据和各自的假象：loss 非零不证明更新（lr=0 时有梯度无变化）；随机文本变了不证明同步（采样本来就随机）；目录里有 `global_step_64` 不证明能恢复（要看里面有什么、读回去是否一致）；训练 reward 涨了不证明效果（可能是格式学会了，或在训练题上过拟合）。详见[四种证据](#evidence-4)。

**第二节：评测口径。** 三个口径先核对：训练中的 `_validate()` 对每题贪心生成 1 个回答，`val/test_score/code` 是这些 reward 的均值，不是通过率，LeetCode 和 TACO 混在 `code` 下；原生 `eval_lct` 读的是 release 的完整题库、要求覆盖全部题、用带前缀的原生拼法，不读我们的 parquet 和 GT；本课小池用当前 GT 判定、按 task_id 记 `(n, c)`，只复用 `estimate_pass_at_k()` 的公式。课程的 4 个固定候选 `n=4, c=2`：pass@1 = 1/2，pass@2 = 5/6，pass@4 = 1；把 `bad_format`、`early_exit` 都算进去是 `n=6, c=2`，pass@1 = 1/3。`c` 要用可信的正确性状态定，不能用 `reward>0`，也不能用 `reward==1.1`。详见[评测口径](#metrics-4)。

**第三节：协议先锁。** 训练前写死：checkpoint、tokenizer、Tests、Verifier 版本、温度、seed、每题候选数、token 上限、超时；分母规则（格式失败、空回答、超时都是策略失败，占分母）；infra 政策（重试几次、仍失败怎么办）；dev 和最终测试的用途（dev 选 checkpoint，最终测试只评一次）。去污染两条：题号排除管不到换了题号的同义题，8 元词组重叠能查出来；held-out 按日期隔离。[05 第六环](05_实跑推演_Qwen3-8B.md#stage-eval)用一次推演说明「验证集就是评测集」会偏乐观、配对净胜比百分比相减可信、seed 标准差给噪声尺度。详见[协议先锁](#protocol-4)。

**第四节：一步真实更新。** 先算 batch：Q=4 题、G=4 答、2 卡、输入 mini 4、每卡 micro 2，全局 16 条回答，每卡 8 条，worker 把 mini 归一化成 4 × 4 / 2 = 8，固定累积 4 次；默认 TP=2 在单卡不成立。再追三条链：`update_actor()` → `update_policy()` 的 forward/backward/optimizer；下一次 `generate_sequences()` 进 sharding manager，`__enter__` 取 `state_dict()`、按 vLLM 版本走 `sync_model_weights` 或 wake_up + 加载权重，`__exit__` 卸载；`_save_checkpoint()` 写分片、optimizer、scheduler、RNG、`data.pt`，`_load_checkpoint()` 按 `resume_mode` 读回。单卡还有两个坑：vLLM ≥ 0.7 的单卡同步走 `hf` 格式会抛 `NotImplementedError`，单卡用 0.6.3；本 fork 第一步 lr=0，要看参数变化得跑两步。详见[一步真实更新](#update-4)。

**第五节：故障归因。** 结果不好，先从 Task、Tests、GT、Verifier、执行环境查起，最后才是模型和训练状态；每个结论给竞争性解释和最小对照。训练 reward 涨而 dev 不涨，分别检查覆盖不足、已见题优化、分布差异、策略退化。[05 第七环](05_实跑推演_Qwen3-8B.md#stage-attribution)把 reward 增量拆成格式部分和正确率部分（Base 起点前 64 步八成是格式），再按证据改第二轮。详见[故障归因](#attribution-4)。

**第六节：三项作业和自测。** 三套工具：`run_demo.py evaluate` 是固定示范；`practice.py transfer-init / transfer-grade` 是两数之和的跨题迁移；`prepare_training.py` 做 CPU 上的 batch 算术和小池导出，[训练准备 README](examples/training/README.md) 给 Linux 单卡 smoke 和恢复命令。

- **4.1 先锁协议，再分别记录 CPU 演示与真实 baseline。** 算 pass@k，写协议，没有 GPU 就把「真实 baseline 待实跑」写明。
- **4.2 完成项目最小真实更新、同步与恢复。** 有资源就跑一步加一次恢复；没有就把配置、检查清单和反例准备好。
- **4.3 固定协议评测与 Bad Case 归因。** 只改 Tests 看判定变化，做两数之和迁移，分析一个 Bad Case。

最后是[四阶段综合通关](#graduation)：把四个练习 run 连起来讲三分钟，再答两个随机追问。学完脱稿讲一遍 [60 秒口述](#oral-4)，再从[面试深挖](#interview-4)里随机挑一个追问。

## 先分清四种证据

| 要证明的事 | 什么算证据 | 常见的假象 |
|---|---|---|
| 更新发生了 | 同一参数（或其 hash）在 optimizer step 前后有差异，且 step 与 run/step 号对得上 | loss、grad 非零：lr=0 时有梯度无变化；本 fork 第一步 lr 正是 0 |
| 下一轮用了新参数 | actor 的 `state_dict()` 进了 vLLM，固定输入的数值随版本变化，时序在 `generate_sequences()` 之前 | 随机回答变了：采样本来就随机；函数名叫 sync 不证明装进去的是新的 |
| 能恢复 | 读回的 global step、optimizer、RNG、dataloader 与保存时一致，固定开发验证结果可核对 | 目录里有 `global_step_N`：只有目录名不证明内容完整；vLLM 的生成 RNG 没保存，不能承诺位级复现 |
| 效果 | 训练前锁定的协议下，更新模型对 baseline 的配对比较超过 seed 噪声，held-out 只评一次 | 训练 reward 涨：可能是格式学会了；dev 涨：dev 选过 checkpoint，偏乐观 |

**口述：** 更新、同步、恢复、效果是四件事，各要各的证据；日志里最容易看到的那个数字往往只是假象。

<a id="metrics-4"></a>

## 评测口径：三个必须先核对的

1. 本版本 `RayPPOTrainer._validate()` 设置 `do_sample=False`；vLLM 对应分支设 `temperature=0`、`n=1`。它是每个 Task 一条贪心回答的训练中验证，不能直接作为独立多候选 pass@k 实验。
2. `val/test_score/{data_source}` 对逐条 token reward 求和后取 `np.mean`，是 raw reward 均值。本预处理器将 LeetCode/TACO 均记为 `data_source="code"`，所以 `val/test_score/code` 会合并这些来源；它既不是 LeetCode 独立通过率，也不是二值 accuracy。三条格式合格回答全测试失败仍可得到均值 0.1。verl v0.4.1 把这个指标改名为 `val-core/{data_source}/reward/mean@1`，[05](05_实跑推演_Qwen3-8B.md#stage-curves) 的曲线用的是新名字，含义相同。
3. 原生 `eval_lct` 经 `evaluate(version, split)` 调用 `get_problem_file()`，按 release 的完整 problem_file 读取 Tests，并断言完整题库都被尝试。它不读取我们的 Parquet 或包装 GT，也不接混合 TACO 小池；它用带前缀的原生拼法，所以 v2 test 的参考解在它下面 pass@1 = 0.995（2026-10-15 在 venv 里实测）。将当前扩充 GT 的候选直接喂该 CLI，会回到旧 release 的 Tests/题集口径，不能用来验证这次新增 Tests。

**当前小池的做法：** 使用当前 Task 的 `ground_truth` 与原 scorer 完成判定，额外保存「Tests 是否完整执行、是否通过、格式/运行/infra 状态」；按 task_id 统计 `(n, c)`，只复用原生 `estimate_pass_at_k()` 的公式做聚合。CPU 演示以标准库计算同一公式，不导入原 CLI 的题库与执行器。`c` 由可信的实际正确性状态确定，不能只用 `reward>0`，也不能仅用 `reward==1.1`：报告的 `early_exit` 得 1.1，但 `audit_completed_case_count=0`、`correctness_pass=false`。教学 `data_pool.jsonl` 不是 trainer 输入的 Parquet；实际训练前须转换并核对路径和 schema。

公式：

$$
\widehat{\mathrm{pass}}@k = 1-\frac{\binom{n-c}{k}}{\binom{n}{k}}.
$$

课程的 4 个固定候选 `n=4, c=2`：pass@1 = 1/2，pass@2 = 5/6，pass@4 = 1；只有所有纳入的 Task 都有 `n ≥ k` 时才报告该 k。把 `bad_format`、`early_exit` 都算进去是 `n=6, c=2`，pass@1 = 1/3。四个算法候选是预选的教学组；真实模型生成时不能仿照这个分组把格式失败排除。

**口述：** 训练中的验证是贪心单回答的 reward 均值，不是通过率；原生 CLI 读的是另一套题库和拼法；自己的评测用当前 GT 记 (n, c)，只借 pass@k 的公式。

<a id="protocol-4"></a>

## 协议先锁：baseline、分母与 infra 政策

训练前写清，训练后不改：

1. **划分与用途。** 沿第一阶段的划分确认训练、诊断、开发验证与最终测试；同题跨版本和疑似家族泄漏要查。学习演示的 `diagnostic`、`train_ready=false` 表示实际判题/训练环境尚未验收，不表示已接受的 Tests 答案错误。
2. **固定的东西。** checkpoint、tokenizer、Task/Tests、Verifier/runtime 版本、温度、seed、每题候选数、token 上限、超时与停止条件。没有 GPU 时保留「真实 baseline/训练待实跑」，不补造数字。
3. **分母与 infra 政策。** 格式失败、空回答、提取失败、逻辑错误、超时且确认属于候选问题，都是策略失败，占生成候选分母。infra 另报数量、重试与成本，按预先登记的重试/停跑/不可比较规则处置，不能后验删除失败提高 pass@k。
4. **baseline 先于更新。** 环境可用且已验收后，对 baseline 真正生成并用当前 GT 判定，保存逐题 `(n, c)`、配置和成本；最终测试锁定后不参与调试、调参或修复选择，日常回归用开发验证集。
5. **去污染与 held-out。** 按题号排除只管同一题号；换了题号的同义题要用措辞比对（补强项 7 用 8 元词组、阈值 0.5，对 v1 test 找到 61 对同题号、3 对措辞重叠；对 v2 test 找到 1 对）。held-out 按日期隔离，只在最后评一次，不用它选 checkpoint。

**用 05 看一遍为什么：** [05 第六环](05_实跑推演_Qwen3-8B.md#stage-eval)的推演里，验证集就是评测集的那轮数字偏乐观；两轮在 dev 上几乎分不开（净胜 4 题），held-out 和 pass@8 能分开；配对净胜比两个百分比相减可信，seed 标准差给出噪声尺度。

**口述：** 协议是训练前的合同：固定什么、谁占分母、故障怎么办、哪个集合只评一次；结果出来再定规则，数字就不可信了。

## 一步真实更新：batch 算术、同步与恢复

**先算 batch。** 一个可手算的配置：Q=4、G=4、world=2、输入 M=4、每 GPU micro=2、TP=1、SP=1。全局 16 条回答、每 rank 8 条；本版本 worker 归一化 mini 为 M × G / world = 8，固定累积 4 次。只看输入 M 或原脚本算术断言不够；默认 TP=2 在单卡不成立。用[准备脚本](examples/training/prepare_training.py)先检查完整 mini/micro 与并行可整除，再谈显存、吞吐和效果；8B 模型在几张卡上放不放得下，查[显存帐](examples/training/显存帐_Qwen3-8B.md)。

**三条链各怎么追：**

| 链 | 本版本的路径 | 要核对的 |
|---|---|---|
| 更新 | `RayPPOTrainer.fit()` → `ActorRolloutRefWorker.update_actor()` → `DataParallelPPOActor.update_policy()` 的 forward/backward/optimizer | 同一参数前后差异与 run/step 对应；本 fork 第一步 lr=0，参数变化要看第二步 |
| 同步 | 下一次 `generate_sequences()` 前进 `FSDPVLLMShardingManager.__enter__()`：取 actor `state_dict()`，vLLM ≤ 0.6.3 走 `sync_model_weights()`，更新版走 wake_up + 加载权重；`__exit__()` 卸载或 sleep | 装进去的是哪一版；单卡时 `load_format` 变成 `dummy_hf`、同步走 `hf` 格式，vLLM ≥ 0.7 只实现了 `dtensor`，第一次生成就抛 `NotImplementedError`，单卡用 0.6.3 |
| 保存与恢复 | `_save_checkpoint()` 每 64 步写 `global_step_N/actor` 的模型分片、optimizer、lr scheduler、RNG，以及 dataloader 状态 `data.pt`；`_load_checkpoint()` 按 `resume_mode` 读回 | 哪些状态真的存了；sharding manager 里 vLLM 的生成 RNG 没存；换了数据集再恢复要去掉 `data.pt`，否则 dataloader 按旧数据集的状态继续（[05 的 your-02](examples/training/runs/qwen3-8b-grpo-yourplan-20261018/notes/your-02_plan.md) 续训时就这么处理） |

操作桥接见[训练准备与具体 Linux 命令](examples/training/README.md)：标准库命令能导出 6 条不同来源记录的 JSONL、来源 manifest 和具体 batch 算术；目标环境有 pyarrow 时再导出并读回 Parquet。模型/环境/逐题审核未完成时，状态明确为 `prepared_not_admitted`，不因导出成功就允许可信效果实验。本机未运行 Linux/CUDA 训练。

**上机前必查**（2026-10-15 核对，详见训练 README 的「实跑前必查」）：Hydra 覆盖值里的中文路径要加单引号；单卡装 vLLM 0.6.3；模型先下载到本地目录；先用一个正确解和一个错解做判分探针，没装 firejail 时原版判分器不报错、格式合格的回答全记 0.0；只跑 1 步参数不变，接着跑恢复命令再更新一次。

**口述：** 一步更新要追三条链：optimizer 走了一步且参数变了；新参数在下一次生成前装进了采样引擎；存下来的状态能读回去接着训。每条链都有一个常见假象。

<a id="attribution-4"></a>

## 故障归因：从结果回到该修的层

顺序是从数据到模型，不是反过来：

1. Task 与 prompt：题意、约束有没有传给模型，合法输入是什么。
2. Tests 与 GT：expected output 对不对、覆盖够不够、比较规则合不合理、测试版本有没有升。
3. Verifier 与执行环境：格式门、拼接、后端、超时、判题故障。
4. 评测协议：分母、k、题集、seed、是否用了 dev 选 checkpoint。
5. 模型与训练状态：最后才讨论 SFT、reward 设计、继续 RL。

每个结论给竞争性解释和最小对照：训练 reward 提高而开发验证不变，分别检查覆盖不足、已见题优化、分布差异与策略退化，不直接认定其中一个。Task 错误修 Task，Tests 错误修 Tests，Verifier 或执行环境错误先修相应层；判定改动要升版本并重验；只改 Tests/Verifier 而没训练，不称为模型能力提升；最终测试参与过修复或选择后改记开发用途，并重新保留独立测试边界。

**用 05 看一遍怎么拆：** [05 第七环](05_实跑推演_Qwen3-8B.md#stage-attribution)把 reward 增量分解成格式部分和正确率部分（Base 起点前 64 步八成是格式），把一次判题故障用三条指标证据定位到判题层而不是模型层，再按诊断改第二轮、用 held-out 验证——归因不是解释一次，是改完要能被验证。

**口述：** 结果不好先查数据和判分，再查协议，最后才是模型；每个归因要有竞争性解释、最小对照，以及改完怎么验证。

## 作业 4.2：完成项目最小真实更新、同步与恢复

**目的：** 有实际资源后，把第三阶段机制落实到 Code-R1 参数更新；没有资源时先完成源码追踪与运行准备，真实更新明确待实跑。

**操作：**

1. 用已选择的模型与资源制定小配置，核对数据路径、GPU/batch 关系、生成长度、判题并发、保存频率和退出条件，保留配置快照；不照抄原作者硬件设置。先完成 baseline，再更新。
2. 从一个批次追到真实生成、当前 GT 判定、advantage 与 actor update，关联 run_id、step、candidate/reward 记录及前后 checkpoint。调用或 loss 数字不能单独证明实际参数变化。
3. 追下一次 `generate_sequences()`：按[一步真实更新](#update-4)的同步链核对实际同步内容与 policy 版本，不能仅凭函数名和注释宣称使用了新参数。
4. 保存并恢复一次，核对 checkpoint、global step、优化器/随机数/dataloader 等实际保存的关键状态，以及固定开发验证的执行结果。哪些状态有保存由源码与产物决定，不能预先保证完整位级复现。
5. 先验收单步闭环，再决定是否扩大。测量耗时、显存/内存、token 和执行成本；规划估算与实测分开。没有 GPU 时，用[05 第一、四环](05_实跑推演_Qwen3-8B.md#stage-machine)和[显存帐](examples/training/显存帐_Qwen3-8B.md)把估算做一遍。

**交付与验收：** 一份 `notes.md` 链接本次配置、run_id/step、前后 checkpoint、实际参数变化、下一轮推理同步与恢复证据。关联 candidate → reward → advantage → 更新 → 下一轮生成，排除「actor 更新但 rollout 仍用旧参数」的解释。保存/恢复结果与固定开发验证可核对，GT 和 scorer 确实参与闭环。

**资源边界：** 受控 CPU 演示没有 actor 参数、梯度、权重同步与训练状态，不是训练复现；它也不是安全执行任意未知代码的 sandbox。真实任务须使用已验收的隔离后端与适合的 GPU/runtime。尚未跑则写待实跑；单步成功证明执行链，不宣称泛化提升，不要求先修完整工业系统才能开展一个小闭环。

## 作业 4.3：固定协议评测与 Bad Case 归因

**目的：** 从结果回到应修的环节，并用条件变化与独立迁移检验判断。

**有真实运行时：** 使用与 baseline 相同协议评更新模型，按 Task 聚合 pass@k，另列格式、逻辑、复杂度、运行和 infra 失败。记录所有生成候选、拒绝/重试、token、耗时与成本。开发验证用于日常回归，最终报告使用未参与方案选择的测试集。效果实验在运行前登记：同一 Task 上的 baseline/更新模型配对比较、固定生成 seed 列表或重复次数、按题与家族汇总、成本与停止标准。共同 seed 是协议记录，不消除采样与小题集波动；至少报告逐题差异和重复结果分布。预训练见过 Hot100 也可能影响结果，train/eval ID 隔离不自动排除预训练污染。

**CPU 也可完成的条件变化：** 固定 `wrong_empty`，比较漏掉全负输入的 Tests 与补入 `[-3,-2,-5]→-2` 后的判定。只改变 Tests、冻结候选与 scorer，说明为什么分数变化说明覆盖/判定口径变化，不能归因为模型学习。再检查该 case 若被错写为 6 时，应该隔离错误 case 而不是用它奖励错误代码。保留前后版本与旧结果，重新验证 Tests 和 Verifier。

### 四阶段综合通关：实际操作、抽象机制和追问

把 `data-01` 的新配对/GT/评分、`blind-01` 的诊断、`mechanism-01` 的报告、`transfer-01` 的迁移链接到自己的 `notes.md`。每题先独立答，再允许查源码；由同伴、教师或自己隔日复核，记录原回答与返工项。自动工具只验数值/类别/装配，不能证明文字理由或独立掌握。

| 项目（每项 0—2 分） | 2 分的可观察标准 | 返工触发 |
|---|---|---|
| 数据与 GT | 自选且不同于教材已展开输入；完整答案依据，新 GT 含该条，坏行隔离且正确同输入保留 | 把 hash 当正确性证明，或新增配对没有实际进入 GT |
| 判分与故障 | 用未知类别包指出责任层、具体字段与最小对照；能识别无错误与多层问题 | 将 reward>0/退出 0/计数齐全直接当正确 |
| 训练机制 | 独立算 logprob/梯度变式、冻结量、clip 两侧、uid 重排、EOS 和 micro 权重 | 梯度经判题程序、old/ref 可随本次 new 求导、温度/位置错配 |
| 跨题迁移 | 从 Two Sum 题意推导完整合法性，原版与新 GT 均实执行，解释判定假阴性 | 只 sort/set 就宣布完整合法，或把材料替换当同一实验 |
| 评测与证据 | 正确算另一个 (n, c, k)，区分 reward/correctness/按题指标，说明开发与最终测试边界 | 固定池/改 Tests/换 k 被讲成模型能力提升 |

0 分 = 未完成或关键机制错误；1 分 = 能在提示后修正但证据或独立推导不足；2 分 = 独立解释、操作证据与反例齐全。机制通关需至少 8/10，前四项均不得为 0，且返工触发中的关键错误全部修正。程序退出 0 不自动授予通关；文字解释依[人工评分依据](examples/maximum-subarray/ANSWERS.md#graduation-rubric)。

最后不看文档，用三分钟讲「题意/测试 → 判定 → 相对信号 → token 概率 → 更新 → 独立评价」；再回答两个随机深挖问题，并现场定位函数。能记住抽象、又能用具体实现和反例补足，才达到本课的学习目标。

## 60 秒口述

训练有效要拆成四件事：参数变了是更新，下一轮采样用了新参数是同步，存下来的状态能接着训是恢复，固定协议下比 baseline 好才是效果；loss 非零、随机回答变了、目录里有文件、训练 reward 涨了，各自都只是假象。评测口径有三个：训练中的验证是贪心单回答的 reward 均值，不是通过率；原生 CLI 读的是另一套题库和拼法；自己评测用当前 GT 记每题的 (n, c)，只借 pass@k 的公式，4 个候选 2 个对就是 pass@1 二分之一、pass@2 六分之五。协议在训练前锁死：固定什么、谁占分母、判题故障怎么办、dev 选 checkpoint、held-out 只评一次。结果不好先查数据和判分，再查协议，最后才是模型，每个归因要有竞争性解释和改完能验证的办法。
